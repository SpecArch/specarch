## Item 1690, round 2: routes answer 401, the nonce clause, the caching scope and the file a files route's test requests

Summary: the review of 4b7226fc asked for five changes, all taken: the
generated route guard answers 401 for a caller not signed in, the
derived golden of an application route names the nonce only when its
policy does, the technical specification names routes among what holds a
permission and writes each route's Cache-Control with its scope, and a
files route's test names the file it requests.

- `specarch-gen-go-dxlib`: the written handlers define `ErrNotSignedIn`;
  `routeGuard` answers 401 when `Allowed` returns or wraps it, or when the
  route's permission is `signedIn`, and 403 otherwise, so a service that
  mounts `RegisterRoutes` answers the statuses the validator gives the
  route and the cases `derive` writes. The compile-and-serve test covers
  the sentinel, a wrapped sentinel and a `signedIn` route.
- Both validators say "its policy naming a nonce made for this response"
  in an application route's golden only when a directive names `nonce`;
  `validate-routes-refused` re-recorded for route `asked`.
- The technical specification's Permissions paragraph names routes, and
  the Fixed routes table's Caching column reads as the server sends it,
  `public, max-age=...` or `private, max-age=...`, by the permission;
  every recorded technical specification re-recorded for the paragraph.
- A files route's test names its file as `input: { file: <path under the
  prefix> }`, checked in both builds (`file` alone, not empty, without a
  leading slash; `input` on another route is `test_data`), and the test
  generators request the prefix followed by the file; a files route test
  that names no file gets a body to write by hand, the comment saying
  why. The schema's `input` text, conventions, test-generation, ADR-216
  and SA-114 say so. New case `generate-tests-routes`;
  `validate-routes-valid` names the files in its tests;
  `validate-routes-refused` adds a file on a health route's test, a wrong

## Item 1691: development seed data generated from the entities

Summary: a `seed` target of its own, `specarch-gen-seed`, writes
`seed.sql`, made-up development rows for the tables `generate sql`
writes, drawn from the entities with a fixed seed so the file is the same
bytes on every run, in the four dialects (ADR-219, SA-116). The need was
read from a private project whose seed was SQL written by hand and
drifted from its specification; nothing of that project is here.

- `internal/genseed` and `cmd/specarch-gen-seed`: the tables through
  `gensql.ModelOf`, new, which also gives each `Column` the field it was
  rendered from (`Definition`) and its enum `Values`; sqlc is unchanged.
  The dialect is the seed target's, else the sql target's, else
  PostgreSQL, and the two must agree. Rows per entity from
  `settings.rows` (ten by default, 0 leaves the entity out), the seed
  from `settings.seed` (one by default), through a SplitMix64 generator
  written in the package so the stream never moves with a Go release.
- Values by field: bounds and `multipleOf` for integers, numbers and
  decimals at their precision and scale; "Field words N" text within the
  lengths; patterns walked through `regexp/syntax` and matched back;
  enums; dates, instants, times and durations in 2026 in each dialect's
  literal; uuids; binary in each dialect's hex form; emails, URIs, host
  names and addresses in the ranges RFC 2606, RFC 5737 and RFC 3849
  reserve for documentation; `examples` as the first rows, `const`
  everywhere; optional fields NULL in one row of four; value objects in
  columns present or absent whole with required parts set; JSON for json
  storage, lists of value objects and maps; PostgreSQL arrays for lists
  of scalars. Keys and uniques count up or are checked as tuples; check
  constraints evaluated on each row with `internal/expr` as `test_data`
  evaluates a fixture, a failing row drawn again up to a hundred times.
  Foreign keys at earlier rows, optional ones NULL in one of four, self
  relations at earlier rows, one-to-one at the same rank; the tables in
  dependency order.
- Errors at the entry, the entity gets no rows and the file says so: a
  required field encrypted at rest (the key and the hash's salt are the
  service's), a required relation to an entity with no rows or owned by
  another stakeholder, a required self relation, a cycle of required
  relations, a one-to-one with too few rows across, no row satisfying
  the constraints in a hundred draws, a key or unique column with fewer
  values than rows, an unsupported pattern. The dialect's literals live
  in the plug-in, not in type-rendering, so no idiom version moves and
  no snapshot changes.
- `seed` joins the estate targets in `cmd/specarch/generate.go`, so a
  field typed by another module's element is drawn as for sql.
- Cases: `generate-seed` (PostgreSQL), `-mariadb`, `-sqlserver`,
  `-oracle`, `-encrypted-refused`, `-dialect-refused`, `-rows-zero`.
  Unit tests: determinism and the seed, the four dialects' literals,
  the encrypted refusal, pattern values, literal forms.
- Spec: ADR-219, SA-116, the generate design names seed among the
  targets that read an estate, the layout, four sources (the three RFCs
  and the SplitMix paper), the implementation schema's `dialect` text.
  Docs: `docs/generators.md` (Development seed data), the roadmap (the
  "seed data per profile" line now says what is built and what waits),
  the README and plug-ins help (fifteen), `generate` help, the landing
  and regenerate scripts.
- The example gets a seed target writing `examples/library-lending/seed/`
  for the catalogue alone: a member's email is encrypted at rest, so
  members, loans and fee waivers are set to 0 rows and made through the
  service; the target's description says so.
- Left out on purpose: a seed per profile or environment; an encrypt
  expression per dialect for encrypted fields (it would need the key and
  salt delivered at load time, and the idiom names none); the fixture
  records of design tests as seed rows (they are each test's own). No
  dependency added.
- The handoff mailbox was empty.
