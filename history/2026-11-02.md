## Item 1690, round 2: routes answer 401, the nonce clause, the caching scope and the file a files route's test requests

Summary: the review of 4b7226fc asked for five changes, all taken: the
generated route guard answers 401 for a caller not signed in, the
derived golden of an application route names the nonce only when its
policy does, the technical specification names routes among what holds a
permission and writes each route's Cache-Control with its scope, and a
files route's test names the file it requests.

- `specarch-gen-go-dxlib`: the written handlers define `ErrNotSignedIn`;
  `routeGuard` answers 401 when `Allowed` returns or wraps it, or when the
  route's permission is `signedIn`, and 403 otherwise, so a service that
  mounts `RegisterRoutes` answers the statuses the validator gives the
  route and the cases `derive` writes. The compile-and-serve test covers
  the sentinel, a wrapped sentinel and a `signedIn` route.
- Both validators say "its policy naming a nonce made for this response"
  in an application route's golden only when a directive names `nonce`;
  `validate-routes-refused` re-recorded for route `asked`.
- The technical specification's Permissions paragraph names routes, and
  the Fixed routes table's Caching column reads as the server sends it,
  `public, max-age=...` or `private, max-age=...`, by the permission;
  every recorded technical specification re-recorded for the paragraph.
- A files route's test names its file as `input: { file: <path under the
  prefix> }`, checked in both builds (`file` alone, not empty, without a
  leading slash; `input` on another route is `test_data`), and the test
  generators request the prefix followed by the file; a files route test
  that names no file gets a body to write by hand, the comment saying
  why. The schema's `input` text, conventions, test-generation, ADR-216
  and SA-114 say so. New case `generate-tests-routes`;
  `validate-routes-valid` names the files in its tests;
  `validate-routes-refused` adds a file on a health route's test, a wrong
  key and a leading slash.
- Left out on purpose: nothing of the private project; the examples stay
  a notice board. The handoff mailbox was empty.

## Item 1689: a web UI target with no build step, Vue's runtime-only build with htm

Summary: `specarch-gen-ui-vue-htm`, the fourth UI generator, for a `ui`
target of platform web and framework `vue-htm` in a JavaScript
implementation file (ADR-218, SA-115): the menus, pages and actions as
plain data files under `config/`, one data file per page under `pages/`
compared by value, every call through one `api.call` over the plain
JavaScript transport, the components once under `screens/` on Vue and
htm alone with the table named by the idiom's `list-page` part,
`index.html` loading the vendored files with their integrity and nothing
inline, `vendor/manifest.js` from the libraries' files, strings, theme and
derived tests under `node:test`.

- The owner found the stack in a private project already specified in
  SpecArch, which wrote its pages and the data files mirroring the
  specification by hand. Nothing of that project is here: the design doc
  (`docs/ui-vue-htm.md`) describes the stack generically, and the
  example is the library lending one.
- Spec first: ADR-218, SA-115, the `files` map on a library in the 1.0
  implementation schema (subresource integrity per vendored file), the
  source `sri`, the `vue-htm` rendering of every `ui-components` part
  (1.12.0, with the table contract at `list-page`), the layout entries,
  and the Swift build's embedded schemas. The idiom override copies in
  the cases and the example move to 1.12.0.
- `internal/genscreens` gained the printer the TypeScript generator had
  (`print.go`, exported), `internal/genui` exports `ThemeCSS` and
  `IdentityProviderFile`; `genuits` keeps aliases and its output is
  unchanged.
- Decisions: the files and their hashes on the library, not a separate
  file list, since the library carries the version and licence a
  manifest row needs; paths under a declared application route, with
  `base` in the document, and fragments otherwise; one `api.call` in both
  dialects, the transport deciding; the table through the idiom part,
  never a component library in the generator; `vendor/manifest.js`, a
  module with the header on line 1 like every other file, not JSON.
- Cases: `generate-ui-vue-htm`, `-dxlib`, `-refused`, `-table-override`,
  `-hand-built`; `idioms-lists-ui-framework` re-recorded for 1.12.0.
- Docs: `docs/generators.md`, `docs/ui-vue-htm.md`, `docs/idioms.md`,
  `docs/ui-design.md`, `docs/roadmap.md`, the README, the plug-ins help
  (fourteen, naming register too), the landing and regenerate scripts, a
  CI job for the example's derived tests and vendored files.
- The example: `examples/library-lending/web-vue`, generated from a
  JavaScript implementation file, with Vue 3.5.43 (MIT, copied from the
  owner's own node_modules) and htm 3.1.1 (Apache-2.0, not MIT as first
  assumed; fetched once from the npm registry on the owner's yes, the
  tarball's sha512 checked against the registry's record) committed under
  `vendor/` with their licences, the loan form's hook and the Indonesian
  texts written by hand. `web-vue/smoke` runs the generated application
  under node on the vendored Vue and htm over a small browser stand-in
  with the service stubbed, ten checks over every page kind; it found
  nothing wrong in the screens after the first run.
- The handoff mailbox was empty.
