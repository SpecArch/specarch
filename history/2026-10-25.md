## Paging names never empty in server/settings.ts (BUG-061)

Asked by the owner (item 1226), from a side finding of item 1209: the
Next.js generator wrote `server/settings.ts` with every paging wire name
empty when the ui target had `settings.server` and the specification no
`listOf`, and `tests/server.test.ts` paged by those empty names; visible
in the golden `generate-ui-typescript-estate-picker`, whose loans module
lists nothing itself. The names come from the paginated-list idiom, and
`specarch generate` hands a plug-in only the idioms whose keywords the
design uses (`reads: [listOf]`), so a design with no `listOf` gave the
plug-in no idiom and the generator wrote the names empty, saying nothing.

Decided after review: not a refusal. A module whose lists are all paged by
the server has no `listOf` by design (ADR-074), and refusing
`settings.server.pages` there would have left the feature usable only
beside some unrelated `listOf`. Instead the ui target's request carries
the paginated-list idiom whether or not the design has a `listOf`, for the
implementation files and the dependencies alike, with the file's exclusion
or override still applying (`validate.IdiomUsesWith`, `pluginIdioms`).
The generator, `forward.ts` and the derived test are unchanged;
`specarch idioms` and the documents list the idioms as before.

The other writers of these names were checked: the list page and the
picker of the Next.js, SwiftUI and plain JavaScript generators refuse
before writing when the names are missing, and SwiftUI writes no server
names; `server/settings.ts` was the one unguarded writer, and no example
output held an empty name (the estate's reading room is plain JavaScript).

The new golden `spec/tests/generate-ui-typescript-paged-whole` gives a
specification with no `listOf`, one list read whole and paged by the
server, and expects the names filled; its generated `tests/server.test.ts`
passes under node 26, and with the names emptied by hand its page test
fails, since the envelope's three members collide on one empty key. The
two estate-picker goldens changed in their `wire` line alone: the names
`page`, `pageSize`, `items`, `totalItems` and `totalPages` in place of
empty strings.

Review of the change found one path still silent: an implementation file
that excludes the paginated-list idiom beside `settings.server` got the
idiom from the request, skipped it as excluded, and wrote the names empty
as before. `server/settings.ts` now leaves the `wire` member out and
reports an error under the settings naming the idiom and "keep the idiom",
in the words of the list page's refusal; SA-56 lists the refusal. The red
case `generate-ui-typescript-paged-whole-refused` is the golden's
specification with the exclusion, refused at the settings and at the list
page's source. Second commit, on main.

## A reference inside another module's element resolves through that module's dependencies (BUG-062)

Asked by the owner (item 1227), from a side finding of item 1209:
`internal/xref` looked a reference inside an imported copy up among this
specification's own dependency names, so in a chain loans → customer-registry
→ places the registry's `streets#/schemas/Street` resolved only when loans
also declared places under the key `streets`.

Why the limit existed: it was not a rule. ADR-112 and ADR-184 import "what
each names in its own specification in turn" and say nothing of a module's
own dependencies; the plug-in request simply carried only the modules this
specification names. It protected nothing: the version a module's
dependency pins is already checked when that module is validated in the
run, before any plug-in runs (checked: places at 3.2.0 against the
registry's 3.1.0 is refused at the registry's dependency, nothing produced),
and there is one specification per name in a run. It was worse than a
limit: without the key, `generate openapi` exited 0 with
`$ref: '#/components/schemas/Street'`, a component that does not exist, and
a key that named another module would have resolved into it.

The fix keeps every rule (ADR-185): each dependency in the request carries
its own dependencies that name a specification, with the version each
pins, and the request carries `modules`, the specifications of the run the
dependencies reach through their own, at any depth, by `info.name`;
`internal/xref` resolves a reference inside a copy through the module it
came from. A specification declares a module only where it names it
itself. A module the run does not give is `reference` at the entry that
led to it: "customer-registry#/schemas/Address names places#/schemas/Street
through customer-registry's dependency streets on places 3.1.0 (loans →
customer-registry → places), and this run does not give places, ...; give
places in the run, as a module of the estate or a folder beside the
others; loans need not declare it". The cycle check is unchanged (copies
are tracked by module name and pointer). Additive: no schema change, a
specification whose dependencies repeated the key gives byte-identical
output (compared against the build before this change), and the request
gains optional fields only.

Not done: a module that names an element of the specification being
generated, back up the chain, gets that element imported as a copy and so
refused as a name the specification already declares, as before; writing
it as the specification's own element would be a further decision. Not
checked: list pages and pickers over another module's entity read its
fields as they stand there, as before this change.

## Design: the reason behind every edit of a specification

Asked by the owner (item 1228): track why each decision in a specification
was taken, for every add, change and delete, so that a reader of an
element sees the reason, who decided, when and what it replaced. A design
item: `docs/decision-tracking-2026-10-25.md` is written and no code,
schema or generator changes.

What it found, from the docs, the schemas and the validator: the reason's
one home exists, the decision record (`why`, `cites`, `decidedBy`,
`answers`, `supersededBy`, and `decidedIn` on the element), and a change
request's `reason` and `decision.why` are already required. The gaps are
what is required and what is linked: `why` is optional on a decision;
`decidedBy` is required only with `answers`; an element may name a
decision only with `origin: decided` (`origin_decision`), so a spec-first
element cannot point at the decision behind it; nothing holds the
alternatives rejected; a delete, a rename, a move, every status step of a
requirement and a decision but superseded, a deprecated decision or field,
a withdrawn change or release and a defect's triage leave no reason but
git; and nothing lists what has no reason. In this repository's own
specification 5 of 176 decisions lack `why`, none carries `decidedBy`, and
no element carries `decidedIn`; every commit is the owner's, so git cannot
tell an agent's edit from the owner's.

The design keeps one construct and is additive to meta-model 0.3:
`alternatives`, `governs` and `proposedBy` on a decision, the warnings
`decision_reason`, `decision_decider` (under `tracksOrigin`) and
`retired_reason`, a Reasons section in `gaps` and the `questions`
document, the diff against the approval that ADR-083 step 8 plans with
the reason printed beside each changed element, and `supersededBy` and
`governs` among `specarch model`'s references. The rule "an element
changed since approval has a change record with a reason" is `diff`'s
`covered` check against the approved commit, never a `validate` rule. The
one breaking part, `why` and `decidedBy` required on an accepted decision,
is meta-model 0.4 and 0.8.0, for the owner. An agent never writes a reason
as the owner's: its conclusion is `origin: inferred` with `why`, or a
proposed decision with `proposedBy: agent` and a question for a human;
"reason not recorded" is the absence of `why`, listed, never a sentence.
Eight editor items are listed for approval, none built. The smallest
first step is phase 1: `alternatives`, `decision_reason`, the Reasons
section, and one `could` question per accepted decision here that lacks
`why`, for the owner to answer.

Open for the owner: `why` and `decidedBy` as warnings now and errors in
0.4; ADR-083 section 8.1 (a decision naming the change request it
settles); `governs` on the decision against `decidedIn` without origin;
`proposedBy: agent` as a value against a declared stakeholder; a retired
or deprecated element without a reason as a warning or an error; which
editor items to queue. Generic examples only; nothing was left out on
purpose. The handoff mailbox was empty.

Review round 1 (two comments, both bugs in the design, both taken): `retired_reason` was satisfied by the element's own `why`,
which section 1.3 says is about the requirement and not about the step,
so a requirement accepted with a `why` and retired later would never
warn; now only a reason for the step counts, a change record whose
`affects.removes` names the element (with `change_applied` extended to a
deprecated decision or field) or the accepted decision that deprecates
it, naming it under `governs`, and a key of its own is named as the
rejected alternative; E5
offers those two or nothing, never a `why` on the element. Phase 1 had
the agent write `why` for the owner's decisions that lack one, against
section 4's rule that an agent never writes a reason as the owner's; now
the agent writes one `could` question per decision and `why` only from
the owner's answer, as question 7 for the owner, and the count is four
(ADR-001, ADR-002, ADR-006, ADR-009): ADR-007 lacks `why` too but is
superseded and outside `decision_reason` on purpose, its step's reason
being ADR-010's `why`. The questions need a declared owner role first,
since the specification's stakeholders hold none.

Review round 2 (one comment, a bug in the design, taken): the second
branch of `retired_reason`, an accepted decision whose `governs` names the
element, was met by the decision that shaped the element when it was
written, since `governs` names what a decision shapes; retire the element
later and that decision silences the warning while saying nothing about
the retirement, and "whose decision states the retirement" is free text
`validate` cannot check. The branch is out. `retired_reason` now reads one
thing, the only one `validate` can check: a change record, implemented or
released, whose `affects.removes` names the element, its `reason` and
`decision.why` already required; the element's own `why` and a decision's
`governs` count for neither, and the `governs` branch joins the key on
the element as a rejected alternative, with the reason (`validate` sees
one version, the element carries no date for the step, and the validator
never reads git, so the reviewer's other fix, a decision dated on or
after the step, cannot be built). Section 3.4, question 5, E5 and the plan
follow: E5's Decide this… on Retire… and Deprecate… writes the decision
and the change record beside it, linked as question 2 settles;
`retired_reason` and the `change_applied` extension move from phase 4 to
phase 2, since they wait on no question (question 5 asks only whether the
warning becomes an error). One consequence stated plainly: a requirement
retired or a decision deprecated with no change record warns in
development too, where a record may be raised with `phase: development`,
and a requirement that no longer applies before any approval is as well
removed. `diff`'s reason beside each element keeps the newer decision,
since `diff` holds both sides and can tell it from an older one.
Also corrected: section 1.3's development row cited `docs/maintenance.md`
for the sentence that an answer to an open question of an unapproved
specification is not a change request; the sentence is in
`docs/refinement.md`, under the decision that closes a question.

## A flow step with no event is told only that its event is missing (BUG-063)

Asked by the owner (item 1231), from a side finding of an earlier item: a
flow step with a page alone got `action is missing` from the schema beside
`event is missing`, at the same step. The `flowStep` rule's `if` read only
`event: { const: action }`, which holds when `event` is absent, so its
`then` asked for an action.

The `if` now also requires `event`, so the rule asks for `action` only of
a step whose event is `action`. The `else` (no `action` beside another

step with no event to the event message alone, which fails against the old
rule.

The case `validate-flow-step-missing-key` gains a fourth step with a page
alone and expects `event is missing` alone there; built before the fix it
gives both messages. It is the one golden that changed. The step with

## A value kept in columns is checked in the module that declares its schema

Asked by the owner (item 1232), from a side finding of item 1225: for an
entity's field typed by another module's schema and kept in columns, the
default, neither build checked any rule on the parts of the value, since
the value object check read one specification. A value in columns whose
schema had no required part, or held a list, itself or an entity, passed
when its schema was declared in another module and was refused when it
was declared in the module itself.

Both builds now check one value kept in columns as one of the module's
own schemas, wherever the schema is declared. Each reference inside the
value is read in the module that declares it, so `#/schemas/Phone` inside
another module's schema is that module's `Phone`, and a part typed by a
third module's schema is read through the second module's dependency; a
cycle is found across modules too. A schema of another module is named in
the message as `<Name> of <module>`. The same reading applies to a part of
the module's own schema that is typed by another module's schema, which
also went unchecked before.

When the run does not give a module the value reaches, the field gets one
warning, under the new rule `value_object_unchecked`, at the field: it
names the schema, the module, the rules left unchecked and how to have
them checked (give the module in the same run or through the estate, or
store the field as json). It is a warning and not an error because a
module alone still validates (ADR-112) and what is missing is the run's;
it is printed as every other problem line, so the editor lists it with its
rule and id. No warning is added where a reference error already stands:
a dependency not declared or with no specification, two specifications
given under one name, a schema the other module does not have, or a
module that is given and does not parse. A field stored as json, and a
list, which is json only, are not touched.

ADR-184 (decision and why), SA-50 and the Rule enum (`value_object`
extended, `value_object_unchecked` added) say so.

### Release note: new errors and warnings, and the fix for each

A 0.3 specification that passed may now get these, all at the entity's
field (`/entities/<Entity>/properties/<field>`), when the run gives the
module that declares the field's schema:

- `value_object`: `<field> is optional and <Name> of <module> has no
  required part that is never null`. Make the field required, store it as
  json, or have that module make a part of the schema required and not
  nullable.
- `value_object`: `<field>.<part> is a list of <Name> of <module>`. Store
  the field as json.
- `value_object`: `<field>.<part> is <Name> of <module> again, inside
  <Name> of <module>`. Store the field as json.
- `value_object`: `<field>.<part> refers to <Entity> of <module>, a record
  of its own`. Store the field as json, or relate the entity to that
  module's entity.

When the run does not give that module, the field gets the warning
`value_object_unchecked` in place of these, and validate still exits 0
for them. Give the module in the run, or store the field as json. One of
them stays an error without that module: a part that is a list of
another module's schema (`<field>.<part> is a list of <Name> of
<module>`), since a list has no columns whatever it holds; the name comes
from the reference.

## Design: meta-model 1.0.0

Asked by the owner (item 1230): bump the meta-model to 1.0.0 without
stranding existing specifications. `docs/meta-model-1.0.0.md` is the
design; nothing is built, since five decisions in it are the owner's.
The owner's reading is confirmed: 1.0.0 is the version of the
specification's format (the `specarch:` line, the design schema and its
fragment schemas), not the program's; the program would ship it as
0.8.0, and whether the program should be 1.0.0 too is question 1.

The design says what 1.0.0 freezes (every key with its place, type,
allowed values and required-ness; the meaning of every key, reserved
word and expression; what is an error), what a 1.x may add (optional
keys, values, derived cases, warnings), what a 2.0.0 is, and how a
keyword is deprecated (JSON Schema's `deprecated` annotation, a
`meta_model_deprecated` warning, removal only in the next major). It
lists every deferred item of the 0.2 and 0.3 plans and the documents they
lead to: all but two are additions any 1.x can take; the two breaking
ones are the "read until 1.0" promise of ADR-055 and ADR-094 for 0.1 and
0.2 files, and the reasons the decision-tracking design plans as errors
for a meta-model 0.4, which 1.0.0 replaces. Of the keys the design
schema declares in more than one definition, `rows` (a role's row rule
and a view's relation rows) and `source` on the handover mean two
things; renaming them is proposed, and `via`, `when`, `flow` and
`client` are kept with the reason for each. A 0.3 file is read beside
1.0.0 until 2.0.0 with a warning naming `specarch upgrade`, the verb
proposed in place of `migrate` because `migrations` already names the
database's; it edits lines in place and has a dry run.

Counted for the plan: 732 conformance cases, 449 on 0.1, 15 on 0.2; 245
expect the `meta_model_version` warning; 161 of the 0.1 cases expect a
missing-test warning that is an error on 0.2 and later; 49 cases and 274

Found on the way, not changed: `docs/meta-model-0.3.md` still shows
`callers: clients` and the `actor` claim, which caller context replaced;

## Meta-model 1.0.0: read 1.0.0 beside every earlier version, two keys renamed, the conditionals fixed

The validator reads a specification that says `specarch: "1.0.0"`, or any
later 1.0 patch, against a new design schema,
`schema/specarch-design-1.0.schema.json`, and keeps reading 0.1, 0.2 and
0.3 against `specarch-design-0.3.schema.json`, each with one warning that
now names `specarch upgrade`. A version line it does not read (`"1.2.0"`,
`"1.0"`, anything else) is an error at the line, and the file is read as
1.0.0 so that every other problem is still listed. Both builds.

The owner's answers to the design's five questions (2026-10-25): every
file kind goes to 1.0.0, and the program is 1.0.0; every earlier version
stays read, none dropped, and the 463 cases on 0.1 and 0.2 stay on their
versions; a missing reason of a decision is a warning in 1.0.0, not an
error; `rows` on a role becomes `rowPolicies` and `source` on the
handover `sourceDelivery`, the old keys deprecated and still read; the
verb is `specarch upgrade`. ADR-186 records them.

What changed in this step:

- The 1.0 schema is the 0.3 schema with the version line as a pattern
  per minor (`^1\.0\.(0|[1-9][0-9]*)$`), `rowPolicies` beside `rows` and
  `sourceDelivery` beside `source`, each old key marked
  `deprecated: true`, and the conditionals of `source`, `constraint`,
  `parameter`, `page`, `workflowStep` (on `kind` and on `onDeadline`) and
  `decision` each requiring the key their `if` reads, the side finding of
  BUG-063. `TestConditionalsAcceptWhatTheyDid` proves on every such object
  of the library lending example and SpecArch's own specification, with
  the key absent or given each value and each branch key kept or
  dropped, that 1.0 accepts and refuses what 0.3 does; only the second
  messages go. The 0.3 schema changed only in the description of its
  version line. `tools/fragment-schemas` writes the seven fragment
  schemas of each version; a tree's hint lines name those of its own
  version.
- A file on 1.0 that gives `rows` on a role or `source` on the handover
  gets a `meta_model_deprecated` warning at the key and is read as the new
  key; both spellings in one object is an error at the old one. A file on

## Meta-model 1.0.0: `specarch upgrade`

`specarch upgrade [--dry-run] [--to <version>] <folder or file>...` moves
a specification and every file it is read from to 1.0.0, in both builds,
designed first in `spec/design/commands/upgrade.yaml`. It reads each file
of the tree (the root file, the stage files and tests, the implementation
files and the idioms beside them, the records, an estate named) and
rewrites only the version line of its format, the first line's editor
hint (to the 1.0 schema of its kind: a release URL at the program's tag, a
relative path in the same folder) and the keys 1.0.0 renamed, at the line
and column the parser gives; every other byte stays. A key the reader
adds (a tenant's derived row policy) is not in the text, so nothing is
written for it.

Steps left to the author are found by checking the specification as if
its line said 1.0.0: every error it would have then that it does not have
now (a field named `caller` in a 0.2 file, a test a 0.1 file lacks), a
key given under both spellings, and a file the parser cannot read. Its
other problems are `validate`'s, so an incomplete specification upgrades
cleanly. Exit 0 when nothing is left to the author, 1 when a step is, 2
for a usage error, a path that cannot be read or written, or a `--to`
other than 1.0.0. On standard error it names `specarch derive` when the
steps are missing tests.

`extract` and `merge` write trees on `"1.0.0"` with the 1.0 schema hint;
the expected trees of the 116 `extract-*` and `merge-*` cases changed in
those two lines only, by one replacement each. The README gained the
compatibility statement and the upgrade commands.

Ten cases: `upgrade-dry-run`, `upgrade-writes-changes` (comments, a
single-quoted version line, a flow-style `rows`, a quoted `source`, an
implementation file, an idiom and a record, byte for byte) and
`upgrade-second-run`; `upgrade-0-2-caller` and `upgrade-0-1-missing-tests`
(steps, exit 1); `upgrade-estate` (an estate on 0.1 over modules on 0.3 and
1.0.0); `upgrade-both-keys`; `upgrade-unreadable-file`; `upgrade-to-older`
and `upgrade-usage-error`. The Swift conformance runner now runs the
`upgrade` cases too. A run on a copy of `examples/library-lending` made 265
changes in 257 files, left `validate`'s output as it was, and a second run
changed nothing.

For the release (item 1229): the hint a release URL moves to names the
program's tag, `v0.7.5` today, so `upgrade-writes-changes` and the
`extract-*`/`merge-*` expected trees move to the release's tag with the
other hints when the version is bumped.
