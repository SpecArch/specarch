## extract go follows a helper that returns the group it makes

Reported from a project that extracts a Go codebase with 0.6.4: a gin
service registers routes on a plain group, through a local helper that
takes a prefix and a callback (read since 0.6.4, BUG-018), and through a
local helper that takes a prefix and returns the group, `g :=
returned("/d")` with routes on `g`. Expected 5 operations, got 3: the
two on the returned group were missing, with no question or warning.
BUG-022.

Cause, in `internal/extract/golang_routers.go`: a call of a function
value held in a local name, or bound to a parameter, was followed only
as a statement, never as a value. The router a call gives was a
library's maker, a group or subrouter, or what a function of the module
returns, so the name assigned from such a call held no router, and the
routes on it reached no registration, counted or asked. Latent beside
it: a literal's `return` set the return of the function it is written
in, so a function that declared such a helper and then returned its own
group could hand a caller the helper's group instead.

Fix: the walk of a literal gives the router the literal returns and
keeps the return of the function it is written in apart from it; a call
of a held function gives that router, so a call of one is the call's
value, and the statement walk leaves a call already followed as a value
alone. The walk paragraph of `spec/design/commands/extract.yaml` says
that the router such a call returns is the call's value, a literal's
return never standing for the return of the function it is written in;
`docs/extraction.md` step 15 says a helper returning the group it makes
is followed through its value; `docs/techspec.md` is regenerated, the
other document targets unchanged.

Tests: `TestGoRouterReturnedByHelper` in
`internal/extract/golang_test.go`, seven cases: a closure returning the
group assigned in a block, one called with two prefixes and in a chain,
one registering a route before it returns, one passed to a function of
the module that calls it for the group, a function of the module
returning the group called by name and passed as a value, and a literal
whose return must not become the return of the function around it
(which wrote a route under the wrong group before). All seven failed
before the fix and pass after it, together with
`TestGoLiteralSeesWhereItIsWritten`, which now shares the harness
`goRoutesCases`. The whole module passes `go test ./...`, the validator
passes on `spec/` and `examples/`, and every document target checks
clean.

Left out on purpose: the reporter's service names, route names and
route counts. Not touched: the Swift build (extract is Go only), and
ADR-081 and `docs/reading-code.md`, which do not state the walk at this
level. The handoff mailbox folder was empty. The fix is commit dda47fdd;
the commit after it records that hash here and in `BUG_HISTORY.md`.

## merge adds up a role's grants from trees that declare different permissions (ADR-127)

Handoff 15 processed. A specification merged from the permission tables
of several services, one tree each, lost every grant of a role that was
in more than one table: merge compared the two lists as any key, left
the role's `permissions` out with a must question asking which list is
right, and the question blocked every permission the lists name that no
other role grants. The sender expected the union of the lists with both
citations and no question.

Rule chosen: a tree's list of a role's grants says nothing of a
permission the tree does not declare in its `permissions` section, so
the lists of several trees add up, the first tree's then what each
later tree adds, with every tree's citation and one "joined:" line
naming the trees. A permission one tree grants that another tree, which
has the role, declares and does not grant is still a disagreement: the
list is left out, and the must question names each such permission
with the trees that grant and withhold it, beside the lists each tree
gives, and blocks the ungranted permissions as before. A role a printed
and a parsed tree both give is still compared grant by grant with the
printed grants kept. Not taken: the handoff's rule of joining the lists
whenever the trees come from different sources, since a documents tree
that lists a role's permissions and leaves one out would then be joined
silently with the code that grants it, against "never choose between a
document and the code"; and two trees of one source key are already
joined or refused as one source, so the only same-source case left is
printed against parsed. The handoff's own term for the merged files was
left out of the repository.

Code: `roleGrants` in `internal/extract/merge.go`, run after the last
tree is in and before the disputed keys are left out, so the order the
trees are given no longer decides whether a list is a dispute (the old
check in `mergeNode` saw only the trees read so far); `mergeNode` skips
a role's `permissions`; `disputeQuestions` words the why of such a
dispute with the grant withheld. Design: the rule in
`spec/design/commands/merge.yaml` and its standard output line, the
new ADR-127 with its reason, a bullet in SA-45's acceptance list, and
the paragraph in `docs/from-sources.md`, section 3.2. `docs/extraction.md`
is unchanged: the lending desk's roles are printed and parsed, which
this does not touch.

Cases: new `merge-role-grants-add-up` (two services' tables, each
declaring its own permissions and granting one role of the same name
its own: the role gets both grants with both citations, the joined line,
and no question on the grants) and `merge-role-grants-withheld` (both
tables declare one permission, one grants it to the role and the other
has the role and withholds it: the list is left out and the must
question says which tree grants and which withholds). `merge-role-names-
disagree` already held this very dispute beside the wire-name question
it is about; its role now gets every grant of both tables and only the
wire-name question is asked.

Checks: `go test ./...` with the conformance suite, `swift test`,
validate on `spec` and `examples` (0 errors; SA-57 unverified as
before), the Go and Swift validators print the same output on `spec`,
`examples` and both new merged trees, and `examples/lending-desk/extract.sh`
run with the binary before and after writes the same bytes. Every
document target of CI regenerated. No dependency change. The handoff
mailbox folder was empty. Simulator: not needed, no app code.

## extract database reads a partition as its table (BUG-023, ADR-128)

From a handoff: a system read through `extract database` has partitioned
tables, and the reader wrote an entity for each partition beside the
table's, each with the primary key and the indexes the partition takes
from its table, so every generated default and every index was a could
question once per partition. `check` would have reported each partition
as a table the specification does not hold. The handoff named the
product, its table and key names and the PostgreSQL version it runs;
none of that is in this repository, and the case here is written from
scratch around a table of events. The handoff mailbox folder was empty;
the handoff itself lives outside every repository and stays there.

What changed, in one commit:

- `tools/catalogue/catalogue.sql` prints for each table `partitionBy`
  (pg_get_partkeydef), `partitionOf` (the schema and name of the table a
  partition is a partition of) and `partitionBound` (pg_get_expr of
  relpartbound), and for each constraint and index `inherited`. A
  constraint is inherited when `coninhcount > 0` or `conparentid <> 0`:
  a partition's key and foreign key carry both, an inherited CHECK only
  the count, since PostgreSQL creates it with no parent constraint. An
  index is inherited when pg_inherits has a row for it.
- `internal/extract/database.go` reads a partition as the table
  `partitionOf` leads to, through a partition of a partition as well. No
  entity is made for it; the table's citation names the partitions; one
  could question at the entity lists them with their bounds; a
  partition's own constraint, index or column setting is a could question
  citing the partition's entry; a foreign key to a partition is a
  relation to its table with a question; a partition whose table the
  dump does not list is read as a table of its own. The counted line
  says how many tables are partitions, and the wrote line says one entity
  per table that is not a partition, only when the dump has one. An
  index definition with `ON ONLY`, as pg_get_indexdef prints a
  partitioned table's index, is a plain index as any other.
- `internal/extract/check.go` compares no partition, so none is a table
  the specification does not hold; the `ON ONLY` index is compared as
  the plain index the mapping lists.
- Spec first: ADR-128 (satisfies SA-44 and SA-72), the database bullet of
  `spec/design/commands/extract.yaml`, the catalogue bullet of
  `spec/design/commands/check.yaml`, one acceptance bullet each on SA-44
  and SA-72, and the cases `extract-database-partitioned-table` and
  `check-skips-a-partition`: a table partitioned by range with a check and
  a plain index, a partition partitioned again by list, a partition with
  its own column default, and a default partition with a check and an
  index of its own. The documents are regenerated; `docs/extraction.md`
  and `docs/from-sources.md` each gain a sentence.
- BUG-023 is recorded in `BUG_HISTORY.md`. The fixing commit's hash cannot
  be in the commit itself, and a branch is rebased when it lands, so the
  entry names the commit by its message, `Fixes BUG-023`;
  `BUG_OUTSTANDING.md` moves the next free number to BUG-024.

The reader's design choices are in ADR-128: partitioning is physical
design, as an index is, so it stays a could question until the mapping
has a key for it; a partition's own constraint holds for its rows alone,
which the meta-model cannot say, so it is left out with a question rather
than read as the table's.

Checks: `go test ./...` passes with the two new cases; `validate` passes
on `spec/` and the examples; the regenerated documents differ only where
this item changes them. The validator's two builds are untouched, so the
Swift build needs no change.

The catalogue dump of the two cases is the output of
`tools/catalogue/dump-catalogue.sh` on the case's migration, run in a
repository built as the conformance runner builds it, so the dump names
that repository's first commit, 0ef0e4e3bac900e108dee9363ce651f02c3accf9.
The Podman machine's disk was full to the byte for most of the item, and
every container job on this Mac failed with "no space left on device".
The owner's first decision, a prune of the unused images, could not free
it, since podman could not rewrite its image index on a full disk; the
owner then enlarged the machine's disk to 53 GB. Until then the work was
developed against a dump written by hand from PostgreSQL's documented
catalogue output, and the real dump matched it byte for byte, so nothing
in the expected files changed. What the real dump confirms: the range
bound as `FOR VALUES FROM ('2026-01-01 00:00:00+00') TO ('2027-01-01
00:00:00+00')`, `ON ONLY` in the definitions of the partitioned tables'
indexes, the names PostgreSQL gives a partition's inherited index and key
(`events_default_at_idx`, `events_default_pkey`), a partition's copy of
the table's check marked inherited, and `'sale'::text` and
`CHECK (((kind)::text <> ''::text))` as the catalogue spells a default
and a check.

## Deployment: who runs an environment, and a handover for a customer who runs one (ADR-129, SA-73)

The owner asked that a specification cover deployment in two parts: the
environments the vendor runs (what is deployed where, how it is built from
source with a pinned toolchain and base images, how it is installed,
configuration and secrets by name and source only, the checks after each
deploy, rollback), and, optional per specification, a production the
customer runs from a source handover, as regulated customers do, with
everything they receive and what stays their responsibility. The existing
deployment stage was extended rather than doubled.

Design, spec first:

- `environments.<name>.runBy`: `vendor` (the team that builds the system;
  the one meaning every environment had, so left out means vendor) or
  `customer`. ISO/IEC/IEEE 12207 calls them supplier and acquirer; the
  plain words are used, with the reason in ADR-129.
- `handover`, one object of the deployment stage: `description`, `to` (a
  stakeholder), `source` (how the source reaches the customer) and
  `responsibilities` (`customer` and `vendor` lists). Nothing another
  section already says is repeated in it.
- `backup` and `restore`, two procedures of the operation stage, with the
  steps of release and rollback.
- An implementation file's deployment gains `build` (`description`, `task`,
  `baseImages` by name, digest and purpose, `reproducible`, `sbom`),
  `method` (`tool`, `files`, `description`) and `infrastructure` (`cpu`,
  `memory`, `storage`, `network`, `ports`, `services`).
- Rules `handover` and `build_task`, in both builds: an environment the
  customer runs without a handover, release or rollback is an error at its
  `runBy`; a handover with no such environment is an error; a handover
  whose `to` names nobody is `stakeholder`; no check or monitor in that
  environment, and no backup and restore, are warnings; a must question
  that blocks the stage or the section holds the problem about it. An
  implementation deployment of such an environment without build, method
  or infrastructure is an error at the deployment; a build naming a task
  the file lacks is `build_task`.
- A new document target, `handover`, writes `handover.md` for the
  customer's engineers: what they receive, the responsibilities, each
  implementation's build with toolchain, base images, reproducibility and
  the licences of its dependencies, what the hosts must provide, every
  setting, the migrations in order, release with the vendor's install
  method, rollback, backup, restore, the monitors, the checks and
  acceptance tests in that environment, and the sign-off sheet. A
  specification with an output folder for it and no handover is passed over
  with a warning, as ADR-073 passes over one with no folder; the questions
  document lists the handover document only for a specification that has
  a handover. `--audience external` applies to it as to every document.
- The deployment guide shows who runs each environment once any
  environment says so, each installation's build, method and
  infrastructure, backup and restore after rollback, and the handover; the
  technical specification's chapter 7 the same. A specification without
  the new keys renders byte for byte as before: SpecArch's own deployment
  and commissioning guides and the `document-writes-deployment` case did
  not change.

Code: `internal/generate/handover.go` (the document and the shared
tables), `documents.go`, `implementation.go`, `questions.go`, `site.go`,
`cmd/specarch/document.go` (the pass-over and its closing message),
`internal/validate/lifecycle.go`, `implementation.go`, `diagnostic.go`,
`internal/spec/spec.go`, `internal/diff/diff.go` and
`internal/extract/merge.go` (the single sections); the Swift twins in
`Design.swift`, `Implementation.swift`, `Spec.swift`, `Diagnostic.swift`,
`Audience.swift` and `Questions.swift`; the design and implementation
schemas, the fragment schemas and the Swift embed regenerated.

Example: library-lending's production is run by the library's IT staff, a
new stakeholder `library-it`: `deployment/handover.yaml`,
`operation/backup.yaml` and `operation/restore.yaml`, the Go
implementation's `build` and `sbom` tasks and its production deployment's
build, method and infrastructure, and a `handover` target that writes
`docs/handover.md`. CI's library-lending loop, the contributing guide and
the `documents-current` task check it.

Cases, each with its design test and recorded output: `validate-handover-
valid`, `validate-handover-missing`, `validate-handover-incomplete` (two
errors and two warnings, the monitors warning held by a must question),
`validate-handover-no-customer`, `validate-handover-build-missing`,

Checks: `go test ./...` and `swift test`, validate on `spec` and `examples`

## extract go reads what an endpoint declares where it is registered, and validate warns of an unwritten body or success (BUG-025, ADR-130)

Reported while converting a Go service on dxlib: every endpoint is
registered with `NewEndPoint`, which is given its parameter list and its
response possibilities, and the handlers read their parameters through
dxlib. `extract go` said each handler "reads no parameter by name" and
wrote every operation with no body, no parameters and no responses but
the refusals the handler answers; the document the service dumped had no
schemas either, and nothing in validate or the questions said so.
BUG-025.

Fix, in `internal/extract/golang_declared.go`: the reader follows the
registration's parameter list, content type and response possibilities
through a literal, a pointer to one, a name assigned one once, or a
module function whose one statement returns one, and recognises a
parameter by its keys (`NameId`, `Type`) and a response by `StatusCode`,
whatever package declares their types. Each dxlib parameter type is
written in JSON Schema by dxlib's own table, as its emitter writes it,
and the result goes through extract openapi's field writer, so widths,
wire names (`info.wireNames` when the declared names are snake_case) and
gaps are what extract openapi gives for the emitted document. Where the
parameters go follows dxlib's `PreProcessRequest`: a POST or PUT with a
JSON, form or multipart content type takes them as body fields, an octet
stream or plain text takes that body, and their parameters, or those of
an endpoint with no content type, which dxlib reads from the X-Var
header, print a line; every other method takes them as query
parameters. A declared GET parameter named like a path segment is a
query parameter, because dxlib reads it from the query and not the path
(decided here; it is what dxlib's emitter writes too). What cannot be
followed is a must question naming the call and why; a parameter inside
a list that is not read is written by name with a must question; a body
that declares nothing is any object with a must question on its fields.
A declared success leaves only the missing descriptions to ask.

Validator, in both builds: `request_body_open` warns of a request body
that is an object naming no property and not saying
`additionalProperties`, and `success_response_missing` of responses that
are refusals alone (no 1xx, 2xx, 3xx or default). A must question that
blocks the operation, its body or its responses holds them.

Cases: `extract-go-dxlib-declared` (new, with its design test), and the
goldens of `extract-go-dxlib-endpoints` (its first endpoint now declares
the JSON content type as the literal 3) and `extract-go-dxlib-tables-seeds`
regenerated; `validate-interface-unwritten` (new). The notice board's two
readings still merge with 0 keys the trees disagree on, and the Go
reading's width question on its int64 fields merges as the one the
document asks.

Checks: `go test ./...`, `swift test`, validate on `spec` and `examples`
with the same output from both builds, every document target of CI
checked current (techspec, testplan and traceability regenerated), and
the notice board's extract script with CI's greps. No dependency change.
Docs: `spec/design/commands/extract.yaml`, `spec/design/enums/rule.yaml`,
`docs/conventions.md` (lists, limits and problem types),
`docs/reading-code.md` (Go on dxlib), `docs/extraction.md` step 13. The
handoff mailbox folder was empty. Nothing of the service the report came
from is in the change; the fixtures are a fictional lending desk.
Simulator: not needed, no app code.

## The middleware chain in the specification: declared once, listed per operation, shown in the documents (ADR-131)

The owner's addition to the item above: the middleware chain an endpoint
is registered with (authentication, sessions, permissions, rate limits,
audit, tenancy) is extracted per operation, in order, into the
specification, each middleware named with what it checks or does and what
it refuses with, cited to the code, shared chains declared once, shown per
operation in the generated documents, and never silent when it cannot be
read. The owner chose the split (2026-10-19): the design holds each
middleware's name, description and refusals and each operation's ordered
list; the function each one is goes in the implementation file under
`bindings.http.middlewares`.

Meta-model: `middlewares` is a section of the design stage, keyed by
kebab-case name, each a `description` and `refusals` (`status`,
`problem`, `condition`) with origin, cites, why and audience; an
operation's `middlewares` lists names in order, `[]` for none. The word
middleware is kept (guard already names a data change's precondition);
`x-middleware` stays a stack-specific extension key. The design and
implementation schemas, the design fragment schema and the Swift embed
are regenerated, and every list of sections in both builds lists it.

Validator, in both builds: `middleware` for a name an operation lists
that is not declared; a refusal's problem is checked as a response's is,
under `problem`; `middleware_missing` warns of an operation with no
`middlewares` once the specification declares any, held by a must
question on the operation or on its `middlewares` key (Covered learns
that key).

extract go (`internal/extract/golang_middlewares.go`): each middleware a
chain names is declared once by its function's name in kebab-case, its
doc comment its description (the parser now keeps comments), and each
refusal its body answers through its request, read as a handler's are,
with its problem declared under errors; it cites the function and the
first registration that runs it. A chain is followed like the parameter
list, and through a helper that returns its variadic parameter
(`mw(a, b)`). A chain not followed, a middleware outside the module or
made by a call, one with no doc comment, a refusal not a literal and two
functions of one name are questions. The gates on a setting now read the
chain where it is written. extract openapi reads `x-dxlib-middlewares` by
the last name of each function, none when the key is absent (dxlib omits
an empty chain), declares each with one must question on what it does,
and asks for a closure; the question on an operation with no privilege
now says it runs no middleware rather than that the document does not
name them.

Documents: the technical specification adds a column of each operation's
middlewares to its table of operations, once any operation names them, a
line in each operation's runtime view with the refusals, and a
Middlewares table under the cross-cutting concepts (what each does, its
refusals, the operations that run it). The HTML page links each name.

Cases: `extract-go-dxlib-middlewares`, `validate-middlewares` and

## Review round 1 of the declared interface and middleware work (BUG-025, ADR-130, ADR-131)

The review asked for eight fixes and one decision; all eight are made,
and the decision is recorded here for the owner.

- validate stopped with an index out of range on a response keyed by
  the empty string (`checkInterface` read `code[0]` before any length
  check). Both builds now skip a response key that is not three
  characters long, which the schema already reports, so a key that is
  no status counts neither as a success nor among the refusals the
  warning names. The Swift build read the empty key as no success and
  listed it; both now print the same. New cases
  `validate-interface-response-key-empty` and
  `validate-interface-response-key-empty-only`, each with its design
  test.
- extract go asked about a chain with an expression that names no
  function and then still wrote the names it could read; it now writes
  no list, as extract openapi does and ADR-131 says, so the two readings
  agree in the merge. `extract-go-dxlib-middlewares` gains a chain
  holding a function literal.
- extract openapi now asks a must question on the middlewares of an
  operation without `x-dxlib-endpoint-type` when the document's dxlib
  operations run any, so the tree carries no uncovered
  `middleware_missing` warning (renewLoan in
  `extract-openapi-dxlib-privileges`).
- extract go asked twice about a registration whose response
  possibilities it could not follow (once on what they are, once on
  the success); the second is gone.
- dxlib's PreProcessRequest reads parameters from the query for GET and
  DELETE only, from the body for POST and PUT, and refuses every other
  method with 422 before the handler. A PATCH registration was written
  with query parameters dxlib never reads; a method other than those
  four now writes no parameter and asks a must question on the
  operation. ADR-130 and the extract design say so;
  `extract-go-dxlib-declared` gains a PATCH registration.
- The schemas no longer refuse an operation whose chain runs one
  middleware twice (`uniqueItems` dropped from `middlewares`); a chain
  lists each middleware as often as it runs, and
  `extract-go-dxlib-middlewares` gains such a chain.
- `operationDetails` in the technical specification generator got back
  its own doc comment, and its Middlewares table lists an operation once
  under a middleware its chain runs twice (`document-techspec-middlewares`
  gains such a chain).

Left out, for the owner to accept: the request asked that the
registration patterns be configurable or recognised by shape and
documented. The elements of a parameter list and of the response
possibilities are recognised by their keys, but the registration call is
still dxlib's `NewEndPoint` by name and argument position, the types are
read by dxlib's constant names, and there is no implementation-file
binding for a project's own registration helper, as `permissionChecks`
gives one for permission checks (ADR-081). The reason: the reader for a
second framework, or a binding that names a call and the positions of
its arguments, is a design of its own (which arguments a call has, how
its element keys map), and no second framework is at hand to design it
against. A helper that returns a literal list is followed already.

Side finding, filed as BUG-026 and not fixed here: when two operations
each have a response keyed by the empty string, the Go build of validate
reports the schema error of one of them only (`propertyNameObject`
resolves both to one object); the Swift build reports both.

Checks: `go test ./...`, `swift test` (14 tests, the conformance suite
included), validate on `spec` and `examples` (0 errors),
`tools/fragment-schemas -check`, and techspec, testplan and traceability
regenerated. Simulator: not needed, no app code.

## validate reports the empty response key of every operation that has one (BUG-026)

Summary: when two operations each had a response keyed by the empty
string, the Go build of `validate` reported the schema error of one of
them only; it now reports one at each, at its own entry, as the Swift
build already did. BUG-026, moved to `BUG_HISTORY.md`.

Cause: the schema library stores a `propertyNames` error's location in
the slice it goes on appending to while it walks the rest of the input
(every other error path copies it), so when the errors are read, every
`propertyNames` error of one walk holds the path of the last sibling
walked at its depth. `propertyNameObject` in `internal/validate/schema.go`
chose, among the mappings at that depth under that key holding the
name, the one that agreed most with that path, so both errors resolved
to the last operation and the second was dropped as a repeat of the
first. The library's latest release (v6.0.3) still does it, and this
repository carries no patched copy of any library (the copied TypeScript
compiler source is unchanged), so the fix is in the checker, from what
the library does report right: the length of the error's location; the
location of the enclosing error, which the library copies and which is
the object itself or an ancestor of it (a `$ref` wraps the errors of the
object it refers to in a reference error at that object, so a rule on a
definition, or on a key of one, is pinned to the object or to its
parent); and the schema location, which ends in
`properties/<key>/propertyNames` when the rule sits on a document key,
and in the definition's name when it sits on a definition reached
through a `$ref` (`$defs/statusEvents/propertyNames`, which a task page's
`onSubmitted` refers to), a name that is no key in the document and is
not used. The candidates for an error are the mappings at its depth
under the enclosing error's location that hold the name, under the key
when the schema location names one: the object itself when the
enclosing error is at it, the one child under that key when the
enclosing error is at its parent, and otherwise the siblings under it
that hold the name, such as the media types of one content object. They
are listed in the order of the merged specification (the root file's own
keys, then the sections in life-cycle order, entities before schemas
whatever the file says, and within a section the order written), and
the k-th error of one name, depth, enclosing location and key takes the
k-th candidate; the count is keyed by exactly what the candidates were
filtered by, so two errors never take one mapping. Where the candidates
are siblings, that rests on one invariant: every `propertyNames` rule the
schema reaches at one depth under one object gives the same verdict on a
name, with the same pattern, so the candidates holding the name equal
the errors, and the errors, which arrive in the library's map order, can
take the candidates in any order. In the design schema every site is
pinned to one candidate: a rule on a definition (the 2xx statuses of
`onSubmitted`, the type names of a test's expected `state`) is reached
through a `$ref` and its enclosing error is the object; a rule on a key
of a definition (`properties` of an entity, `responses` of an
operation, `checks` of a page) has the definition's object as enclosing
error and the key under it; a rule on a root key (`entities`,
`requirements`) has the root. The one site that is not pinned is `modes`
under `theme`, inline two keys below the root: its enclosing error is
the root, and its candidates are the depth-2 mappings named `modes` that
hold the name, one in any specification written so far. One error more
than candidates takes the last, which the repeat check then drops, as
before.

The Swift build resolves locations itself and reported both already; it
is unchanged. The new case
`validate-interface-response-key-empty-two-operations` (two operations,
`closeLoan` and `openLoan`, each with a response keyed by the empty
string) prints the same text from both builds: two schema errors, one at
each operation's empty key, `success_response_missing` for `closeLoan`
alone, and the missing-test warnings of each.

Two siblings of the same flaw are covered by cases of their own.
`validate-schema-field-name-entity-and-schema`: an entity and a schema
that each have a field named `Bad-Name` are checked by two schema
definitions (entity and valueObject) under one key at one depth, each
pinned to its own object, and both builds print one error at each.
`validate-schema-field-name-entity-and-page-status`: an entity with a
field `Bad-Name` and a task page whose `onSubmitted` has a status
`Bad-Name`, the latter checked by a definition reached through a `$ref`
under another key, whose schema location names no document key; both
builds print one error at each, with the pattern of the rule that
checked it, and the page rule's error at that status (the operation does
not answer `Bad-Name`) is not printed, since a rule error at a path that
holds a schema error is an echo of it and is dropped.

## merge asks about a schema named like an entity instead of writing a tree validate refuses (BUG-027, ADR-132)

Reported from a project that merged a service's OpenAPI document with
its database on 0.6.4: the document declares a schema that no operation
creates, so `extract openapi` wrote it under schemas; the database has a
table of the same name, written under entities. Each tree passed
`validate`; `merge` wrote `/schemas/Note` beside `/entities/Note`, asked
nothing, and `validate` refused the merged tree with the one-namespace
error (`value_object`). A merged tree is not edited by hand, so the
extraction stopped. BUG-027. The usual case is a document left from a
service template whose schema happens to share a table's name, so
whether the shape is the record is exactly what the merge cannot tell.

Decision (ADR-132): `merge` keeps both entries, each as its trees give
it, and asks one must question per schema or view so named: is the name
one element or two, with an option that makes it the entity (or the
view) it is named like, where what refers to the one refers to the
other, and an option that gives it another name; the why names the
trees that give it each way, the question cites both entries and blocks
the schema or the view, where the validator reports. A line names the
question. The validator, in both builds, covers the `value_object` or
`view` one-namespace error when a must question blocks the entry it is
reported at (the covered list of ADR-017 grows by it); a should question
covers nothing, as before, and with no question the error is reported as
it was. Why not the other ways: leaving the schema out breaks what refers
to it (the list that carries it), leaving the entity out drops the
record, joining the schema into the entity is the choice ADR-060 records
the owner refusing, and a made-up name is a placeholder.

Changed: `namespaceQuestions` in `internal/extract/merge.go`, run after
the dispute questions; `Covered` in `internal/validate/questions.go` and
`coveredByQuestions` in `swift/Sources/SpecArchKit/Questions.swift`;
the merge bullet in `spec/design/commands/merge.yaml`; ADR-017's covered
list; ADR-132; one acceptance line on SA-45; `docs/from-sources.md`
3.2, `docs/conventions.md` and `docs/refinement.md`. New cases:
`merge-schema-named-as-entity` (the document and database trees of the
report, generalised) and `validate-question-covers-namespace` (a schema
and a view each named like an entity under a must question, covered; a
schema named like a view under a should question, reported), the latter
run by both builds.

Handoff: the request came through the scope's handoff mailbox, generic
already; nothing of it was left out, and no client or product name was
in it.

Checks: `go test ./...`, `swift build` and `swift test`, validate on
`spec` and `examples` (0 errors; the SA-57 warning is older), and
techspec, requirements, testplan, traceability and problems regenerated.
Simulator: not needed, no app code.
