# 2026-10-22

## A float tagged by hand with underscores, in the Swift build

Review of the BUG-054 fix (ade76e44): the Swift build dropped every
underscore of a scalar tagged `!!float` by hand, so `!!float ._5`,
`!!float .5_` and `!!float _1.5` printed 0.5, 0.5 and 1.5, where the Go
build, through yaml.v3, prints them as text. Before that fix the Swift
build printed them as text too, so the fix had brought the difference
in. The tagged path now drops underscores under the same rule as a
plain float (a digit or sign start drops them all, a dot start only
between two digits, any other start keeps them); checked on 22 tagged
forms, both builds print the same bytes. ADR-175 says so, and the case
`model-float-underscores` adds the tagged forms. The handoff mailbox
was empty. Nothing was left out on purpose.

## Every YAML scalar read alike in both builds (BUG-055)

The third fix in a row for one family (BUG-048 hexadecimal, BUG-054
floats with underscores) showed another: `!!int _1` printed 1 from the
Swift build and "_1" from the Go build. Rather than fix the next form,
the class was ended. A table of every scalar form yaml.v3 tells apart
(integers in each base with leading zeros, signs and underscores in
every place; floats with exponents, the infinities and NaN; booleans
and nulls in every spelling; timestamps in each layout and out of
range; texts that look like numbers; quoted and block scalars; and
each under `!!int`, `!!float`, `!!str`, `!!bool`, `!!null`,
`!!timestamp`, `!` and other tags) was run through both builds'
`model`. The plain forms already agreed; 35 values and 7 problems did
not, and a worked example of a double field read its number its own
way too. All came from one cause, the Swift build resolving scalars by
patterns of its own, so they are one entry, BUG-055.

The Swift build now reads a scalar in one place, a port of yaml.v3's
resolve, its parser's tag rule and its timestamp layouts, and the Yams
parser is given a resolver that keeps an untagged scalar untagged, so
Yams' YAML 1.1 resolver, which runs when a mapping's keys are compared,
never replaces the tag written. ADR-176 records why both builds follow
yaml.v3 rather than the core schema. The table is the case
`model-scalar-forms`, and `validate-example-double-forms` covers the
double examples; the Swift conformance suite runs both, so a form either
build reads differently fails CI. Against the build before the fix the
two cases differ in 35 values, 7 problems and 5 validate lines; after
it, in none.

Side finding, not fixed here: a YAML syntax error inside a flow
sequence (such as `[!!null]`, where `]` is read as part of the tag)
gets a different message from each build. The handoff mailbox was
empty. Nothing was left out on purpose.

## A YAML syntax error in the same words from both builds (BUG-056)

A yaml_syntax error printed the parser's own message, and the two
builds use different parsers, yaml.v3 and libyaml through Yams. They
share one set of messages but not always the same one for a text:
`[!!null]` was an unclosed `[` to the Go build and a missing space to
the Swift build. Of 45 broken files tried, that and a few Yams
messages printed with the source line inside the problem line were
the wording differences. Three more were one build reading what the
other refused: a file with bytes that are not UTF-8 (the Swift build
reported nothing), `[!!str, a]`, and a `?` inside a value of a
`{ }` or `[ ]`. The owner asked for all of them in this one entry.

Each parser message now has a class in one table the two builds share
(a Go test holds the Swift copy equal), and the problem line says the
class's sentence, what is wrong and what to do. The parser's own
message is kept and printed on standard error, `yaml parser
(<parser>): <message>`, never in the problem line, the problems file
or the model, since those must be the same bytes in both builds; that
was the decision this item turned on (ADR-177). A tag running into a
`,` `[` `]` `{` or `}`, and a `?` that is not a key's, in a flow
collection are refused by both builds, read from the collection's
text, because YAML 1.2 and yaml.v3 read them differently and a choice
between them would be a guess. The Swift build reads a byte that is
not UTF-8 as U+FFFE, which libyaml refuses as yaml.v3 refuses the
byte. Yams keeps a collection's end event style instead of its start's,
so whether a collection is in flow style is read from the text in both
builds. An unclosed `[` or `{` on line 1 was reported at line 2; it is
now line 1.

The cases `validate-yaml-syntax-classes`, `validate-yaml-not-utf8`,
`validate-yaml-tag-in-flow` and `validate-yaml-question-in-flow` hold
both builds to the same bytes; `validate-yaml-syntax-entries` now
reads "a value is missing" where yaml.v3's "did not find expected node
content" stood. A multi-line flow collection is classified from the
`[` or `{` that holds the reported line, found by counting brackets
back; a quoted value that holds a bracket on an earlier line can still
mislead that count. The handoff mailbox was empty. Nothing was left
out on purpose.

## Two more texts the builds printed differently (BUG-056, review round 1)

The review of BUG-056 found two inputs that still gave different
standard output from the two builds. A block mapping whose first key
is written as `[ ]` or `{ }` was taken for a flow collection, since
both parsers give a block mapping the position of its first key; the
flow check read only the key and skipped every value after it, so
`[k]: v` followed by `enum: [!!str, a]` was refused by the Swift build
alone. The check now walks on into the mapping's values. And a
multi-line flow collection was found by counting brackets back from
the line a parser names, which a quoted `]` or `[` on an earlier line
misled; the two parsers name different lines of such a collection, so
the problem landed on different lines. The collection is now found by
reading the file from its top, skipping quoted values, comments and
block scalars, in both builds; the known limit written above is gone.

docs/diagnostics.md now says the text after `yaml parser (<parser>)`
is the parser's message unchanged, its own line numbers included,
which may count from 0. The cases `validate-yaml-flow-key-first` and
`validate-yaml-quoted-bracket-in-flow` failed before (the first in the
Go build, the second in the Swift build) and pass in both now.
Nothing was left out on purpose.

## A crash on a line that starts inside an open flow (BUG-056, review round 2)

The review of round 1 found that the new forward scan, which finds the
`[` or `{` a broken line belongs to, read the character before the
first one of a line when that line starts a plain value inside an open
flow collection after an anchor or a tag. The Go build stopped with an
index out of range and the Swift build trapped, so one broken file
ended the whole run. The scan now treats the start of a line as a
space, in both builds. TestEnclosing holds two such texts, and the case
`validate-yaml-anchor-at-line-start-in-flow` crashed the Go build
before and passes in both now. Nothing was left out on purpose.

## Release 0.7.4

The owner asked for a release of everything on main since 0.7.3. The
release commit is made on main at 33e0bca2: the 0.7.4 release record is
released (dated 2026-10-22, no commit yet), `info.version` and both
implementation files' `implements.version` are 0.7.4, and both builds,
the version case and the five model cases print 0.7.4, with meta-model
0.3 for specifications and 0.1 for implementation files. The install
lines in the README and `docs/from-sources.md` point at v0.7.4. No schema
changed since v0.7.3, but every editor hint and the schema line extract
writes (`internal/extract/tree.go`) still move from v0.7.3 to v0.7.4, as
the owner asked, so that a hint names the release it comes with. The
roadmap gains a 0.7.4 row in its release table and calls 0.7.4 the
latest, as the README's status does. The documents are regenerated.

`RUN_INSTRUCTION.md` stays at v0.7.3 here, beside the `h1:` checksum of
the v0.7.3 module; its install lines and checksum move to v0.7.4 with the
commit that opens 0.7.5, from the installed module.

What 0.7.4 carries beyond 0.7.3, for its users:

- `extract swift`, `extract javascript` and `extract dart` ask for the
  transaction token and `via` of an operation whose handler reads the
  `Txn-Token` header, in the words `extract go` asks it (ADR-173). Every
  item of caller context on the roadmap is built.
- ADR-167 (`specarch-gen-scripts` on MariaDB) and ADR-168 (a guard's
  `writes`), shipped in 0.7.3, are accepted.
- Both builds read every YAML scalar as yaml.v3 does: integers in every
  base with a bare leading 0 as octal (ADR-174), floats with underscores
  (ADR-175), and every tagged and untagged form, held to the same bytes by
  the table of scalar forms in `model-scalar-forms` (ADR-176; BUG-048,
  BUG-054, BUG-055).
- A YAML syntax error is worded the same by both builds, by class, with
  the parser's own message on standard error; a tag running into a flow
  indicator, a `?` that is not a key's in a flow collection and bytes that
  are not UTF-8 are refused by both builds (ADR-177; BUG-056).
- A question that blocks one method of a path holds up only that
  operation's drafts (BUG-030); `extract go`'s handlers line counts the
  questions the handler walk asks (BUG-031); both builds keep a run of
  capitals as one word in a suggested test name (BUG-033); an earlier
  `use()` on the parent router reaches a mounted router's routes in
  `extract javascript` (BUG-045); a problem in an implementation file is
  marked at the entry a document shows (BUG-049).

Open bugs, not in this release: none; `BUG_OUTSTANDING.md` lists none.

Checks on the release tree: `scripts/landing-check.sh` passed in full
(the Go tests, validate of the specification and the examples, every
