## extract go follows a helper that returns the group it makes

Reported from a project that extracts a Go codebase with 0.6.4: a gin
service registers routes on a plain group, through a local helper that
takes a prefix and a callback (read since 0.6.4, BUG-018), and through a
local helper that takes a prefix and returns the group, `g :=
returned("/d")` with routes on `g`. Expected 5 operations, got 3: the
two on the returned group were missing, with no question or warning.
BUG-022.

Cause, in `internal/extract/golang_routers.go`: a call of a function
value held in a local name, or bound to a parameter, was followed only
as a statement, never as a value. The router a call gives was a
library's maker, a group or subrouter, or what a function of the module
returns, so the name assigned from such a call held no router, and the
routes on it reached no registration, counted or asked. Latent beside
it: a literal's `return` set the return of the function it is written
in, so a function that declared such a helper and then returned its own
group could hand a caller the helper's group instead.

Fix: the walk of a literal gives the router the literal returns and
keeps the return of the function it is written in apart from it; a call
of a held function gives that router, so a call of one is the call's
value, and the statement walk leaves a call already followed as a value
alone. The walk paragraph of `spec/design/commands/extract.yaml` says
that the router such a call returns is the call's value, a literal's
return never standing for the return of the function it is written in;
`docs/extraction.md` step 15 says a helper returning the group it makes
is followed through its value; `docs/techspec.md` is regenerated, the
other document targets unchanged.

Tests: `TestGoRouterReturnedByHelper` in
`internal/extract/golang_test.go`, seven cases: a closure returning the
group assigned in a block, one called with two prefixes and in a chain,
one registering a route before it returns, one passed to a function of
the module that calls it for the group, a function of the module
returning the group called by name and passed as a value, and a literal
whose return must not become the return of the function around it
(which wrote a route under the wrong group before). All seven failed
before the fix and pass after it, together with
`TestGoLiteralSeesWhereItIsWritten`, which now shares the harness
`goRoutesCases`. The whole module passes `go test ./...`, the validator
passes on `spec/` and `examples/`, and every document target checks
clean.

Left out on purpose: the reporter's service names, route names and
route counts. Not touched: the Swift build (extract is Go only), and
ADR-081 and `docs/reading-code.md`, which do not state the walk at this
level. The handoff mailbox folder was empty. The fix is commit dda47fdd;
the commit after it records that hash here and in `BUG_HISTORY.md`.

## merge adds up a role's grants from trees that declare different permissions (ADR-127)

Handoff 15 processed. A specification merged from the permission tables
of several services, one tree each, lost every grant of a role that was
in more than one table: merge compared the two lists as any key, left
the role's `permissions` out with a must question asking which list is
right, and the question blocked every permission the lists name that no
other role grants. The sender expected the union of the lists with both
citations and no question.

Rule chosen: a tree's list of a role's grants says nothing of a
permission the tree does not declare in its `permissions` section, so
the lists of several trees add up, the first tree's then what each
later tree adds, with every tree's citation and one "joined:" line
naming the trees. A permission one tree grants that another tree, which
has the role, declares and does not grant is still a disagreement: the
list is left out, and the must question names each such permission
with the trees that grant and withhold it, beside the lists each tree
gives, and blocks the ungranted permissions as before. A role a printed
and a parsed tree both give is still compared grant by grant with the
printed grants kept. Not taken: the handoff's rule of joining the lists
whenever the trees come from different sources, since a documents tree
that lists a role's permissions and leaves one out would then be joined
silently with the code that grants it, against "never choose between a
document and the code"; and two trees of one source key are already
joined or refused as one source, so the only same-source case left is
printed against parsed. The handoff's own term for the merged files was
left out of the repository.

Code: `roleGrants` in `internal/extract/merge.go`, run after the last
tree is in and before the disputed keys are left out, so the order the
trees are given no longer decides whether a list is a dispute (the old
check in `mergeNode` saw only the trees read so far); `mergeNode` skips
a role's `permissions`; `disputeQuestions` words the why of such a
dispute with the grant withheld. Design: the rule in
`spec/design/commands/merge.yaml` and its standard output line, the
new ADR-127 with its reason, a bullet in SA-45's acceptance list, and
the paragraph in `docs/from-sources.md`, section 3.2. `docs/extraction.md`
is unchanged: the lending desk's roles are printed and parsed, which
this does not touch.

Cases: new `merge-role-grants-add-up` (two services' tables, each
declaring its own permissions and granting one role of the same name
its own: the role gets both grants with both citations, the joined line,
and no question on the grants) and `merge-role-grants-withheld` (both
tables declare one permission, one grants it to the role and the other
has the role and withholds it: the list is left out and the must
question says which tree grants and which withholds). `merge-role-names-
disagree` already held this very dispute beside the wire-name question
it is about; its role now gets every grant of both tables and only the
wire-name question is asked.

Checks: `go test ./...` with the conformance suite, `swift test`,
validate on `spec` and `examples` (0 errors; SA-57 unverified as
before), the Go and Swift validators print the same output on `spec`,
`examples` and both new merged trees, and `examples/lending-desk/extract.sh`
run with the binary before and after writes the same bytes. Every
document target of CI regenerated. No dependency change. The handoff
mailbox folder was empty. Simulator: not needed, no app code.

## extract database reads a partition as its table (BUG-023, ADR-128)

From a handoff: a system read through `extract database` has partitioned
tables, and the reader wrote an entity for each partition beside the
table's, each with the primary key and the indexes the partition takes
from its table, so every generated default and every index was a could
question once per partition. `check` would have reported each partition
as a table the specification does not hold. The handoff named the
product, its table and key names and the PostgreSQL version it runs;
none of that is in this repository, and the case here is written from
scratch around a table of events. The handoff mailbox folder was empty;
the handoff itself lives outside every repository and stays there.

What changed, in one commit:

- `tools/catalogue/catalogue.sql` prints for each table `partitionBy`
  (pg_get_partkeydef), `partitionOf` (the schema and name of the table a
  partition is a partition of) and `partitionBound` (pg_get_expr of
  relpartbound), and for each constraint and index `inherited`. A
  constraint is inherited when `coninhcount > 0` or `conparentid <> 0`:
  a partition's key and foreign key carry both, an inherited CHECK only
  the count, since PostgreSQL creates it with no parent constraint. An
  index is inherited when pg_inherits has a row for it.
- `internal/extract/database.go` reads a partition as the table
  `partitionOf` leads to, through a partition of a partition as well. No
  entity is made for it; the table's citation names the partitions; one
  could question at the entity lists them with their bounds; a
  partition's own constraint, index or column setting is a could question
  citing the partition's entry; a foreign key to a partition is a
  relation to its table with a question; a partition whose table the
  dump does not list is read as a table of its own. The counted line
  says how many tables are partitions, and the wrote line says one entity
  per table that is not a partition, only when the dump has one. An
  index definition with `ON ONLY`, as pg_get_indexdef prints a
  partitioned table's index, is a plain index as any other.
- `internal/extract/check.go` compares no partition, so none is a table
  the specification does not hold; the `ON ONLY` index is compared as
  the plain index the mapping lists.
- Spec first: ADR-128 (satisfies SA-44 and SA-72), the database bullet of
  `spec/design/commands/extract.yaml`, the catalogue bullet of
  `spec/design/commands/check.yaml`, one acceptance bullet each on SA-44
  and SA-72, and the cases `extract-database-partitioned-table` and
  `check-skips-a-partition`: a table partitioned by range with a check and
  a plain index, a partition partitioned again by list, a partition with
  its own column default, and a default partition with a check and an
  index of its own. The documents are regenerated; `docs/extraction.md`
  and `docs/from-sources.md` each gain a sentence.
- BUG-023 is recorded in `BUG_HISTORY.md`. The fixing commit's hash cannot
  be in the commit itself, and a branch is rebased when it lands, so the
  entry names the commit by its message, `Fixes BUG-023`;
  `BUG_OUTSTANDING.md` moves the next free number to BUG-024.

The reader's design choices are in ADR-128: partitioning is physical
design, as an index is, so it stays a could question until the mapping
has a key for it; a partition's own constraint holds for its rows alone,
which the meta-model cannot say, so it is left out with a question rather
than read as the table's.

Checks: `go test ./...` passes with the two new cases; `validate` passes
on `spec/` and the examples; the regenerated documents differ only where
this item changes them. The validator's two builds are untouched, so the
Swift build needs no change.

The catalogue dump of the two cases is the output of
`tools/catalogue/dump-catalogue.sh` on the case's migration, run in a
repository built as the conformance runner builds it, so the dump names
that repository's first commit, 0ef0e4e3bac900e108dee9363ce651f02c3accf9.
The Podman machine's disk was full to the byte for most of the item, and
every container job on this Mac failed with "no space left on device".
The owner's first decision, a prune of the unused images, could not free
it, since podman could not rewrite its image index on a full disk; the
owner then enlarged the machine's disk to 53 GB. Until then the work was
developed against a dump written by hand from PostgreSQL's documented
catalogue output, and the real dump matched it byte for byte, so nothing
in the expected files changed. What the real dump confirms: the range
bound as `FOR VALUES FROM ('2026-01-01 00:00:00+00') TO ('2027-01-01
00:00:00+00')`, `ON ONLY` in the definitions of the partitioned tables'
indexes, the names PostgreSQL gives a partition's inherited index and key
(`events_default_at_idx`, `events_default_pkey`), a partition's copy of
the table's check marked inherited, and `'sale'::text` and
`CHECK (((kind)::text <> ''::text))` as the catalogue spells a default
and a check.

## Deployment: who runs an environment, and a handover for a customer who runs one (ADR-129, SA-73)

The owner asked that a specification cover deployment in two parts: the
environments the vendor runs (what is deployed where, how it is built from
source with a pinned toolchain and base images, how it is installed,
configuration and secrets by name and source only, the checks after each
deploy, rollback), and, optional per specification, a production the
customer runs from a source handover, as regulated customers do, with
everything they receive and what stays their responsibility. The existing
deployment stage was extended rather than doubled.

Design, spec first:

- `environments.<name>.runBy`: `vendor` (the team that builds the system;
  the one meaning every environment had, so left out means vendor) or
  `customer`. ISO/IEC/IEEE 12207 calls them supplier and acquirer; the
  plain words are used, with the reason in ADR-129.
- `handover`, one object of the deployment stage: `description`, `to` (a
  stakeholder), `source` (how the source reaches the customer) and
  `responsibilities` (`customer` and `vendor` lists). Nothing another
  section already says is repeated in it.
- `backup` and `restore`, two procedures of the operation stage, with the
  steps of release and rollback.
- An implementation file's deployment gains `build` (`description`, `task`,
  `baseImages` by name, digest and purpose, `reproducible`, `sbom`),
  `method` (`tool`, `files`, `description`) and `infrastructure` (`cpu`,
  `memory`, `storage`, `network`, `ports`, `services`).
- Rules `handover` and `build_task`, in both builds: an environment the
  customer runs without a handover, release or rollback is an error at its
  `runBy`; a handover with no such environment is an error; a handover
  whose `to` names nobody is `stakeholder`; no check or monitor in that
  environment, and no backup and restore, are warnings; a must question
  that blocks the stage or the section holds the problem about it. An
  implementation deployment of such an environment without build, method
  or infrastructure is an error at the deployment; a build naming a task
  the file lacks is `build_task`.
- A new document target, `handover`, writes `handover.md` for the
  customer's engineers: what they receive, the responsibilities, each
  implementation's build with toolchain, base images, reproducibility and
  the licences of its dependencies, what the hosts must provide, every
  setting, the migrations in order, release with the vendor's install
  method, rollback, backup, restore, the monitors, the checks and
  acceptance tests in that environment, and the sign-off sheet. A
  specification with an output folder for it and no handover is passed over
  with a warning, as ADR-073 passes over one with no folder; the questions
  document lists the handover document only for a specification that has
  a handover. `--audience external` applies to it as to every document.
- The deployment guide shows who runs each environment once any
  environment says so, each installation's build, method and
  infrastructure, backup and restore after rollback, and the handover; the
  technical specification's chapter 7 the same. A specification without
  the new keys renders byte for byte as before: SpecArch's own deployment
  and commissioning guides and the `document-writes-deployment` case did
  not change.

Code: `internal/generate/handover.go` (the document and the shared
tables), `documents.go`, `implementation.go`, `questions.go`, `site.go`,
`cmd/specarch/document.go` (the pass-over and its closing message),
`internal/validate/lifecycle.go`, `implementation.go`, `diagnostic.go`,
`internal/spec/spec.go`, `internal/diff/diff.go` and
`internal/extract/merge.go` (the single sections); the Swift twins in
`Design.swift`, `Implementation.swift`, `Spec.swift`, `Diagnostic.swift`,
`Audience.swift` and `Questions.swift`; the design and implementation
schemas, the fragment schemas and the Swift embed regenerated.

Example: library-lending's production is run by the library's IT staff, a
new stakeholder `library-it`: `deployment/handover.yaml`,
`operation/backup.yaml` and `operation/restore.yaml`, the Go
implementation's `build` and `sbom` tasks and its production deployment's
build, method and infrastructure, and a `handover` target that writes
`docs/handover.md`. CI's library-lending loop, the contributing guide and
the `documents-current` task check it.

Cases, each with its design test and recorded output: `validate-handover-
valid`, `validate-handover-missing`, `validate-handover-incomplete` (two
errors and two warnings, the monitors warning held by a must question),
`validate-handover-no-customer`, `validate-handover-build-missing`,
`validate-build-task-unknown`, `document-writes-handover` (with an internal
setting marked) and `document-handover-none`. The Go and Swift validators
print the same output on every validate case and on `spec` and `examples`.

Checks: `go test ./...` and `swift test`, validate on `spec` and `examples`
(0 errors; the two warnings, LEND-4 and SA-57 unverified, were there
before), `tools/fragment-schemas -check`, and
every document target of CI checked current. `docs/problems.txt` and
`problems.sarif` had been one line behind the last commit (the SA-57
warning's line moved); they are regenerated here. No dependency change.
Docs: `docs/stages.md`, `docs/conventions.md` (tree, boundary table, keyword
table), `docs/generators.md`, `README.md`. The handoff mailbox folder was
empty. Nothing of a client or employer is in the change; the example's
customer is the fictional library. Simulator: not needed, no app code.
