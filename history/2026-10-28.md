# 2026-10-28

## Decision tables on an algorithm (item 1342)

Item S4 of the spec-authoring plan the owner chose on 2026-10-27 (item
1325). An algorithm may now give `table` in place of `formula`, after
DMN 1.5's decision table (ADR-199, SA-104): the inputs are its columns,
each of `rules` has `when`, a condition per input it tests, and `then`,
the output, and `hitPolicy` is `unique` or `first`, always written. A
condition is a value, a comparison (`"< 6"`), comparisons joined by
`and` (`">= 3 and < 6"`), `null`, or a list of these; an input a rule
does not name matches anything, so a rule with no `when` is "everything
else".

Both validators read each rule as a box of value sets, one per input,
and check the table by its hit policy: under `unique` two rules that
both match some inputs are `table_overlap` at the later one, naming the
inputs; under `first` a rule the earlier ones always match first is a
`table_overlap` warning; under both, inputs no rule matches are
`table_gap`, written as whens that can be pasted in as rules. The gap
check keeps to an input's `minimum` and `maximum`, an int32's range and
a uint's zero. A condition or an output that cannot be read is
`decision_table` at it; a condition that holds for no value its input
may take (`"<= 0"` for an input above 0) is a `decision_table` warning,
found in review of the change before it was committed: it was first
reported as a rule the earlier ones always match. An input whose minimum and
maximum leave it no value is `decision_table` at the input, from the
same review. Each rule is a worked example (the first inputs
it reaches, its `then` expected), so `examples` is optional with a
table; the examples given are checked against the table as a formula's
are. `specarch try` evaluates a table on each rule's example and each
worked example and prints a step per rule tested. The technical
specification draws the table, a column per input, "any" where a rule
does not test one.

The library lending example gains `mayLend`, LIB-3's loan limit as a
table: no loan while a fee is unpaid, then below three open loans for a
standard member and six for an extended one. Design 9.5's mockup names
the algorithm `loanLimit` with an output `mayLend`; the example names
the algorithm `mayLend`, since it gives a yes or no, not a limit.

Cases, the same output in both builds: `validate-decision-table`,
`validate-decision-table-refused`, `try-decision-table` and
`try-decision-table-unreached`.

Left out on purpose: DMN's other hit policies (any, priority, output
order, rule order, collect), FEEL's own syntax for ranges and lists,
and tables over timestamps, times of day and durations; ADR-199 says
why for each. The test generators still write a test per worked example
only; a test per rule is a later addition.

## Decision tables: review round 1 (item 1342)

The review of the decision tables found three faults and a note; this
round settles them, in both builds.

- An input of a type a table does not test (a timestamp, a time of
  day, a duration) that no rule names made the table unread with no
  problem reported, so overlap, gaps and the worked examples went
  unchecked and `validate` passed. Such an input is now left out of the
  table's columns: every rule matches any value of it, the table is
  checked over the other inputs, and a worked example or `specarch try`
  may give it a value. A rule that names it is still `decision_table`.
  The alternative, an error at the input, was not taken: ADR-199
  already says an input a rule does not name matches any value.
- The `table_gap` advice "or a last rule with no when" is given only
  under hit policy `first`. Under `unique` such a rule overlaps every
  other one, so the advice is now "add a rule for each" alone.
- A string or enum condition that begins with `<`, `>` or `!=` is read
  as a comparison, so a value such as `<none>` cannot be matched by a
  table. ADR-199 and `docs/conventions.md` now say so, and the error
  names why the cell was read as a comparison and that a formula tests
  such a value. No second, quoted way to write it was added.

Cases: `validate-decision-table` gains an instant input no rule names
and a worked example that gives it; `validate-decision-table-refused`
gains `dueSoon`, a unique table with such an input whose overlap, gap
and wrong example are all reported.

## Decision tables: review round 2 (item 1342)

The second review found one fault in both builds and two lines left
unwrapped.

- An enum input whose `$ref` does not resolve has no values, and the
  checker read that as an input whose minimum and maximum leave no
  value. That pointed at bounds the input does not have, beside the
  real `ref_type` error, and left the table unchecked. Now the
  empty-bounds error is given only for an ordered type. Such an enum
  input is treated like an untested type: when no rule names it, the
  table is checked over the other inputs; when a rule names it, the
  table is not checked, and `ref_type` alone is reported.
- ADR-199's gap paragraph and the decision-table paragraph of
  `docs/conventions.md` are rewrapped to the files' width, and both
  now say how an unresolved enum input is handled.

Cases: `validate-decision-table-refused` gains `lostShelf` (no rule
names the input; its gap is still reported) and `namedShelf` (a rule
names it; only `ref_type`).
