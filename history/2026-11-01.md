## Generated tests with real bodies (item 1684)

In the library lending example 185 of the 197 tests that apply were
generated as a test whose body is written by hand: the `tests` target
writes a body only for a test that gives `input` or `expect`, and derive
drafted little beyond a status. The idea taken from Spec Kit, whose tasks
step turns each item into work that runs: draft the call the design
already fixes. Now 66 of 198 are generated with their bodies.

- `specarch derive` drafts, for an operation's case, a caller, a valid
  value of every required parameter and body field, the records those
  values name and the status, when the operation declares the status
  the case answers (success, 403, 404, 401, and 400 or 422). A value
  `test_data` would refuse (a malformed date, a value not of an enum) is
  never written; those cases keep the status alone, as before (ADR-213,
  SA-111).
- `specarch derive --fill` adds that data to each existing test that has
  none of `fixture`, `input` and `expect`; a test whose cases draft
  different data, or that keeps its data in `input/` or `expected/`, is
  named on standard error and left as it is. A role the test's own words
  name is taken as the caller.
- The test plan says, after its summary, how many tests the `tests`
  target writes with their bodies, and counts them by kind of subject,
  when an implementation file declares that target; SpecArch's own test
  plan does not, since its tests run as conformance cases.
- The example's operations declare 400, 401 and 403 (problems
  `request-invalid`, `not-signed-in`, `not-allowed`), and those under a
  loan or a fee waiver 404 (`loan-not-found`, `fee-waiver-not-found`);
  each page that calls them has a message for each, in English and in
  the two Indonesian string tables; the tests of createLoan, lendCopies
  and the member-loans page cover the new responses, and
  `member-loans-bad-member-id` is new. `derive --fill` then filled 54
  tests, read one by one against their given, when and then:
  `get-profile-succeeds` was changed by hand to sign in as the member it
  describes; `lend-copies-denied` (which had a caller only) was given its
  403 by hand; the three golden tests of the fee waiver steps and
  `waive-fee-denied` got their FeeWaiverRequest record by hand, since
  `waiverId` does not name the entity by derive's rule
  (`feeWaiverRequestId` would); and the fill of `list-loans-denied`, "a
  caller holding no role", was taken back, since the data cannot say a
  signed-in caller with no role.
- New cases `derive-drafts-calls`, `derive-fill` and
  `document-testplan-bodies`; twelve derive cases,
  the test plan cases and the usage text re-recorded.
- The owner's decision (2026-11-01): operations only in this item; the
  `tests` target's calls for constraints, transitions and pages are a
  follow-up.
- Handoffs: the mailbox was empty.
- Left open: 16 operation tests cover several cases whose data differ
  (four missing fields in one test, for one) and stay with a body
  written by hand until split; the cases whose set-up data cannot say
  (an expired session, a failing dependency, two writers) keep a status
  alone, so a generated `denied with expired session` test calls with no
  session and checks 401; drafted dates are one fixed day, so a design
  that needs one date after another gets two equal dates to correct.

### Item 1684, review round 1: status kept, mixed tests named

- derive keeps the status the operation declares, and a caller who may,
  for a not-found, missing or limit case whose call cannot be made: a
  required field no value can be made for (a list, an object, a
  pattern), no role holding the permission, or a value test_data would
  refuse (a malformed date, a value not of an enum). Before, only a
  denied case kept them, and the others drafted nothing, though the
  design files said every such case keeps them. Cases about a pattern or

  `derive-drafts-calls`, `derive-fill` and `derive-caller-estate`

- `derive --fill` names a test of several cases, rather than filling it

## An MCP server and an agent skill (item 1685)

SpecArch was easy for an agent to use and hard for it to find: an agent
had to be told the program existed before `capabilities --json` or
`guide --agent` were any use. The idea taken from Spec Kit (MIT), which
reaches many coding agents by installing its commands and skills into
each agent's folder: ship into the places agents look. SpecArch ships two,
both made from the command definitions, so neither can drift from the
program (ADR-214, SA-112).

- `specarch mcp`: a server of the Model Context Protocol, revision
  2025-11-25 (and 2025-06-18, 2025-03-26, 2024-11-05 when asked), on the
  stdio transport, written with the standard library alone, no new
  dependency. It answers initialize, ping, tools/list and tools/call;
  tools/list is `capabilities --json`'s tools cut to MCP's keys, mcp's own
  left out; tools/call runs the command in the program with `--json` and
  answers with the object it prints, exit 2 marked `isError`, exit 1 a
  result. The command line follows the command's synopsis, since generate,
  document and extract read their target before any option. An input the
  tool does not take, a required one missing, a value of the wrong JSON
  type or an argument that starts with `-` is answered as a tool error
  with the reason, before anything runs, as the protocol's 2025-11-25
  revision asks so the model can correct it; patterns and enums are left
  to the command's own usage error. `server/discover`, the stateless
  2026-07-28 revision's first call, is answered -32601, on which that
  revision's clients fall back to initialize. `specarch mcp --json` is a
  usage error: its standard output is JSON-RPC.
- `specarch skill --out <folder> [--check | --dry-run]`: writes
  `<folder>/specarch` in the Agent Skills format, SKILL.md (front matter
  name and description, then the agent guide and the list of references)
  and `references/<command>.md` per command. A stale reference is
  removed; a `specarch` folder this command did not write is refused, so
  `--out` at the wrong folder loses nothing. The repository holds the
  skill in `skills/specarch/`; `TestSkillFolder` fails when it differs
  and `scripts/regenerate.sh` writes it.
- SA-96 said no command reads standard input but a plug-in; mcp is now
  the second exception, named there. The conventions (`help
  conventions`, the agent guide, AGENTS.md) say mcp refuses `--json` and
  name the two ways in; `specarch help agents` shows a client's server
  entry and where to write the skill.
- The conformance runner gives a case's `standardInput` to the run, for
  mcp; CONTRIBUTING.md says so. Cases `mcp-serves-tools`,
  `mcp-usage-error`, `skill-lists-what-it-writes`, `skill-check-differs`,
  `skill-usage-error`, `skill-refuses-another-folder`; unit tests check
  that tools/list equals the listing, that every tool's command line is
  read as made, the input errors and the revisions answered.
- Fixed on the way: BUG-066, `idioms` and `idioms diff` refused `--`,
  which the conventions promise every command takes (cases
  `idioms-after-dash`, `idioms-diff-after-dash`); BUG-067, document's
  target was listed as a `$ref` into SpecArch's own specification, which
  no client could resolve: the program embeds `spec/design/enums` and
  writes the enum's values into the schema.
- Left for later: serving revision 2026-07-28's `server/discover`, once
  its schema is read; this work was done from the 2025-11-25 schema.
  No per-agent command files are written: one skill format and one server
  stand in for them.
- Handoffs: the mailbox was empty.

## Tabular data as a capture source: CSV, TSV and Excel registers (item 1688)

The owner asked for registers and spreadsheets as a capture source, the
data model of many real systems that SpecArch could not read: CSV, TSV
and Excel files read into entities with inferred, cited fields and
questions for every ambiguity, several files of one register merged, a
register template with its instructions read and enforced, and the
generators and checks that go with it. The origin is a compliance
records repository (registers, evidence, controlled documents), described
only so; the samples are a lending library's loan registers.

- `specarch extract tables` (ADR-215, SA-113), beside documents, on
  `internal/xlsx` from item 1683 and `encoding/csv`; no dependency added.
  Each file is a document source cited as a spreadsheet program shows it
  (`C17`, `Loans!C17`, a column as `C1:C13`); each register, a sheet or a
  CSV or TSV file, is an entity named by its sheet or file, `--entity`
  naming the one register every file belongs to, so period files give
  one entity citing each file.
- Types inferred from every value of every file: integer (int32, or
  carried as text beyond it), decimal with the widest value's precision
  and scale, date, date-time, boolean, email, UUID, an enum of at most
  ten distinct values fewer than half as many as the values, else text;
  a leading zero is text. The entity carries `origin: inferred`, a `why`
  saying what each column's values gave and `cites` per file, since a
  field has no origin of its own in the meta-model. A mixed column, a
  column of dates that read two ways and an empty column stay a string
  with a must question at the type citing the cells (ADR-122's way);
  required is a column with no blank; a column some files leave blank,
  one some files lack, a value of an enum only some files hold, and
  every inferred enum are questions; the primary key question lists the
  candidates.
- `--template` (the header row, with an instructions sheet beside it)
  and `--instructions` (a table of fields with a Values column) state the
  fields, with the type word, whether required, sensitivity, description
  and allowed values; the filled files are checked against them, each
  difference a must question citing the cells. The vocabulary gains the
  optional keys `headers.values`, `types.integer` and `types.decimal`
  (a file without them reads as before); the documents reader reads
  them too, integer as int32, decimal as a question for its precision
  and scale, and its line for a table that is no table of fields now
  names `extract tables`.
- The CSV dialect is detected and named: byte order mark, LF or CRLF,
  the delimiter of comma, semicolon, tab and bar that the most records
  hold as often as the header does, quoting; not UTF-8, lone CR, two delimiters
  that fit equally and a quote not closed are refused.
- `specarch check` takes a register file by its extension and compares
  it with the entity of its name: `register_not_specified`,
  `register_column_not_specified`, `register_column_missing` (a report
  for an optional field), `register_blank_required`,
  `register_value_not_in_enum` and `register_value_not_of_type`, each at
  the cell.
- `specarch generate register`, the plug-in `specarch-gen-register`
  (`internal/genregister`): per entity the header row as CSV, the
  instructions as CSV in the English vocabulary's words, and a workbook
  holding both, written by a workbook writer of the package's own that
  `internal/xlsx` reads back, the primary key's fields first. A plug-in
  may now answer a file that is not text in base64 under `encoding`,
  which generate decodes and `--check` compares byte for byte.
- Cases `extract-tables-register` (a BOM, CRLF, semicolon file),
  `-mixed-column` (a workbook), `-two-periods`, `-template`,
  `-quote-not-closed`, `check-register` and `generate-register`; unit
  tests for the dialect, the value kinds, the inference and the workbook
  round trip. The sample workbooks were written with the package's own
  writer.
- Left out on purpose: a register whose header is not its first row; a
  column of a form the rules do not name (a duration, a time of day),
  read as text with no question; instructions in another language, which
  a vocabulary file gives; a draft notice or a problem mark inside a CSV
  file, which has no comment. The records repository is described only
  generically. The handoff mailbox was empty. No bug was found.
