# 2026-10-15

## Bugs move from GitHub issues to BUG_OUTSTANDING.md and BUG_HISTORY.md

The owner decided that a public repository has no GitHub issues: issues
are being used against public repositories as the first step of a
malicious pull request that claims to fix one. Bugs are now kept in the
repository, one BUG-NNN entry each.

All 18 issues the repository had (#1 to #13, #15, #17, #18, #19 and #21,
every one closed as completed, no labels, no comments) are exported to
`BUG_HISTORY.md`, each as BUG-NNN with the same number and "was #N", with
its title, body, dates, state and the commits whose message says
`Fixes #N`. Numbers 014, 016 and 020 were pull requests and stay unused.
`BUG_OUTSTANDING.md` is empty; the next free number is BUG-022. The export
was checked against `gh issue view` for every issue: title, body, state
and comments match. No issue text named an employer, client or product,
so nothing was generalised.

`CONTRIBUTING.md` gets a Bugs section and no longer invites issues; a pull
request whose only grounds are that it fixes a listed bug is closed.
`SECURITY.md` sends a bug that is not a weakness to the owner instead of
an issue. `CLAUDE.md` says how an agent records and closes a bug, and
`README.md` lists the two files. The rollback step in
`spec/deployment/rollback.yaml` records the problem in
`BUG_OUTSTANDING.md` instead of an issue; ADR-117 and ADR-122 and
`docs/estate.md` name BUG-010, BUG-011 and BUG-009 for the issues they
cited. `docs/techspec.md` and `docs/deployment.md` are regenerated.

After this commit is pushed the 18 issues are deleted and the issue
feature is turned off on GitHub; the next entry records it.

## The issues are deleted and the issue feature is off

The owner deleted all 18 issues (#1 to #13, #15, #17, #18, #19, #21)
with `gh issue delete` and turned issues off with `gh repo edit
--enable-issues=false`, after 9f2f9d24 with the export was pushed.
Settings now: issues, discussions, projects and the wiki off; the owner
the only collaborator; rulesets protect-main (no force push, no
deletion, no bypass) and protect-version-tags; no interaction limits;
workflows on a fork's pull request need approval for first-time
contributors only; private vulnerability reporting on.

Open question for the owner: raise the fork pull request approval to
every outside contributor, add an interaction limit (six months at
most, renewed by hand), or require a review on main. Nothing was
changed there.
