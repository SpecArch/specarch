# 2026-10-28

## Decision tables on an algorithm (item 1342)

Item S4 of the spec-authoring plan the owner chose on 2026-10-27 (item
1325). An algorithm may now give `table` in place of `formula`, after
DMN 1.5's decision table (ADR-199, SA-104): the inputs are its columns,
each of `rules` has `when`, a condition per input it tests, and `then`,
the output, and `hitPolicy` is `unique` or `first`, always written. A
condition is a value, a comparison (`"< 6"`), comparisons joined by
`and` (`">= 3 and < 6"`), `null`, or a list of these; an input a rule
does not name matches anything, so a rule with no `when` is "everything
else".

Both validators read each rule as a box of value sets, one per input,
and check the table by its hit policy: under `unique` two rules that
both match some inputs are `table_overlap` at the later one, naming the
inputs; under `first` a rule the earlier ones always match first is a
`table_overlap` warning; under both, inputs no rule matches are
`table_gap`, written as whens that can be pasted in as rules. The gap
check keeps to an input's `minimum` and `maximum`, an int32's range and
a uint's zero. A condition or an output that cannot be read is
`decision_table` at it; a condition that holds for no value its input
may take (`"<= 0"` for an input above 0) is a `decision_table` warning,
found in review of the change before it was committed: it was first
reported as a rule the earlier ones always match. An input whose minimum and
maximum leave it no value is `decision_table` at the input, from the
same review. Each rule is a worked example (the first inputs
it reaches, its `then` expected), so `examples` is optional with a
table; the examples given are checked against the table as a formula's
are. `specarch try` evaluates a table on each rule's example and each
worked example and prints a step per rule tested. The technical
specification draws the table, a column per input, "any" where a rule
does not test one.

The library lending example gains `mayLend`, LIB-3's loan limit as a
table: no loan while a fee is unpaid, then below three open loans for a
standard member and six for an extended one. Design 9.5's mockup names
the algorithm `loanLimit` with an output `mayLend`; the example names
the algorithm `mayLend`, since it gives a yes or no, not a limit.

Cases, the same output in both builds: `validate-decision-table`,
`validate-decision-table-refused`, `try-decision-table` and
`try-decision-table-unreached`.

Left out on purpose: DMN's other hit policies (any, priority, output
order, rule order, collect), FEEL's own syntax for ranges and lists,
and tables over timestamps, times of day and durations; ADR-199 says
why for each. The test generators still write a test per worked example
only; a test per rule is a later addition.

## Decision tables: review round 1 (item 1342)

The review of the decision tables found three faults and a note; this
round settles them, in both builds.

- An input of a type a table does not test (a timestamp, a time of
  day, a duration) that no rule names made the table unread with no
  problem reported, so overlap, gaps and the worked examples went
  unchecked and `validate` passed. Such an input is now left out of the
  table's columns: every rule matches any value of it, the table is
  checked over the other inputs, and a worked example or `specarch try`
  may give it a value. A rule that names it is still `decision_table`.
  The alternative, an error at the input, was not taken: ADR-199
  already says an input a rule does not name matches any value.
- The `table_gap` advice "or a last rule with no when" is given only
  under hit policy `first`. Under `unique` such a rule overlaps every
  other one, so the advice is now "add a rule for each" alone.
- A string or enum condition that begins with `<`, `>` or `!=` is read
  as a comparison, so a value such as `<none>` cannot be matched by a
  table. ADR-199 and `docs/conventions.md` now say so, and the error
  names why the cell was read as a comparison and that a formula tests
  such a value. No second, quoted way to write it was added.

Cases: `validate-decision-table` gains an instant input no rule names
and a worked example that gives it; `validate-decision-table-refused`
gains `dueSoon`, a unique table with such an input whose overlap, gap
and wrong example are all reported.

## Decision tables: review round 2 (item 1342)

The second review found one fault in both builds and two lines left
unwrapped.

- An enum input whose `$ref` does not resolve has no values, and the
  checker read that as an input whose minimum and maximum leave no
  value. That pointed at bounds the input does not have, beside the
  real `ref_type` error, and left the table unchecked. Now the
  empty-bounds error is given only for an ordered type. Such an enum
  input is treated like an untested type: when no rule names it, the
  table is checked over the other inputs; when a rule names it, the
  table is not checked, and `ref_type` alone is reported.
- ADR-199's gap paragraph and the decision-table paragraph of
  `docs/conventions.md` are rewrapped to the files' width, and both
  now say how an unresolved enum input is handled.

Cases: `validate-decision-table-refused` gains `lostShelf` (no rule
names the input; its gap is still reported) and `namedShelf` (a rule
names it; only `ref_type`).

## The integration contract (item 1343, S5)

S5 of the spec-authoring plan: a dependency says how this system
proves itself to it, how often it may call and, when it has no
specification of its own, its operations; a call says how it is made,
mapped, retried and answered (ADR-200, SA-105).

- On a dependency: `auth` (none, apiKey, basic, bearer,
  oauth2ClientCredentials, mutualTls, signedRequest), `credential`, the
  name of a secret setting under `configuration`, `rate`, lifted out of
  `limits` into a definition of its own so both read the same, and
  `operations`, each a request (method and path) or a message sent
  (channel and message), with its request fields and its answers by
  status, one level deep. A calls entry names one as
  `<dependency>#/operations/<name>`.
- A calls entry of an operation may be an object with `call` and the
  contract: `mapping.send` and `mapping.receive`, `idempotencyKey`
  (header and value), `retries` (limit, delay, backoff, on), `errors`
  (their status or timeout to ours) and `mode` (sync, async with a
  `callback`, fireAndForget). A plain entry reads as before. Every
  reader of `calls`, in both builds and the generators, now reads the
  name through one helper, so an object entry is never read as an
  empty name.
- Both validators check both sides under a new rule, `integration`
  (with `setting`, `expression_type`, `expression_name` and `emits`
  where those already apply), and give the same lines. A post or patch
  retried with no idempotency key is a warning.
- Derived cases, always written as a failing dependency's are:
  `dependency retries exhausted`, `dependency answers unmapped` and
  `dependency rate exceeded`, the last for a job's and a gateway's
  calls too. A timeout that `errors` maps is answered
  as it maps it, and a dependency called only fire and forget fails and
  times out with the operation succeeding all the same.
- The context diagram writes a dependency's auth and rate on its node;
  the technical specification says how each dependency proves itself,
  its rate and its operations, names each called operation's method and
  path, and gives each call's contract under its operation; the
  workflow diagram draws each dependency an operation step calls, the
  edge naming the operation.
- The library lending example's fee ledger gains bearer auth with the
  secret setting `feeLedgerToken`, a rate of 10 calls a second and its
  `postCharge` operation; `returnLoan` maps the late fee to it, sends an
  idempotency key, retries 503 and timeouts and maps both to its own
  503. Four tests cover the new cases.

Where the design and the format differ: the design names the call's
key `retry`; it is `retries`, the word and the `limit` a job and a
workflow failure already use. The design's `idempotencyKey` on a call
is an object with `header` and `value`, since on an operation the same
word names only the header. Object entries are taken on an operation's
`calls` only: a job has no answer to map errors to, and a gateway's
calls are lookups. Examples of a mapping run through `specarch try` are
S2's (item 1341), which waits for this item. A mapping on a call through
another specification's paths is read and not checked against that
specification's fields.

Cases: `validate-integration-contract`, `validate-integration-contract-refused`,
`derive-integration-contract` and `document-techspec-integration` (the
context diagram golden). No dependency changes.

## S5, review round 1: one case per call, fire and forget to the end, null sends

The review of the integration contract asked for five changes, all made
in both builds.

- A call made fire and forget is not waited for, so its retries used up
  and its unmapped answer now end with the operation succeeding all the
  same, as its failure and its timeout already did; so does the rate
  exceeded case of a dependency the operation calls only fire and forget.
- A call's retries-used-up and unmapped-answer cases are named by the
  dependency and the operation called (`dependency retries exhausted
  feeLedger postCharge`), so a second call to the same dependency no
  longer loses its cases to the first's name. Two calls that still read
  the same (the dependency named alone twice) add their place
  (`auditLog call 4`). The retries' last answer comes from that call's
  own `errors`, not from another call to the same dependency. The
  library lending example's two tests and the cases' tests were renamed
  to match; the cases are not released yet, so no written test elsewhere
  is affected.
- An `errors` that maps only `timeout` no longer derives an unmapped
  answer case, which only repeated the dependency fails case.
- A value sent or kept that may be null where the field takes none is an
  `expression_type` warning at the value.
- The generators' reader of calls skips an object entry with no `call`,
  as the validator's does, so no diagram draws a dependency with no name.

New cases: `derive-integration-contract-per-call` and
`validate-integration-contract-null`. No dependency changes.

## The caller's home after a sign-in (item 1414)

A task page's answer may now lead to the caller's home with `navigate:
callerHome`: the home of the first of the session's roles that has one,
and the application's start when none of them has one (ADR-206). The
review of S7 (item 1331) found that a sign-in through a page of the
specification's own had to name one page for everyone, so in the
library lending example a member signing in was led to the members list
and refused there. The example's sign-in and second-factor pages now
lead to `callerHome`, and their two tests say the librarian is led to
their home, the members list.

- `callerHome` has a capital, as `signIn` and `signedIn` do, so no page
  can take the name and no valid file of an earlier 1.x turns into an
  error.
- Both builds take it on a task page's answer only, with a message and
  no `with`, and report it as `flow` anywhere else, with `with`, or when
  no role names a home. A flow step whose answer leads to `callerHome`
  goes on at the actor's home. The derived case reads "leads to the
  caller's home".
- specarch-gen-ui leads to `index.html`, the start, which reads the
  session anew and opens the home, and now shows the message a page left
  for it when the person has no home; without an `index.html` it warns
  at the event and the answer stays on the page.
  specarch-gen-ui-typescript reads the session in the task page and
  opens the home's route, or `/`; specarch-gen-ui-swiftui reads it
  through the session store and puts the home alone on the navigation
  stack, or empties it. Both open the page that sent the person to sign
  in first, as for any other answer.
- The techspec's page flowchart draws the caller's home as one node, and
  the manual says "Your home page opens."

The decision was first written as ADR-201, a number the Swift
implementation file already holds; it is ADR-206. New cases:
`validate-caller-home`, `validate-caller-home-refused`,
`validate-caller-home-no-home` and `derive-caller-home`; the four
navigation generator cases gained a sign-in page. No dependency changes.
Not released: the tag waits for the review's approval.

## Worked examples of a call's mapping (item 1341, S2)

A call's mapping may hold `examples` (ADR-207, SA-106): each a name, a
note and four records, `inputs` (our values send reads), `sent` (their
request's fields as send gives them), `answer` (their answer's fields)
and `kept` (the record's fields as receive gives them). Both validators
read each value at its field, check that `inputs` and `answer` give
exactly the names the expressions read and that `sent` and `kept` give
exactly the fields send and receive give, evaluate send and receive and
report what does not hold under example_input, example_expected,
example_mismatch and example_error at the value; `kept` on a call that
does not wait or has no receive, and `sent` with no send, are
integration errors. `specarch try` takes an operationId in place of an
algorithm and prints, per call named as the derived cases name it, each
example's inputs, each field's steps and its value beside the expected
one, the answer and each field kept; `--json` puts them under
`tryOperation`, and `try`'s own object is unchanged. A name both an
algorithm and an operation have is refused, and so are `--inputs` and
`--file` with an operation.

The Go, Swift and Dart test generators write a test per example through
`MappingHarness` (`Send`, `Receive`), declared beside `Harness` only when
the specification holds a mapping example, so a project's harness that
has none keeps compiling, and one that lacks it fails the mapping tests
alone. The technical specification lists each call's examples in a
table under the call's contract. The library lending example's
returnLoan call to the fee ledger has one example, sent only, since
Loan keeps nothing from the ledger's answer; the conformance cases
cover receive.

Decisions: the examples sit under `mapping`, beside send and receive,
not on the calls entry; `inputs` gives the names read, not every name
send may read (the whole guarded record); try takes the operationId
rather than a second command or a `--call` option; the generated tests
go through an interface of their own because `Harness` is written by
hand in every project. Derive's naming of calls moved into one helper,
callNames, used by derive and try in both builds.

Left out on purpose: the transition half of S2 (examples on a state
machine's transitions), which needs a transition's `when` and `set`,
not built yet (ADR-190); `--file` for a proposed mapping. No release:
Review is on, so the tag, `agentq sbom` and the install into ~/go/bin
follow the approval. The handoff mailbox was empty. Nothing of the
private design file was copied; the examples are library lending's.
