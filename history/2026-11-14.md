## Design security rules: weaknesses a specification shows before code

The validator now warns about seven design weaknesses, at the element to
change and in the problems file, in both builds (ADR-247, SA-146 and
SA-147): `object_unscoped` (an operation that reaches any record by its
key, IDOR by design), `internal_key_exposed` (a whole-number key in a URL,
a request body or a response), `refusal_reveals_record` (a 403 that tells
whether a record exists),
`query_from_caller` (a sort field, filter, field list or query taken from
the caller with no list of the values it allows), `duties_unseparated` (a
requirement asking for separation of duties that no set gives),
`secret_unprotected` (a credential field with no atRest, a secret setting
with no rotation) and `audit_not_append_only` (an audit trail that can be
changed). Each is a warning, so a specification is still read whole; the
names are stable, since a tool that traces a finding into the code cites
them, and the problems file's SARIF log tags each with
`properties.tags: [security]`.

Four keywords give the rules what to read: a requirement's `controls`
(`separationOfDuties`, `auditTrail`), an entity's `appendOnly: true`,
`atRest: hashed` beside `encrypted`, and a secret setting's `rotation`. A
hashed field is never a key, unique, searched, filtered or sorted
(`at_rest`, `list_of`), and specarch-gen-sql and the dxlib generator's
row filters report a hashed field rather than treating it as a plain
column. The keywords went into the 1.0 schema as optional keys, as the
intent keys of ADR-244 did. `secret_unprotected` holds only for a file
on meta-model 1.0 or later, whose schema has `hashed` and `rotation`, as
`problem_missing` holds; an earlier file is not warned.

Choices made on the way:

- `duties_unseparated` does not warn at a workflow approver who also
  holds the permission that starts the workflow: every approval step
  already derives the case "requester approves own request", refused at
  run time, so the warning would ask for a set the design does not need.
- `refusal_reveals_record` does not warn at a keyed operation over a
  row-limited entity that lists no 404: the derivation already answers a
  key outside the row policy as not found, listed or not.
- `query_from_caller` reads every name in parameters, but only a query's
  own names (`sql`, `rawQuery`, `statement`) in a request body: a body's
  `order` or `condition` is as often a value of the record.
- Raw SQL has no construct in the design, nor in the implementation
  schema (no key for a hand-written query), so it is found as a query a
  caller sends.

The rules over SpecArch's own specification and the examples
(`specarch validate spec examples`, both builds the same): 7 warnings.
examples/lending-desk 4 `internal_key_exposed` (a loan's integer id in
lendBook's 201 and listMemberLoans' 200, and loanId in the URL of
returnBook and renewLoan; the estate reads lending-desk and shows the same
4), examples/library-lending 2 `secret_unprotected` (databaseUrl,
feeLedgerToken with no rotation), examples/release-watcher 1
`secret_unprotected` (registryToken). spec, notice-board, reading-list,
room-booking and the estate's own modules: none. The examples are left as
they are, so the warnings show.

Existing cases on 1.0 whose secret settings had no rotation got
`rotation: P90D`, so they test what they were written for; the cases
whose fixtures reach a record by key with a public permission
(generate-scripts, generate-sqlc-queries, validate-guard-writes) and
the extract and merge cases that read integer keys from OpenAPI carry the
new warnings, and validate-guard-writes says so.

specarch-gen-sql does not write a column for a hashed field yet: it
reports the field (generate-sql-hashed-refused), so the advice of
`secret_unprotected` for a password leads, for now, to a field the sql
target refuses.

New cases: generate-sql-hashed-refused, validate-security-<rule> and validate-security-<rule>-fixed
for each rule, validate-security-audit-not-append-only-changed,
validate-security-hashed-at-rest and document-problems-security-tags. Docs:
docs/diagnostics.md section 4.1 gives each rule's text, docs/conventions.md
the keywords. New sources: OWASP API Security Top 10, NIST SP 800-57
Part 1, NIST SP 800-63B.
