# 2026-10-13

## Release 0.6.0

The sixth release is cut from this commit, on top of 8f9a555 (CI green),
so that a project outside this repository can pin an exact version that
reads meta-model 0.2. The owner approved the v0.6.0 tag. The release
record is released; `info.version` and both implementation files'
`implements.version` are 0.6.0; both builds and the version case print
0.6.0, with meta-model 0.2 for specifications. The implementation files
stay at 0.1.0.

Hint lines that move to the tag, as 0.5.0 did: the root files of `spec/`
and both examples, the schema line `extract` writes and every expected
tree in `spec/tests` that carries it, the editor hints in the README and
`docs/conventions.md` (design 0.2, which had pointed at `main` because no
tag served it), and the implementation-file hints (v0.5.0 to v0.6.0). The
install lines in the README (all nine plug-ins) and `docs/from-sources.md`
point at v0.6.0. Left as they are on purpose: the 0.1 conformance
fixtures' hints at `v0.5.0/schema/specarch-design-0.1`, since v0.5.0 is
the last tag that serves the 0.1 design schema; the schemas' `$id`s and
the idiom and record hints, which stay on `main` as they did at v0.5.0.

What 0.6.0 carries beyond 0.5.0, for its users:

- Meta-model 0.2. Separation of duties, approval workflows with the
  four-eyes rule, task pages that load no record, value objects, unique
  rules with a condition, switched elements, a requirement's release,
  wire names (`info.wireNames`), child rows, pickers, actions by state
  with a reason, rules across fields, and the rows of a one-to-many
  relation on a view.
- The one change that breaks a 0.1 file moved to 0.2: in a file that says
  `specarch: "0.2"`, a derived case no test covers, and a subject with no
  golden test when the design gives its success, are errors; `specarch
  derive` writes those tests as drafts. A file that stays on
  `specarch: "0.1"` keeps validating, with the old warnings and one
  `meta_model_version` warning, until 1.0. `extract` and `merge` write 0.2
  trees with the drafts derived.
- New readers for `extract`: BPMN 2.0 workflows, Go source (routes on
  net/http, chi, gin, echo and gorilla/mux; dxlib services, tables, seeds
  and gates), Swift, JavaScript and TypeScript, Next.js, Vue and Nuxt, and
  Dart and Flutter, the last four through code-facts dumps.
- One problems file (`problems.txt` and a SARIF log) with a mark above
  every entry a problem touches, in the fragments and in generated code;
  documents and gaps are written for an invalid specification too; every
  diagnostic line names its column and id.
- `document html`, the whole specification as one page.
- Two plug-ins new in a release: `specarch-gen-ui-typescript` (task,
  list, form and view pages on Next.js and Carbon, with server routes,
  strings per language and the theme) and `specarch-gen-bpmn` (each
  workflow as BPMN 2.0 with an SVG). `generate --check` compares screens
  built by hand.
- Errors from a read, a plug-in or a version name the real reason. Go
  1.27.2.

go build, go vet, go test, govulncheck (no vulnerabilities), swift test
(14 pass), validate on `spec` and `examples` in both builds with the same
output (0 errors, 2 warnings, 7 open questions), the fragment schema check
and every `document --check` CI runs pass. No dependency change.

Handoffs: none processed. `metamodel-gaps-from-sources.md` stays in the
mailbox for an item of its own.
