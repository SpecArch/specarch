# 2026-10-14

## extract go follows a router into a method of a constructed value; extract documents keys an all-caps name as one word

Two defects in 0.6.0, reported from a project that extracts a
multi-module Go codebase. Issues #8 and #9.

Issue #8, serious: `extract go` wrote 0 operations for a module whose
routes are registered by a method of a struct another package's
constructor returns, in the shape `server := rest.NewServer();
server.RegisterRoutes(r)`, with `RegisterRoutes` doing `r.GET("/items",
s.List)` in `internal/api/rest`. Every route became a must question,
"registers GET /items on a router whose place the reader does not know
(... is given the router r, and the reader found no call that passes it
one whose path it knows)". Cause: the walk typed a name only from `T{}`,
`&T{}` or `new(T)`, so a value a constructor returned had no type, the
method the router was passed to was not found, and the method was later
walked as one given a router from nowhere. Fix in
`internal/extract/golang_routers.go`: a name assigned from a call of a
function or method of the module takes the type that function declares
for its result, in the one-value form and in `server, err :=
rest.Open()`; `ADR-081` says so. A call inside a closure, a command's
run function, needed nothing more, since the walk already descends into
function literals. Tests: `TestGoRouterPassedToMethodOfConstructedValue`
(constructor alone and with an error, two commands) and
`TestGoRouterPassedFromClosure` (a run function in a command struct),
both in `internal/extract/golang_test.go` with a `go.mod` written at
test time, as the handler test does, since a conformance fixture carries
no module file and cross-package names need the module path. Both fail
on the old reader and pass on the new.

Issue #9, small: `extract documents ARCHITECTURE.md` gave the source key
`a-r-c-h-i-t-e-c-t-u-r-e`, so two such documents collided at `merge`.
Cause: `kebab` put a dash before every capital. Now a capital starts a
word after a small letter or a digit, and inside a run of capitals only
the last does, and only when a small letter follows it: `ARCHITECTURE`
is `architecture`, `README` `readme`, `FSD-Login` `fsd-login`,
`HTTPServer` `http-server`, `userID` `user-id`. The same function names
an OpenAPI document's default key and the derived tests' names, so the
Swift validator's `kebab` in `Tests.swift` takes the same rule, and
both builds still print the same on `spec` and `examples`. Tests:
`TestKebab` in `internal/extract/tree_test.go`, and the conformance case
`extract-documents-upper-case-name`, recorded from a run of the built
binary. The design test count rises to 401.

Checks: go build, go vet, `go test ./...` with the conformance suite,
every `document --check` on `spec` and `examples`, swift build and
test, and validate on `spec` and `examples` in both builds with the same
output. No dependency change. The documents are regenerated.

Handoff: the request came through the queue's handoff folder, not the
mailbox; nothing of it is in the repository. The mailbox holds two
files for other items (`audience-marker-and-items-owned-elsewhere.md`,
`extracting-many-modules-read-only.md`), left for them.

Open: the version. The code is unchanged since v0.6.0 and `specarch
version` still prints 0.6.0 while the specification is at 0.7.0-dev, so
the fixes can be cut as 0.6.1 from main; the owner decides how and when
to tag, and the binary in `~/go/bin` is reinstalled then.

Simulator: not needed, no app code.

## Specifying an estate of modules: the design, from the second handoff

A team specifying an estate of some twenty modules from an umbrella
repository that holds the code as submodules, without the right to
commit to any of them, ran a pilot of `specarch extract` and `merge`
0.6.0 on one module and asked for twelve things, ordered by what blocks
the job. `docs/estate.md` is the answer: where each stands, the design
of the planned ones, fourteen build items in order with the must-have
points first, and seven questions for the owner with the recommendation
first. Nothing is built; each item writes its own decision record when
it lands, so `spec/` is unchanged and no document is regenerated. The
roadmap's section 5 and `docs/extraction.md` point at the plan.

Where each point stands:

- planned, must-have: a dump committed outside the code's repository
  (`repository` in every dump, checked against the gitlink the dump's
  repository records; item 1); role names on the wire
  (`info.roleNames: upper_snake`, after the one-rule choice of
  ADR-062; item 2); authorisation by path pattern, as `implies` on a
  permission and pattern rules in the permission table, one permission
  per distinct pattern and method pair named by a fixed rule, each
  route's permission the one every other matching permission implies
  (item 3); documents in another language, with the commitment words,
  table headers, yes words, sensitivity words and quantity units as a
  vocabulary file per language, English shipped, `language` on the
  source, the row-number column skipped and a run of capitals read as
  one word in a source key (item 4); references between specifications
  as `<dependency>#/<pointer>` through a dependency's `specification`
  and `version`, counted as unresolved when the other specification is
  not given and checked when it is (item 5); and the umbrella, a
  `specarch-estate` root listing modules with location and version
  (item 6);
- planned, should-have: a gate by caller kind in the permission table
  (item 7), whose meta-model side reopens a row 0.3 left out and is the
  owner's question; the schema file's name as a UI binding and
  `specarch facts` running the embedded JavaScript reader from a
  per-user cache without a checkout (item 8); a printed workflow table
  read by `extract workflows --table` (item 9); `audience` on an
  element with one validator check, `ownedBy` and `fulfilledBy` on a
  requirement held elsewhere (item 10); material questions grouped,
  `opens` on a decision for a partial answer, per-stage counts and the
  `citation_clause` warning (item 11); `--given-outside`, the list
  twin without a question, `generatedDefault` as a closed set, and
  indexes in the implementation file's mapping written by the database
  reader (item 12);
- shipped: the OpenAPI document and SQL migrations (0.4.0); the
  Next.js UI generator with task pages, list, form and view pages and a
  private component library through an idiom override (0.6.0); a row
  citation as a clause carrying the row's identifier (the clause rule);
- planned later: sqlc queries (item 13) and `specarch check` with a
  shrinking allowlist for the CI gates (item 14);
- declined, with the reason in the plan's table: a permission defined
  by a path pattern, a plug-in reader for workflows, a shipped
  vocabulary per language before a project supplies one, `release`
  naming a release with no record, a per-file acknowledgement of the
  version warning, Go server interfaces as a SpecArch target, and an
  index as a design keyword.

Left out of the public files on purpose: the estate's owner, its
modules, their names, routes, roles and tables, the language of its
documents, and every count the pilot measured (tables, sentences,
pages, files, questions). The plan speaks of a customer registry, a
catalogue service and the lending desk.

Handoffs: the two mailbox files behind the second handoff, the
read-only pilot's lessons and the review-report reconciliation's
lessons, are answered in full by `docs/estate.md`, every section and
every smaller point. They are deleted once this item has landed and
been pushed, by the repository's own agent, since an extra agent's
session closes at its finish.

Checked: a documents-only change; `git diff --stat` and a search of the
new files for the handoff's identifying words. No build, no dependency
change. Simulator: not needed, no app code.
