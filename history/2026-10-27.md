## Both builds read `date()` of an instant in the specification's time zone (BUG-064, item 1300)

Asked by the owner (item 1300), from the finding item 1291 reported: `date()`
of an instant in an expression gave the calendar date at the offset the
instant was written with in the Go build and in UTC in the Swift build,
so `date(timestamp("2026-10-27T03:00:00+07:00"))` was the 27th in one and
the 26th in the other, against the rule that both builds print the same
output; the Go build also printed such an instant with its written
offset where the Swift build printed `Z`. The rule was already designed
by 1291 (ADR-193, `docs/state-machines.md` 12.3, SA-99) and nothing of it
was built.

Built, in both validators: the root key `timeZone`, a name of the IANA
Time Zone Database, in the 1.0 design schema (root only, like
`trustDomain`, so the fragment schemas are unchanged) and in `rootOnly`;
the rule `time_zone` with its two cases for the key, a name the database
does not hold as an error at the key, and a `date()` of an instant in a
specification that declares none as a warning at the call, naming the
input the call reads; both evaluators take the zone and give the
instant's date in it, UTC without one, and the Go build keeps every
instant in UTC, so both print one writing for one instant. The warning
comes from one hook, `zoneWarnings`, after every successful type check:
an entity's check and unique condition, a guard's precondition, a
formula, a page condition, a role's row policy and a token's check; the
tenant rule is derived and holds no `date()`. The design gives `date()`
no zone argument, so the item's "or an explicit zone" branch has nothing
to build. A `timeZone` the database does not hold is the error at the
key alone, and the date is UTC's until the key is corrected (12.3).

The name check is the same on every host, which the platform libraries
alone are not: on this Mac the Go build's `time.LoadLocation` accepted
`asia/jakarta`, `utc`, `Local` and `posixrules` (a case-insensitive file
system, the host's zone), and Foundation accepted `PST` and `GMT+7`
(names ICU knows beyond the database) while refusing miscased names.
Both builds now check the form first (each part begun with a capital),
refuse `Local`, read the host's `zoneinfo` folders by exact spelling and
refuse a name a folder holds in another spelling (`Asia/JAKARTA`), and
the Swift build takes a name no folder holds only when Foundation lists
it as a zone of the database or it is `UTC`, since the Go build's
embedded copy of the database decides there. The case
`validate-time-zone-unknown` holds five specifications at the edges
(`WIB`, `asia/jakarta`, `Asia/JAKARTA`, `PST`, `GMT+7`) and expects the
same five lines from both builds; `validate-time-zone` declares
`Asia/Jakarta` and expects one date for one instant written with `+07:00`
and in `Z`; `validate-time-zone-missing` expects the warning at a call
over an input and over a literal, and the dates in UTC. Each verifies
SA-99, which is proposed, as ADR-193 is: the owner approved the design
(item 1291, round 3) and asked for this fix; the statuses are the
owner's to move.

The library lending example declares `timeZone: UTC`, the zone 12.5
proposes for an example that names no place: its Loan's check
`lentOn <= date(loanedAt)` keeps the reading it had and gets no line.
The Go build imports `time/tzdata`, the database itself, so a host that
keeps none still reads a name. `docs/state-machines.md` 12.3, 12.5 and
the build plan's step 5 now read as the current truth: the `date()`
reading is built, the rest of step 5 (the two formats, `why`, the other
five cases of `time_zone`, the idiom rows, `generate sql` rendering
`date()` in `timeZone` and the nullable `EnteredAt` column) remains;
`docs/conventions.md` gains the `timeZone` row in the keyword table and
the zone in the `date(x)` row and the timestamp row.

Found on the way and reported, not fixed: `generate sql` renders
`date()` of an instant as `CAST(x AS DATE)` (Oracle `TRUNC`), which reads
the zone the stack's type gives it, the session's on PostgreSQL, where
the design said no generator renders `date()` today; the design now
names its rendering in `timeZone` as the build item's. The generated
SwiftUI `Rules.swift` pins UTC for its date reading, for the same item.

`swift/embed-schemas.sh`; `tools/fragment-schemas` changed nothing),
`spec/design/enums/rule.yaml`, `internal/expr` (`eval.go`, `check.go`,
`parse.go`, `expr_test.go`), `internal/validate` (`diagnostic.go`,
`file.go`, `design.go`, `expressions.go`, `caller.go`, `tokens.go`,
`elements.go`, `testdata.go`, the new `timezone.go` and
`timezone_test.go`), `internal/spec/spec.go`, the Swift twins
(`ExprEval.swift`, `ExprCheck.swift`, `ExprParse.swift`,

## `specarch try` evaluates an algorithm and prints each step (item 1328)

Asked by the owner (item 1328), the first item of the plan for writing a
specification through examples with their results: a command that
evaluates an algorithm on its worked examples, on one of them or on
inputs given on the command line, and prints each operation and call of
the formula with the value it gave, the result and the expected value,
in both builds, with `--json` for an editor and `--file` to try a
proposed algorithm not yet in the specification. Designed first as
SA-100, `spec/design/commands/try.yaml` and ADR-195, then built.

What it does: validate first, the specification's errors printed and
the example_mismatch and example_error lines of the examples evaluated
left out, since their evaluations say the same; a summary line; then each
evaluation with its inputs, its steps in the order computed and its
result beside the expected value, and its outcome: pass, fail, cannot
be computed (the steps before the failure, then the reason) or cannot
be read (an input or the expected value that does not fit its field).
The evaluator is validate's: both builds gained an optional recorder in
it and an optional table of each node's type in the type checker, and
validate itself is unchanged. A literal or a name is no step; the
operand of && or || not read and the branch of ?: not taken are not
computed, so they are not printed, as cel-go's state tracking without
exhaustive evaluation records them. Each sub-expression is written from
the parsed tree, with only the parentheses CEL's grammar needs, so both
builds print the same text. `--inputs` is a YAML mapping written as an
example's inputs are and read by the same rules. `--file` is a design
fragment whose algorithm takes the place of the specification's key by
key, so a file holding only a new formula is tried on the examples the
specification holds; the specification is validated with it in place,
so a problem of the proposal is a line at the file.

Settled while holding the two builds to the same bytes: a value is
written as a worked example writes it, so it can be copied into one,
with a date, an instant and a duration in quotes; a duration in ISO
8601's day-and-time form, P14D and P1DT6H rather than the Go build's
`336h0m0s` or the Swift build's seconds; a decimal of no fixed scale, a
quotient, to 20 places, since the Swift build holds 38 digits and the Go
build an exact fraction; a double in one shortest form, written by a
rule both builds now share for the trace (validate's own messages keep
each build's existing form).

Tests: Go `internal/expr` trace tests (order and scale, what is not
computed, the printer's parentheses, the value forms) and their Swift
twins in `ExprTests.swift`; 17 conformance cases `spec/tests/try-*`,
`try-json` in the Go build only as for every `--json` case, the others
in both; the help topic `docs/help/try.txt`, required by
`TestHelpTopics`. `capabilities-text`, `guide-order-of-work` and
`AGENTS.md` gained the command's lines.

Where the plan and the code differ: the plan names `try` for a
transition's `when` and `set` and for a call's mapping as well; the
state machines are designed but not built and calls have no mapping
yet, so this item tries algorithms only, and the recorder is what those
later items reuse.

Files changed: `cmd/specarch` (the new `try.go`, `main.go`, `json.go`,
`self_test.go`), `internal/expr` (`eval.go`, `check.go`, the new
`print.go`, `expr_test.go`), the new `internal/spec/overlay.go` and
`internal/validate/try.go`, the Swift twins (`ExprEval.swift`,
`ExprCheck.swift`, `Spec.swift`, `Command.swift`, the new
`ExprPrint.swift` and `Try.swift`, `ConformanceTests.swift`,
`ExprTests.swift`), the specification (SA-100, the command, ADR-195, both
implementation files), the cases, `README.md`, `AGENTS.md`,
`docs/help/try.txt` and the documents `scripts/regenerate.sh` writes. The
handoff mailbox was empty. No dependency changed. Release (minor) is
left to the release chain, after the review's approval. Nothing was
left out on purpose.

Found in the review before finishing and fixed in a second commit: the
first left out those lines for every example of the algorithm, so with
`--example` or `--inputs` an example that was not evaluated and did not
hold printed nothing and the run exited 0. Now only the lines of the
examples evaluated are left out, in both builds, and the case
`try-example-others-fail` holds it.

Review round 1 of item 1328 found that a proposal whose formula type
does not fit the output (a quotient left unrounded for an output of
scale 2) printed a failing example whose result and expected value read
the same, since the result was written rounded to the output's scale.
Now the evaluation fails, its result is written at the formula's own
type, every place of the quotient, and the line after it gives the type
check's reason, in both builds; the command's design says so and the
case `try-file-unrounded` holds it.
