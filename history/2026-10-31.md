## A test map: the narrowest check for each changed path (item 1589)

`scripts/test-map.json` maps the repository's paths to the narrowest
command that covers them, so work in progress runs those instead of the
whole landing check; the landing check stays the test before landing.
The first matching rule takes a path:

- `go.mod`, `go.sum`: `go test ./...`.
- `spec/tests/**`: only the conformance cases the change touches (the
  case folder names, from the paths, as a `-run` filter on
  `TestConformance`, with `TestCommandTestsHaveCases`), the Swift
  conformance suite, and `validate spec examples`.
- `swift/**`: the landing check's swift part.
- `schema/**`, `idioms/**`, `scripts/landing-check.sh`,
  `scripts/regenerate.sh`: the whole landing check, since both builds
  embed the schemas and idioms.
- `embed.go`, `docs/help/**`: `go test ./cmd/specarch` (its self tests read
  them).
- `third_party/**`: `go test ./internal/extract ./cmd/specarch`.
- `cmd/specarch-gen-*/**`, `internal/gen*/**`: `go vet` and `go test
  -count=1` of the changed packages and `./cmd/specarch`. The count is
  forced because the conformance suite builds the plug-ins with `go build`
  while it runs, which Go's test cache does not see, so a cached pass
  would hide a broken generator.
- `*.go`: `go vet` and `go test` of the changed packages and
  `./cmd/specarch`. Most packages have no tests of their own; the
  conformance suite in `cmd/specarch` is what exercises them.
- `spec/**`, `examples/**`, `records/**`, `vocabularies/**`, `readers/**`,
  `tools/**` and the generated documents in `docs/`: the landing check's
  go part (validate, documents and generated code current).

Paths no rule takes run nothing: the prose in `docs/` and at the root,
`history/`, `.github/`, `sbom/`, `scripts/sbom.sh` and the map itself.
`CONTRIBUTING.md` says how the map is read.

Each rule was then checked by changing one file under it and running the
map's selection on that change. Two rules did not do what this entry says, and the map
was corrected:

- A glob ending in `/**` takes a literal folder, so
  `cmd/specarch-gen-*/**` and `internal/gen*/**` matched nothing and every
  generator file fell to the `*.go` rule, without `-count=1`. They are now
  `cmd/specarch-gen-*/*`, `cmd/specarch-gen-*/*/*`, `internal/gen*/*` and
  `internal/gen*/*/*` (a `*` stops at `/`). The folders two levels deep
  hold templates, not packages, so they have a rule of their own that
  vets and tests the generator package above them.
- The `.go` files under `examples/` went to the `*.go` rule, whose `go vet`
  fails on them: the lending-desk code is a module of its own and the
  notice-board sources import a library this module does not require.
  `examples/**` is now its own rule, the landing check's go part, listed
  before `*.go`.

`cmd/specarch/testdata/**` was added to the `go test ./cmd/specarch` rule;
its two fixtures matched no rule before.

## Asking a person: one question at a time, ranked by gaps --next (item 1680)

The owner compared SpecArch with Spec Kit (github.com/github/spec-kit,
MIT) and tried both on an existing system. SpecArch checked and captured
better; Spec Kit's clarify command asks better: one question at a time,
two to five options with one recommended that the person can accept in
a word, ranked by impact and uncertainty, at most five per run. SpecArch
recorded answers (questions, decide, decision records) and gave the
agent no method for asking. This item takes that method over, credited
to Spec Kit in ADR-209, the help topic and `docs/refinement.md`.

- `specarch help asking`: the procedure. Run `gaps --next`, put the one
  question to the role it names, offer two to five options with one
  recommended and its reason, record the full text of the option chosen
  with `decide --source` an interview, write the entries decide lists,
  validate, and run `gaps --next` again, since an answer can settle or
  open other questions. No fixed number of questions: a must question
  left unasked leaves keys undefined. A material question is asked as a
  request for the file. The agent guide's workflow step 4 and its list
  of what to ask the owner point to it, and `AGENTS.md` follows.
- `specarch gaps --next`: per specification, the one open question
  ranked first: priority, then the outputs it holds up (documents and
  code targets, from the same list as the outputs table, which now reads
  it too), then the entries it blocks, then the stage, then the ID. It
  prints who decides, what it blocks with the keys missing there, what
  it holds up, the options, the Insight and the decide line, with
  `--source` filled when the root file declares exactly one interview
  source (a document source for material), otherwise a line saying
  which to declare or choose. Errors come first as problem lines; the
  exit status is that of gaps. With `--json`, `next` holds the same as
  data and `recommendation: null`, for the agent to fill before it
  passes the question on.
- Specification first: SA-107, ADR-209 (proposed), the option and its
  output in `spec/design/commands/gaps.yaml`, the source `spec-kit` in
  the root file, the topic in `help.yaml`. Cases `gaps-next-ranks-by-outputs`,
  `gaps-next-ranks-by-blocks` (with an error in the specification),
  `gaps-next-should-before-could`, `gaps-next-json`, `gaps-next-none`,
  `gaps-next-usage-error` and `gaps-next-unknown-option`;
  `capabilities-text` and `guide-order-of-work` recorded again.

Left out on purpose: uncertainty as a ranking key. No key of a question
says how unsure the people are (`certainty` is only for questions a
reader asks about code), so the agent says it in its recommendation's
reason. A `recommended` key on the question in the meta-model was
considered and not taken: a format change in both validators that would
write into the design a guess no person has seen. Not built in the Swift
build, which has no gaps. Nothing of the trial's system is named here.

The specarch handoff mailbox was checked and is empty; nothing was
deleted.

## A short on-ramp: specarch init, help start and the lean profile (item 1681)

From the same comparison with Spec Kit (github.com/github/spec-kit, MIT):
Spec Kit sets a project up in one command and asks nothing of a first
draft, while a SpecArch first draft met a wall of errors. The smallest
specification already validated; the step after it did not. A draft of
one entity and one operation, written as a newcomer writes it, gave
eight errors; with the required keys written it still gave five, all of
them tests the design implies (the success and four derived cases). In
the library lending example 198 of 283 YAML files are tests.

- `specarch init [--title <title>] [--profile lean|full] [--dry-run]
  <folder>`: writes `specarch.yaml` with the `$schema` line pinned to the
  release, the meta-model version, and `info` with the title (the
  folder's name when `--title` is left out), version 0.1.0 and the
  profile when given. Nothing else, since a placeholder entity would be
  a definition nobody made. A folder that holds `specarch.yaml` is exit
  2 and is never overwritten.
- `specarch help start`: the next step, a first entity and operation
  that validate, the five things a first draft often leaves out that
  every profile asks for, the lean profile, writing the tests (list
  `tests` in `stages`, make the folder, run derive, since derive refuses
  tests kept in the root file) and how to tighten it. Its
  example is the specification of the case
  `validate-profile-lean-missing-tests`, and `TestStartExampleIsACase`
  keeps the two equal.
- `info.profile`, lean or full, full when left out. On lean the demands
  relaxed are exactly the tests `specarch derive` would write
  (`test_golden_missing` where the design gives the success,
  `test_case_missing`): warnings, not errors, in both validators, with
  one warning at the key under the new rule `profile`. Every other rule
  stays: the schema's required keys, the permission on every operation
  and command (fail-closed), `unsafe_integer` and the correctness rules.
  ADR-210 (proposed) gives the reasons, one per kept demand.
- Specification first: SA-108, ADR-210, `spec/design/commands/init.yaml`,
  the topic in `help.yaml`, `profile` in the Rule enum and the two test
  rules' descriptions, the key in the design schema and the `specarch`
  key's description, the source `spec-kit` widened to name its init
  command. Cases `init-writes-specification`, `init-lean-profile`,
  `init-dry-run`, `init-refuses-existing`, `init-usage-error`,
  `validate-profile-lean-missing-tests`,
  `validate-profile-full-missing-tests`,
  `validate-profile-absent-missing-tests` and
  `validate-profile-lean-permission-missing`, and `derive-lean-profile`,
  which runs the step help start promises; `capabilities-text` and
  `guide-order-of-work` recorded again. The conformance harness checks
  that the tree an init case writes validates; `TestDryRunWritesNothing`
  covers init, and the option and `--json` tests run it with `--dry-run`,
  since they run in the package's folder and init would write there. The agent guide's workflow has a step for init, and
  `AGENTS.md`, the README, `docs/conventions.md` (Profiles) and the
  roadmap follow.

Left out on purpose: relaxing `summary`, a response's `description`,
`primaryKey` or `permission` on lean. A permission left out would read
as open; the description is OpenAPI's own requirement; a required key
that depends on a root key would mean every definition of the schema
written twice. The meta-model version stays 1.0.0 with the new key, as
`restsOn` and the workflow step kinds were added. Nothing of the trial's
system is named here.

The specarch handoff mailbox was checked and is empty; nothing was
deleted.

## Long-running processes: processes, their rules, cases and documents (item 1682)

The owner asked for a design element for long-running processes, from
the comparison with Spec Kit and a capture of a deployment daemon with
both: SpecArch had to write the daemon as a job with `every` plus
commands, which demanded a permission and caller cases a loop with no
caller cannot have, while its restart, crash loop, signals and bad
configuration had no key and no test.

- `processes` in the design, keyed by camelCase name: `runs` (`always`,
  `scheduled`, `onDemand`), `schedule` or `every` on a scheduled process
  that runs no job, `jobs`, `configuration`, `signals` keyed by POSIX
  name, `exitCodes` as a command's, `restart` (`when`, `delay`, `limit`
  with `times` and `within`, `exceptExitCodes`), `health` and
  `monitors`. No permission and no role: the jobs a process runs keep
  their roles. `process:` is a test's subject, and a process test may
  expect `exit` as a command's.
- The rule `process` in both validators, the cases a process implies
  (`signal <name>`, `setting invalid <name>`, `secret missing <name>`,
  `exit <status>`, `restarted after a crash`, `crash loop given up`, the
  last two critical on their own), the draft reasons derive writes for
  them, and `specarch model` listing a process's jobs, settings and
  monitors and a test's process.
- The operations guide writes a Processes section and a daily checklist
  line per process; the technical specification a paragraph per
  process; the site and the traceability document read the section.
- ADR-211 (proposed), SA-109, three sources (systemd.service,
  systemd.unit, POSIX signal.h), cases `validate-processes-valid`,
  `validate-processes-refused` and `derive-processes`; four cases
  recorded again, since the list of design sections and of test
  subjects in their messages now names processes.
- `tools/fragment-schemas` lets an earlier design schema lack a section
  added since, so the 0.3 fragments are written as before.

Decided on the way: when work happens is said once, in a job's
trigger. A first draft let a scheduled process carry its own schedule
and refused one on its jobs, but a job's trigger is required, so no job
could have run under it; a scheduled process that runs jobs is now
started at each job's time and writes none, and only one that runs no
job writes its own. The name is processes, not services, because
service names the HTTP service a specification describes. Left out of
this step: generating code for a process.

Second step: `specarch extract systemd` and the example (commit after
f10210c4).

- `specarch extract systemd` reads `.service` and `.timer` units of one
  repository into processes, each value a unit states citing its line:
  the description, runs (scheduled with a timer, onDemand for a oneshot
  with none, always otherwise), `Restart=`, `RestartSec=`,
  `StartLimitBurst=` with `StartLimitIntervalSec=`, `KillSignal=` and
  `TimeoutStopSec=`, an `ExecReload=` that sends SIGHUP, `WatchdogSec=`,
  a timer's `OnUnitActiveSec=`, and a setting per variable
  `Environment=` sets, never its value. What a unit leaves to the host
  is asked: a restart with no limit, the exit statuses it names, a
  calendar expression (not cron, and read in the host's time zone), the
  settings' description, secrecy and type, an environment file. Every
  other key is a line and a could question; `ExecStart=`, `User=`, the
  ordering keys and `WantedBy=` are named as an implementation file's.
- The process rule's error on a scheduled process with no time, and on
  a restart with no limit, waits while an open must question asks for
  that key, in both validators, so the tree a reader writes is read
  whole with its questions.
- `examples/release-watcher/`: the unit files, the specification of the
  two processes and their jobs on the full profile with every derived
  test completed by hand, and its technical specification and
  operations guide, kept current by `scripts/regenerate.sh`.
- Cases `extract-systemd-reads-units` and `extract-systemd-not-a-unit`;
  `TestTimeSpan` and `TestUnitName` for the span and name rules.

Left out on purpose: launchd property lists and container restart
policies (a Compose `restart:`, a Kubernetes probe), which a later reader
can take the same way; and translating `OnCalendar=` into cron, which
would be a guess.

Third step, from the review of the first two:

- The reader's citation of an `Environment=` line on the process wrote
  the variables' values into the tree; it names the variables only, and
  an `ExecReload=` it does not recognise is a line without its command.
  The case's unit sets a token, and no value of the unit is in the tree
  it writes.
- Cases `validate-processes-must-question` and
  `validate-processes-should-question` show, in both builds, a missing
  time or limit waiting for a must question and an error under a should
  question; `merge-systemd-and-settings` shows merge keeping the
  processes and answering a setting's question from a document's tree,
  with `process` among merge's words for an entry.
- ADR-211 cites no sentence of Spec Kit; its context credits the trial.
