## An all-digit commit without quotes: the fixture quoted, the Swift build reads it as a number, a case shows it

An outside schema check of this repository's own specifications refused
`spec/tests/extract-go-handlers-changed/implementation/lockers.go.specarch-implementation.yaml`:
two handler records gave `commit: 1111111111111111111111111111111111111111`
without quotes, which YAML reads as a number where the implementation
schema asks for a string. Both values are quoted now; `extract go` takes
`commit` as raw text, so the case's output is unchanged. No other
all-digit commit, edition, version or id value was found in `spec/` or
`examples/`; the `maximum: 9007199254740991` lines are numbers by design.

Why neither build of `validate` reported it, BUG-032: no check reads the
file, as `spec.Find` stops at a folder holding `specarch.yaml` and so
never descends into `spec/tests`, and the case runs `extract go` alone.
Pointed at the file, the Go build does report both lines, since yaml.v3
reads an integer past `uint64` as a float, a number; the Swift build did
not, since its resolver tagged the forty digits `!!int`, `scalarValue`
found they fit neither `Int64` nor `UInt64` and returned them as a
string, which the schema's pattern accepts. The Swift resolver now tags a
decimal integer past 64 bits `!!float`, as yaml.v3 does, so it is a
number in both builds and the schema type error is printed at the line;
a 0x, 0o or 0b form past 64 bits stays text in both. The new case
`validate-unquoted-commit` gives one commit of forty digits and one of
seven, each without quotes, and expects the type error at each line and
exit 1; the Swift conformance test runs it too.

Nothing writes such a value: the extractor builds `commit` as a `!!str`
node, which yaml.v3 quotes when the text would read as a number (probed
with a forty-digit and a seven-digit value). The technical specification
and the test plan are regenerated for the new case. Checks: go vet, go
test, the Swift build and its 14 tests, both validators on `spec` and
`examples` with identical output, the fragment schemas, and the document
checks of the three CI loops. No dependency changed.

Not fixed, reported to the owner: `extract go` reads the `--implementation`
file without the schema check, so a record of the wrong type is taken
as read there; and the Swift build returns a 0x, 0o or 0b integer that
fits neither 64-bit width as text under the `!!int` tag, where the Go
build gets a plain string from yaml.v3, the same value under another
tag, which only the expression reader looks at.

## Encrypted operations and streamed files: handshakes and stream in the meta-model

Item 0979, for v0.7.1. dxlib serves most endpoints of its consumers
through an end-to-end encrypted envelope established by a pre-key
exchange (X25519 for the shared secrets, Ed25519 for the signatures,
AES-256-CBC for the body), and streams very large files in and out
without holding them. The specification had no word for either, so an
operation read from such a service showed a JSON body a client could
not send, and a file endpoint a field table.

Decided and built here, the meta-model first:

- `handshakes`, a section of the design, declares each key exchange
  once: `keyAgreement` (x25519, x448; RFC 7748), `signature` (ed25519,
  ed448; RFC 8032), `cipher` (aes-256-cbc, aes-256-gcm,
  chacha20-poly1305, OpenSSL's names), `establishedBy` (the operationId
  a client calls to perform it), `lifetime` and `uses`. An operation
  names the one whose envelope it travels in under `handshake`
  (ADR-145). The bytes on the wire stay with the stack: dxlib's
  `{i, d}` envelope and its endpoint types belong to the dxlib dialect.
- `stream: {direction: upload | download}` on an operation says the
  request body or the success response is a file passed through as it
  arrives; the media type and the binary string stay in OpenAPI's own
  `requestBody` and `responses`, and the largest download is the new
  `limits.maxResponseBytes` (ADR-146). An upload cannot travel in an
  envelope, since its body is the file; a download under a handshake
  has an encrypted request and a plain stream back, which is what
  dxlib's DownloadStreamV2 type does.
- Both validators gain the rules `handshake` and `stream`, with the
  same words, and derive the red case `expired handshake <name>` for
  every operation that names a handshake, as a token's expired case.
  Cases `validate-handshake` and `validate-stream`; requirement SA-77;
  sources rfc-7748 and rfc-8032.
- The design schema, the fragment schemas, the Swift embed and the
  stage maps of both builds carry `handshakes`; `docs/conventions.md`,
  `docs/techspec.md` and `docs/dxlib-lessons.md` say the new words,
  the last no longer setting the session key mechanism and the
  octet-stream shape aside as implementation.

The owner's standing rule for the private dxlib consumer this came from
holds: its code was read as reference only, nothing of it is in this
repository, and the fixtures are written from dxlib's public API.

Found on the way and not fixed here: the two validators kebab-case an
operationId with a run of capitals differently in the test names they
suggest (`uploadJSON` is `upload-j-s-o-n` in Go and `upload-json` in
Swift); filed as BUG-033, and the stream fixture avoids the shape.

## The generators serve the handshake and the streams

Item 0979, part three. The dxlib dialect of `generate openapi` writes the
endpoint type an operation's handshake and stream give it: the V2
envelope for a handshake of dxlib's primitives, the encrypted download
when it also streams one, an error at the operation for other
primitives, the upload type with a required octet-stream body of a
binary string and no parameter (dxlib reads an upload's parameters from
the X-Var header, which the meta-model does not hold), and the download
type with its success described and carrying no content, since dxlib's
reader takes a response's content only as a JSON object. The standard
dialect writes `x-specarch-handshake` and `x-specarch-stream`.

`generate go-dxlib` (`internal/gendxlib/transport.go`, `client.go`)
writes the exchange's handler for the operation the handshake names,
which must take `a0`, `a1`, `a2` and answer `i`, `b0`, `b1`, `b2` as
dxlib_module's pre-login does; the handshake's record, a `PreKeyStore`
with an in-memory store, and the two hooks dxlib calls over its
datablock, set in `Register`; a handshake past its lifetime or its uses
is refused when opened, which dxlib answers as the plain
`REFRESH_PREKEY`. An upload's body takes the request body as a reader
held to `maxRequestBytes` (`UploadStream`), a download streams through
`SendStream` with its media type and `maxResponseBytes` as constants.
A second file, `specarch_dxlib_client.go`, is a Go client with
`Handshake` and a method per operation that seals and opens the
envelope, streams an upload in and a download out; it is written for
every go-dxlib service, so the two existing goldens gain it. The tests
target writes the transport above the call and leaves it to the harness;
both UI targets refuse a page on such an operation at the page, and
`docs/roadmap.md` 5a lists the handshake in the screens as the next
build.

Round trip: `TestEnvelopeStreamRoundTrip` generates the vault fixture,
binds the generated service to a dxlib API through the generated
document, and drives the generated client: the handshake, an encrypted
call opened, a second envelope on the one-use handshake refused as
`REFRESH_PREKEY`, a 40 MiB upload streamed and hashed on both sides, the
same bytes streamed back, a refused download, and an encrypted request
answered with a 24 MiB stream. It runs against the dxlib checkout
`SPECARCH_DXLIB` names (`libraries/dxlib` at v1.128.0-6-g7308fc8) and
passes; CI skips it, as the compile test, without one. Cases
`generate-openapi-dxlib-envelope-stream` and
`generate-go-dxlib-envelope-stream`.

## The technical specification shows the handshake and the streams

Item 0979, part four. `document techspec` (`internal/generate/transport.go`)
lists the design's handshakes at the head of the runtime view, each with
its primitives, establishing operation, lifetime and envelopes, and what a
client does for it in five steps, so a client on any stack reads the
exchange without the code. An operation that names a handshake says it
travels in the envelope and which operation establishes it; its sequence
diagram notes the envelope and marks the request and the answer sealed.
An upload stream says it streams the request body in as a file, with its
media type and `maxRequestBytes`, in place of a body table; a download
says it streams the response body out, its success response reading the
file, streamed, with `maxResponseBytes` where declared; an encrypted
download says the file comes back outside the envelope. Case
`document-techspec-envelope-stream`, the vault again. `docs/techspec.md`
and the document command's design say the same.
