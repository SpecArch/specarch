## extract go follows a router into a method of a constructed value; extract documents keys an all-caps name as one word

Two defects in 0.6.0, reported from a project that extracts a
multi-module Go codebase. Issues #8 and #9.

Issue #8, serious: `extract go` wrote 0 operations for a module whose
routes are registered by a method of a struct another package's
constructor returns, in the shape `server := rest.NewServer();
server.RegisterRoutes(r)`, with `RegisterRoutes` doing `r.GET("/items",
s.List)` in `internal/api/rest`. Every route became a must question,
"registers GET /items on a router whose place the reader does not know
(... is given the router r, and the reader found no call that passes it
one whose path it knows)". Cause: the walk typed a name only from `T{}`,
`&T{}` or `new(T)`, so a value a constructor returned had no type, the
method the router was passed to was not found, and the method was later
walked as one given a router from nowhere. Fix in
`internal/extract/golang_routers.go`: a name assigned from a call of a
function or method of the module takes the type that function declares
for its result, in the one-value form and in `server, err :=
rest.Open()`; `ADR-081` says so. A call inside a closure, a command's
run function, needed nothing more, since the walk already descends into
function literals. Tests: `TestGoRouterPassedToMethodOfConstructedValue`
(constructor alone and with an error, two commands) and
`TestGoRouterPassedFromClosure` (a run function in a command struct),
both in `internal/extract/golang_test.go` with a `go.mod` written at
test time, as the handler test does, since a conformance fixture carries
no module file and cross-package names need the module path. Both fail
on the old reader and pass on the new.

Issue #9, small: `extract documents ARCHITECTURE.md` gave the source key
`a-r-c-h-i-t-e-c-t-u-r-e`, so two such documents collided at `merge`.
Cause: `kebab` put a dash before every capital. Now a capital starts a
word after a small letter or a digit, and inside a run of capitals only
the last does, and only when a small letter follows it: `ARCHITECTURE`
is `architecture`, `README` `readme`, `FSD-Login` `fsd-login`,
`HTTPServer` `http-server`, `userID` `user-id`. The same function names
an OpenAPI document's default key and the derived tests' names, so the
Swift validator's `kebab` in `Tests.swift` takes the same rule, and
both builds still print the same on `spec` and `examples`. Tests:
`TestKebab` in `internal/extract/tree_test.go`, and the conformance case
`extract-documents-upper-case-name`, recorded from a run of the built
binary. The design test count rises to 401.

Checks: go build, go vet, `go test ./...` with the conformance suite,
every `document --check` on `spec` and `examples`, swift build and
test, and validate on `spec` and `examples` in both builds with the same
output. No dependency change. The documents are regenerated.

Handoff: the request came through the queue's handoff folder, not the

## Caller context in the meta-model: the application, the calling service, the delegation chain and the audience

The owner's model of an authorisation decision has more inputs than the
role, the path and the method, and the estate's services call each other
on a person's behalf. `docs/caller-context.md` is the design for the
four inputs beyond the person (`sub`, 0.3 step 4) and the roles: the
application the person signed in through as a condition on a grant, the
calling service with grants of its own, the delegation chain with rules
over it, and the audience per hop. Nothing is built; `spec/` is
unchanged and no document is regenerated. The owner's seven questions
are at the end of the file, the recommendation first in each.

What the design takes, standards first:

- the application is a client of `kind: application` in the one
  `clients` object of ADR-096, since OAuth 2.0 (RFC 6749) has one word
  for a program a person signs in through and a service that acts;
  `roles` and `proof` become optional, a client with roles must have a
  proof, and a `service` with neither only acts for people. The
  condition is `through` on a role, keyed by permission beside `rows`,
  checked against the access token's `client_id` (RFC 9068, section
  2.2; RFC 8693, section 4.3). After a token exchange `client_id` names
  the last hop and no standard claim carries the application, so the
  check belongs to the service that accepts the person's own token, and
  a later hop narrows by chain; the design says so rather than
  pretending. OpenID Connect's `azp` is an ID token's claim and is not
  read;
- the calling service is ADR-096 already; the delta is `kind: service`
  with no roles, `client` on a grant in the permission table, and the
  machine-token confused deputy as a derived red case at every operation
  for people;
- the chain is RFC 8693's registered `act` claim, nested with the last
  actor outermost, in place of 0.3's `actor` string; the rule that the
  actor is not the subject is derived from the keyword, so the expression
  language needs no field access on a claim. ADR-097's rule for
  registered claims widens to the JSON Web Token Claims registry, with
  the list the validator ships. `via` on a token and on an operation
  lists the chains accepted, first hop first, every chain written out;
  two confused-deputy red cases (a service's own token, and a person's
  token requested by a service with no actor, RFC 8693's impersonation)
  are derived at every operation for people once a service is declared;
- the audience is `aud` with JSON Schema's `const` or `enum`, no new
  keyword, required on every token a service accepts (RFC 9068, section
  4; RFC 7519, section 4.1.3; RFC 8707; RFC 9700, section 2.3), with
  the replay red case; the rule is `token_audience` because `audience`
  is the estate's word for an element's readers.

Also in the file: where each keyword sits by the interface boundary's
test, the readers' bindings (`clientChecks`, `chainChecks`,
`audienceChecks`, after ADR-081) and the permission table's two keys,
the validator's rules, the techspec's one matrix with the application in
the cell and the clients as rows, the left-out table (`may_act`,
`scope`, sender-constrained tokens, wildcard chains, the application
past the first hop, `azp`), and five build items that amend 0.3's steps
3 and 4 before they are built. 0.3's left-out row on the roles or the
client in an expression is kept with a revised reason; its row on a
route both people and clients call is the estate's question 3 and this
design's question 5, recommended `callers: all`. `docs/meta-model-0.3.md`,
`docs/estate.md` (point 6) and `docs/roadmap.md` (section 5) point at
the file.

Left out of the public files on purpose: the estate's owner, its
modules, the names of its services, applications, routes and roles, and
the policy library it uses, which stays unnamed as `docs/estate.md`
leaves it.

Handoffs: the mailbox's two files belong to the estate item and are
left for it, as that item's entry says.

## Estate item 1: a dump committed outside the code's repository

Every dump (catalogue, route table, permission table and the three
code-facts dumps) takes an optional `repository`: the folder of the
code's repository from the root of the repository holding the dump,
which must be a gitlink there (ADR-098). The commit the gitlink records
is the reference: the dump's commit must be the last change to its path
at that commit, or the dump is refused as stale, naming the dump's
commit, the last change and the gitlink's commit. The code's checkout
must hold the reference's files under the path (the same tree object),
so a checkout moved ahead without touching the path reads as before and
one that changed it is refused with the `git submodule update` to run;
a plain folder, a gitlink not checked out and a gitlink commit the
code's history does not hold are refused with that reason. The edition
and `url` stay the code's, so the output is byte for byte that of the
dump committed beside the code. A dump without the key reads as before.

The six dump scripts source `tools/repository-key.sh`, which writes the
key after the opening brace when the dump file is in another repository
than the code's and refuses a dump file in a repository that does not
hold the code's. The conformance runner takes `repositories`, made in
order, so a later one records an earlier one as a gitlink. New cases:
`extract-router-dump-through-gitlink` (its expected tree is a copy of
`extract-router-writes-tree`'s and passes unchanged),
`extract-router-stale-gitlink` and
`extract-router-dump-repository-not-gitlink`; a unit test covers the
checkout checks. The extract design, `docs/extraction.md` and
`docs/estate.md` (point 1 built) say so; the documents are regenerated.

The owner's decisions on the estate plan's questions, given with this
item: implies and pattern rules; references as `<dependency>#/<pointer>`;
a route both people and clients call stays out of 0.3, the bypassed
check being the gate question; the readers inside the binary (item 8);
a reader for a standard workflow format and a printed table for a custom
one; a reader may write an implementation fragment; `ownedBy` on a
requirement. Caller context is designed in its own item. `docs/estate.md`
now states them as its decisions section, and `docs/reading-code.md` says
where a code-facts dump may be committed.

go build, go vet, go test ./... with the conformance suite, swift build
and test, and validate on `spec` and `examples` in both builds (the same
output, 0 errors) pass. `dump-routes.sh` was run end to end on a dump
in an outer repository and `extract router` read it; the catalogue and
code-facts scripts were checked with `sh -n` only, since they need
Podman, the Swift toolchain's reader build, Node or Dart. No dependency
change.

## extract go: a body decoded into a struct written in place (#10)

A handler that decodes its body into a variable declared with a struct
type in place (`var req struct{...}` with json tags, bound with

`requestBody`: `fieldSchema` had no case for a struct type, so the

is a type the reader does not find in the module's files", blocking

the tree did not have. `validate` then reported `question_block`
(points below a key that does not exist), and `merge` refused the tree.
Two such handlers in a service kept its whole go tree out of the merge.
Issue #10.

A second shape of the class came in while the item ran: a property typed
`map[string]any` got its should question ("it is a map ... which shape
does it take?") at `.../schema/properties/policy`, and the property was
never written. The handoff that reported it suggested writing the map as
`{type: object, additionalProperties: {}}`; the meta-model's schema
subset does not hold `additionalProperties` (validate reports "not a key
this object can have" for it, in both builds, and extract openapi leaves
it out as not held), so adopting it is a meta-model change, not a patch.
The map is written as `{type: object}` instead, the object whose
properties the should question asks for, with the Go type in the
question's text, and the question blocks the written property.

Three fixes. The struct type written in place goes through the same field
loop as a named struct (`structSchema`, split out of `fieldSchema`): json
tags, a nested struct in place, a pointer nullable, a slice an array, a
named struct of the module in place, the binding and validate tags, and a
field with no json tag printed and left out, named "the field Count of
the struct written in place" since it has no type name. `bodiesSnake`
counts its tags for the snake_case decision too, and `exprText` names a
struct type.

The second is a rule of every tree a reader writes, since the pointer was
not only this shape's: a reader asks at the place an element would have
had and then leaves the element out, so a map as a struct's only field
blocked `.../schema/properties` while the object had no `properties`, and
a dropped property's own questions (an int64's width, a slice's items)
blocked keys below the dropped one. `Tree.Write`, which extract and
merge both write through, now anchors every question's pointer: it is cut to the deepest element the tree has and at
most one missing key under it, the one the validator's `question_block`
allows, or to its section when the element is not written; two blocks of
one question cut to the same pointer are one. The design (every reader's
rules in `spec/design/commands/extract.yaml`) and `docs/extraction.md`
say so. The conformance runner now runs `validate` on the tree of every
extract case that exits 0 and fails the case on an error; all forty
existing cases passed already, so no expectation changed.

New case `extract-go-request-bodies` (gin; the struct in place with its
nested, pointer, slice, named and map fields and a binding tag, a
variable named `body` bound with `BindJSON`, a body of another module's
type, which now blocks `#/paths/~1imports/post/requestBody`, a named
struct whose only field is a map of any value, whose question blocks the
written `properties/policy`, and a struct whose only field is an
interface, which blocks the object's missing `properties`), and the unit

## Estate item 3: implies on permissions, and pattern rules in the permission table

A permission may now list `implies`: the permissions its holder holds
too, transitively (ADR-100, requirement SA-63). The validator refuses,
as the new rule `implies` at the entry, a name that is not declared,
`public` implied or implying, and a cycle, reported at every permission
on it with the shortest way round; both builds print the same output.
Every check of what a role grants counts the implications: the grants
check, separation of duties, workflow approvals, pickers, flows, the
role a derived "denied without" case picks, and merge's unchecked line.
The techspec's and the site's matrices write "through" and the permission
an implied one comes by, and the techspec lists what each permission
implies when one does; `generate go-dxlib` writes a role's privileges
with the implied ones after its own. The expansion is one function
(`internal/implies`) for the documents, the generator and merge, and the
same few lines in each validator build.

The permission table gains `rules`, beside `grants` and `gates`: a
role, a pattern, the methods (a list, or `*`) and the matcher, `colon`
or `brace`. `extract permissions` gives one permission per distinct
pattern and method pair, named by the plan's fixed rule, each implying
what its pattern and methods cover (the fewest implications that give
them all), and grants each role the permissions of its rows. With
`--routes` it reads the route table of the same repository too and
writes its routes as `extract router` does, under one code source at the
later of the two commits; each route takes the matching permission every
other match implies. An ambiguous route and a route no rule reaches are
must questions at the operation, a permission no route reaches a could
question, and one could question offers to rename the inferred names.

Decided here, as points the owner's decision 1 did not settle and the
decision record says why:
- The plan's naming rule gives the list and the read-one route of one
  collection the same name (`/v1/items` and `/v1/items/{id}` with GET
  are both `v1.items.get`). Names that meet are each made with their
  parameters' words too (`v1.items.id.get`); a name that still meets, or
  has a word that does not start with a letter, is a line and a could
  question, left out.
- Both matchers read `*` only as the whole last segment, the rest of the
  path after the slash before it; a rule with `*` elsewhere is a line.
- A rule reaches a route only when its pattern covers every path the
  route serves; one that reaches only some of them does not.
- The ambiguity question names the narrowest matches only.
- `--routes` writes the routes in the permissions tree, so it stands in
  for `extract router` on such a system.

New cases: `validate-implies`, `extract-permissions-pattern-rules` (a
`*` row beside a `get` row gives `v1.all` implying `v1.get`, each route
its one permission, with the ambiguous, closed and dead questions) and
`document-techspec-implies`, and unit tests for the coverage, the naming
rule and its collisions and the go-dxlib privileges. Every existing case
passes unchanged, and the lending desk's documents pass `--check`, its

`tools/permissions/dump-permissions.sh`, `docs/conventions.md`,
`docs/extraction.md`, `docs/generators.md` and `docs/estate.md` (point 5
and build item 3 built) say so; the documents are regenerated. Caller
context (item 0772) is untouched.

The design schema gains `implies` after the 0.6.2 release commit, so

## Estate item 4: documents in another language, and the small reader points

Built item 4 of `docs/estate.md`, Building (the queue named it item 5;
the dispatcher corrected it): point 3 and `--given-outside` of point
10. ADR-105 and SA-64 record it.

The words `extract documents` and merge's days comparison read by are a
vocabulary now, a YAML file per language (`docs/vocabularies.md`).
SpecArch ships `vocabularies/en.specarch-vocabulary.yaml`, embedded, and
reads it when nothing is named; it says exactly what the code said, so
the English run is byte-identical (`extract-documents-writes-tree` and
`merge-documents-days` pass unchanged). `extract documents` takes
`--language <tag>` (a shipped vocabulary) or `--vocabulary <file>`, then
prints a line naming it and writes `language` on the source;
`--given-outside` writes `givenOutside: true`; a leading row-number
column (`#`, `No.` or the vocabulary's word) is skipped in every table.
merge takes `--vocabulary`, repeated one per language, and reads a
requirement's days by its source's language; a language with no
vocabulary is one line per source, not compared. `language` on a source
is in the design schema, a BCP 47 tag by pattern, with the pattern named
in both validator builds.

Decisions the plan left open, for the owner to overrule:

- A word in two lists is refused within a group (the two priorities,
  the headers, the sensitivities, the types), not across the file:
  English's `required` is both a header and a yes word.
- Types are in the vocabulary (`types`), which the plan did not list,
  since a table in another language writes its types in it.
- The units are read by merge, the only place a unit matters; a unit
  counts there when its duration is whole days, so weeks now count in
  English too, and hours do not.
- The linking verbs and leading words merge reads a subject by are in
  the vocabulary as well.
- No JSON Schema for the file: the Go check is the one definition, and
  the validator does not read vocabularies.
- Exit 1 for a vocabulary that is not one this build reads, exit 2 for
  a tag with no shipped vocabulary and no file, and for a `--language`
  that differs from the file's.

The matchers write a word's edges out instead of RE2's `\b`, which is
ASCII only and never matched around a word such as prüfen.

New cases: `extract-documents-vocabulary` (the handbook in German with a
row-number column gives the English counts, priorities, fields,
sensitivities and questions), `extract-documents-vocabulary-word-twice`,
`extract-documents-language-not-shipped`, `merge-documents-days-vocabulary`
(three weeks read as 21 days), `merge-documents-language-not-given` and
`validate-schema-language-tag`. The extract and merge designs,
`docs/conventions.md`, `docs/extraction.md` and `docs/estate.md` (point
3 and build item 4 built) say so. No language beyond English is
shipped; the German file is the case's only. Nothing was left out for
