## extract go follows a router into a method of a constructed value; extract documents keys an all-caps name as one word

Two defects in 0.6.0, reported from a project that extracts a
multi-module Go codebase. Issues #8 and #9.

Issue #8, serious: `extract go` wrote 0 operations for a module whose
routes are registered by a method of a struct another package's
constructor returns, in the shape `server := rest.NewServer();
server.RegisterRoutes(r)`, with `RegisterRoutes` doing `r.GET("/items",
s.List)` in `internal/api/rest`. Every route became a must question,
"registers GET /items on a router whose place the reader does not know
(... is given the router r, and the reader found no call that passes it
one whose path it knows)". Cause: the walk typed a name only from `T{}`,
`&T{}` or `new(T)`, so a value a constructor returned had no type, the
method the router was passed to was not found, and the method was later
walked as one given a router from nowhere. Fix in
`internal/extract/golang_routers.go`: a name assigned from a call of a
function or method of the module takes the type that function declares
for its result, in the one-value form and in `server, err :=
rest.Open()`; `ADR-081` says so. A call inside a closure, a command's
run function, needed nothing more, since the walk already descends into
function literals. Tests: `TestGoRouterPassedToMethodOfConstructedValue`
(constructor alone and with an error, two commands) and
`TestGoRouterPassedFromClosure` (a run function in a command struct),
both in `internal/extract/golang_test.go` with a `go.mod` written at
test time, as the handler test does, since a conformance fixture carries
no module file and cross-package names need the module path. Both fail
on the old reader and pass on the new.

Issue #9, small: `extract documents ARCHITECTURE.md` gave the source key
`a-r-c-h-i-t-e-c-t-u-r-e`, so two such documents collided at `merge`.
Cause: `kebab` put a dash before every capital. Now a capital starts a
word after a small letter or a digit, and inside a run of capitals only
the last does, and only when a small letter follows it: `ARCHITECTURE`
is `architecture`, `README` `readme`, `FSD-Login` `fsd-login`,
`HTTPServer` `http-server`, `userID` `user-id`. The same function names
an OpenAPI document's default key and the derived tests' names, so the
Swift validator's `kebab` in `Tests.swift` takes the same rule, and
both builds still print the same on `spec` and `examples`. Tests:
`TestKebab` in `internal/extract/tree_test.go`, and the conformance case
`extract-documents-upper-case-name`, recorded from a run of the built
binary. The design test count rises to 401.

Checks: go build, go vet, `go test ./...` with the conformance suite,
every `document --check` on `spec` and `examples`, swift build and
test, and validate on `spec` and `examples` in both builds with the same
output. No dependency change. The documents are regenerated.

Handoff: the request came through the queue's handoff folder, not the
mailbox; nothing of it is in the repository. The mailbox holds two
files for other items (`audience-marker-and-items-owned-elsewhere.md`,
`extracting-many-modules-read-only.md`), left for them.

Open: the version. The code is unchanged since v0.6.0 and `specarch
version` still prints 0.6.0 while the specification is at 0.7.0-dev, so
the fixes can be cut as 0.6.1 from main; the owner decides how and when
to tag, and the binary in `~/go/bin` is reinstalled then.

Simulator: not needed, no app code.

## Caller context in the meta-model: the application, the calling service, the delegation chain and the audience

The owner's model of an authorisation decision has more inputs than the
role, the path and the method, and the estate's services call each other
on a person's behalf. `docs/caller-context.md` is the design for the
four inputs beyond the person (`sub`, 0.3 step 4) and the roles: the
application the person signed in through as a condition on a grant, the
calling service with grants of its own, the delegation chain with rules
over it, and the audience per hop. Nothing is built; `spec/` is
unchanged and no document is regenerated. The owner's seven questions
are at the end of the file, the recommendation first in each.

What the design takes, standards first:

- the application is a client of `kind: application` in the one
  `clients` object of ADR-096, since OAuth 2.0 (RFC 6749) has one word
  for a program a person signs in through and a service that acts;
  `roles` and `proof` become optional, a client with roles must have a
  proof, and a `service` with neither only acts for people. The
  condition is `through` on a role, keyed by permission beside `rows`,
  checked against the access token's `client_id` (RFC 9068, section
  2.2; RFC 8693, section 4.3). After a token exchange `client_id` names
  the last hop and no standard claim carries the application, so the
  check belongs to the service that accepts the person's own token, and
  a later hop narrows by chain; the design says so rather than
  pretending. OpenID Connect's `azp` is an ID token's claim and is not
  read;
- the calling service is ADR-096 already; the delta is `kind: service`
  with no roles, `client` on a grant in the permission table, and the
  machine-token confused deputy as a derived red case at every operation
  for people;
- the chain is RFC 8693's registered `act` claim, nested with the last
  actor outermost, in place of 0.3's `actor` string; the rule that the
  actor is not the subject is derived from the keyword, so the expression
  language needs no field access on a claim. ADR-097's rule for
  registered claims widens to the JSON Web Token Claims registry, with
  the list the validator ships. `via` on a token and on an operation
  lists the chains accepted, first hop first, every chain written out;
  two confused-deputy red cases (a service's own token, and a person's
  token requested by a service with no actor, RFC 8693's impersonation)
  are derived at every operation for people once a service is declared;
- the audience is `aud` with JSON Schema's `const` or `enum`, no new
  keyword, required on every token a service accepts (RFC 9068, section
  4; RFC 7519, section 4.1.3; RFC 8707; RFC 9700, section 2.3), with
  the replay red case; the rule is `token_audience` because `audience`
  is the estate's word for an element's readers.

Also in the file: where each keyword sits by the interface boundary's
test, the readers' bindings (`clientChecks`, `chainChecks`,
`audienceChecks`, after ADR-081) and the permission table's two keys,
the validator's rules, the techspec's one matrix with the application in
the cell and the clients as rows, the left-out table (`may_act`,
`scope`, sender-constrained tokens, wildcard chains, the application
past the first hop, `azp`), and five build items that amend 0.3's steps
3 and 4 before they are built. 0.3's left-out row on the roles or the
client in an expression is kept with a revised reason; its row on a
route both people and clients call is the estate's question 3 and this
design's question 5, recommended `callers: all`. `docs/meta-model-0.3.md`,
`docs/estate.md` (point 6) and `docs/roadmap.md` (section 5) point at
the file.

Left out of the public files on purpose: the estate's owner, its
modules, the names of its services, applications, routes and roles, and
the policy library it uses, which stays unnamed as `docs/estate.md`
leaves it.

Handoffs: the mailbox's two files belong to the estate item and are
left for it, as that item's entry says.

## Estate item 1: a dump committed outside the code's repository

Every dump (catalogue, route table, permission table and the three
code-facts dumps) takes an optional `repository`: the folder of the
code's repository from the root of the repository holding the dump,
which must be a gitlink there (ADR-098). The commit the gitlink records
is the reference: the dump's commit must be the last change to its path
at that commit, or the dump is refused as stale, naming the dump's
commit, the last change and the gitlink's commit. The code's checkout
must hold the reference's files under the path (the same tree object),
so a checkout moved ahead without touching the path reads as before and
one that changed it is refused with the `git submodule update` to run;
a plain folder, a gitlink not checked out and a gitlink commit the
code's history does not hold are refused with that reason. The edition
and `url` stay the code's, so the output is byte for byte that of the
dump committed beside the code. A dump without the key reads as before.

The six dump scripts source `tools/repository-key.sh`, which writes the
key after the opening brace when the dump file is in another repository
than the code's and refuses a dump file in a repository that does not
hold the code's. The conformance runner takes `repositories`, made in
order, so a later one records an earlier one as a gitlink. New cases:
`extract-router-dump-through-gitlink` (its expected tree is a copy of
`extract-router-writes-tree`'s and passes unchanged),
`extract-router-stale-gitlink` and
`extract-router-dump-repository-not-gitlink`; a unit test covers the
checkout checks. The extract design, `docs/extraction.md` and
`docs/estate.md` (point 1 built) say so; the documents are regenerated.

The owner's decisions on the estate plan's questions, given with this
item: implies and pattern rules; references as `<dependency>#/<pointer>`;
a route both people and clients call stays out of 0.3, the bypassed
check being the gate question; the readers inside the binary (item 8);
a reader for a standard workflow format and a printed table for a custom
one; a reader may write an implementation fragment; `ownedBy` on a
requirement. Caller context is designed in its own item.

go build, go vet, go test ./... with the conformance suite, swift build
and test, and validate on `spec` and `examples` in both builds (the same
output, 0 errors) pass. `dump-routes.sh` was run end to end on a dump
in an outer repository and `extract router` read it; the catalogue and
code-facts scripts were checked with `sh -n` only, since they need
Podman, the Swift toolchain's reader build, Node or Dart. No dependency
change.
