## Item 1771, round 2: a fresh environment that runs, and one name for the database's password

Summary: the review of round 1 found that the example's `fresh.sh`

cloud-init database host took its password under the image's variable

fixed, and a run of the generated script against a real PostgreSQL 16
found three more faults on the way, all fixed: the script never parsed,
the run's project name was refused by Compose, and a cluster built from

- The paths: `fresh.sh` sits in `<output>/<deployment>/` and names the
  sql and seed targets' folders from there (`../../migrations` in the
  example).
- The parse: `${1:?...}` held an apostrophe (`file's`) outside double
  quotes, which the shell reads as the start of a quoted string, so the
  script stopped at its last line. Each refusal is now a test with its
  text as one single-quoted word.
- The settings: the script read the env file by sourcing it, which reads
  a value as shell (a URL with `&` would have started a background job);
  it now exports each `NAME=value` line as it stands, as Compose reads it.
- The project name: `date +%Y%m%dT%H%M%SZ` gave capitals, which Compose
  refuses in a project name; it is `%Y%m%d-%H%M%S` now.
- The roles: on postgresql the script creates each role of the design,
  as the database role the sql target's policies name
  (`gensql.DBRole`, shared with the sql target), before the migrations.
  The migrations leave roles to the operator, as cluster state, and a
  fresh cluster has none.
- The database's password on a host: the operator writes

  The database's container no longer reads the services' secrets. The
  unit's check doubles its `$` (`$${v}`), since systemd expands `$` on a

- The ports: a fresh run publishes the deployment's own ports, so one
  run at a time fits on a host, not beside a running project of the
  deployment; the script and the docs say so and say where the suite
  reaches each server. Ephemeral ports lost: the suite reaches the

  than replacing them.
- The deployment names under `settings.deployments` that a file lacks
  are reported in name order; a unit test helper lost its unused
  parameter.
- Proof: a unit test runs a generated `fresh.sh` under a stub compose

- Docs: ADR-227, SA-121's acceptance and `docs/generators.md` say the

## Item 1771, round 3: the fresh run tears down on an interrupt too

Summary: the review of round 2 found that `fresh.sh` set its teardown
trap on `EXIT` alone, and dash, `/bin/sh` on Debian and Ubuntu, runs no
`EXIT` trap when a signal ends the shell. A Ctrl-C or a CI timeout
during a run left the project's containers and volume running, holding
the deployment's ports, so the next fresh run on that host failed. The
script now also traps `INT`, `TERM` and `HUP` and exits with the
signal's status (130, 143, 129), which runs the teardown in every shell.

- The generator: `internal/gendeploy/compose.go` writes the three traps
  right after the `EXIT` trap, before `compose up`; the golden case
  `generate-deploy` and the example's `deploy/local/fresh.sh` are
  re-recorded.
- The test: `TestFreshScriptTearsDownOnASignal` runs the generated
  script under `sh` and, where the host has it, `dash`, sends each of
  the three signals once `compose up` has started, and checks the exit
  status and the `down --volumes --remove-orphans` call. Without the
  traps all six cases fail: dash ends by the signal with no teardown, and
  bash on an interrupt carries on and exits 0.
- The real run, asked for by the review: the example's `fresh.sh` ran

## specarch compare: one comparison of alternative implementation files (item 1769)

`specarch compare <folder> <implementation>...` writes one table of
implementation files of a specification, one column each, from the
inputs each option pairs with an implementation by its name, the file
name without `.specarch-implementation.yaml` (ADR-232, SA-127).

- Inputs, all under `records/`, each kept in the output with its SHA-256:
  `--test-run <name>=TR-<n>` (the record of `log test-run`) or
  `--results <name>=<JUnit XML>` mapped as `log test-run` maps it, not
  both; `--scan`, grype's or osv-scanner's JSON, an osv-scanner group read
  into the CVSS v3.1 qualitative scale (source `cvss-3-1`, declared in
  `spec/specarch.yaml`), its None (0.0) written negligible as grype words
  it; `--measurements`, a JSON file with
  `buildSeconds`, `linesOfCode`, `deploySteps` and per requirement
  `latency` and `throughput` as `{value, unit, how}`.
- The table: the summary, one row per derived case that is chosen or
  covered (failed over passed over skipped), per measured requirement and
  quantity beside the requirement's statement, per library of the
  implementation files, per scan finding, the inputs and the gaps. A
  missing result is written `gap` in its cell and listed with the option
  or key that fills it; it never stops the command. An input given but
  wrong is refused with exit 1.
- Without `--out` the Markdown goes to standard output; with `--out` the
  command writes `comparison.md` and `comparison.json` and prints the
  `sources` entry, kind document, edition the SHA-256 of the JSON, by
  which a decision cites the comparison. `--json` holds it under
  `compare`.
- The derived cases come from a new `validate.CoveredCases`, beside
  `LeftOutCases`, so the comparison and the test plan count the same
  cases.
- Decisions taken here, for the owner's review: the inputs are paired on
  the command line rather than by a new key in the test-run record or a
  new record kind, which would change the record format in both validator
  builds; the comparison is cited as a document source rather than a
  record, since a record citation is for what a stakeholder said
  (ADR-220, ADR-221); latency and throughput are shown beside the
  requirement's words, not judged, since no element of the meta-model
  states them as a number; the measurements file is JSON, not YAML,
  because every YAML file under `records/` is read as a record; lines of
  code and deploy steps are measured values, since an implementation
  file's layout paths are not resolvable to files and its deployments
  give their steps in prose.
- Numbered ADR-232 and SA-127: ADR-227 to 231 and SA-121 to 126 are taken
  or in flight on other branches; landing may renumber.
- Cases `compare-two-implementations`, `compare-marks-gaps`,
  `compare-refuses-input-outside-records`,
  `compare-refuses-unknown-name`, `compare-usage-error`; Go tests for a
  decision citing the comparison, `--json` against `comparison.json`, the
  refusals and the CVSS scale. The guide by situation, in English and

- Go only: a command, not a validator change.

## Item 1775: a workflow keeps its as-is beside the to-be during a transition

Summary: a workflow may hold `asIs`, the process the business runs today,
in the workflow's shape without `asIs`; the workflow's own keys are the
to-be. Both validator builds check the as-is by the workflow's rules at
its own pointer under `/workflows/<name>/asIs`. The changes document
writes a section Transitions, and `specarch diff` a `transition` line per
part, with what moving from the as-is to the to-be adds, changes and
removes: the workflow's trigger, subject and messages, its steps, the
approvers and performers at each step, the operations it calls, the
forms and inboxes that rest on it, and the tests about it or about an
operation it calls or no longer calls. Every generator gets the to-be;
`specarch generate --as-is` gives each workflow's as-is in its place.
ADR-236 and SA-130 hold the design.

- The request named `variant: as-is | to-be` on two entries of one key.
  Done instead: the to-be is the entry and the as-is nests under `asIs`.
  Two entries of one name would break the loader's rule that a name is
  defined once in the whole specification (in both builds), would put one
  of the two outside the merged document where the schema, the reference
  table, diff and facts do not look, and would make a test's `workflow`
  and an inbox page's `workflow` and `step` ambiguous. Nested, each element
  has one pointer and every reader of workflows already reads the to-be.
- The schema has `asIs` on `workflow` and a definition `workflowAsIs`
  (description, trigger, subject, steps, emits, why, cites, origin), so an
  `asIs` inside an as-is is a schema error at its key.
- The derived cases and the success come from the to-be only; a
  permission only the as-is checks counts as used; the reference table of
  `specarch model` names the as-is's references too.
- `internal/transition` makes the list once for the changes document and
  diff, and `Select` gives the plug-ins the to-be or, with `--as-is`, the
  as-is. The site's BPMN and the sql check's plug-in request carry the
  to-be as well. The technical specification says a workflow keeps an
  as-is.
- Problem marks follow the variant: a plug-in given the to-be does not

  as-is is moved to the pointer the plug-in sees and one inside the
  to-be is not marked, while a diagnostic it answers is moved back to
  the as-is's line. Every problem not marked in an output is still in
  the problems file. Before this, `--as-is` marked a question about the
  to-be's third step on the as-is's third step. The as-is given to a
  plug-in keeps the workflow's own satisfies, audience and decidedIn.

## Item 1772: a test package for a customer's environment, and test scripts read into the specification

Summary: `specarch generate tests --package <environment>` writes a test
package, every test and every derived case no test covers as a request
to that environment's servers, and `specarch run` runs it from outside
and writes JUnit XML that `log test-run` maps back. `specarch extract
tests` reads Gherkin feature files and test sheets, complete or not, into
tests inferred from them, with a must question for each test's subject
and for each given, step or expected result the script leaves out;
`merge` keeps those tests, and once their questions are decided each
joins the package. ADR-233, ADR-235, SA-128, SA-131.

- The package (`internal/testpackage`, `cmd/specarch/testpackage.go`) is
  one file, `specarch-test-package.yaml`, built into `specarch` since it
  belongs to no stack. A case is a request (method, path with its path
  parameters, query, header and cookie parameters, JSON body), the
  caller's role, the records it needs and the status and body fields
  expected; or why it cannot run from outside (no request given, a
  command or a page, a handshake, a streamed file, a caller with
  properties, only the state after, or a denied case derive drafts no
  caller for). A derived case is drafted as `derive` drafts it and named
  as `derive` names it. No credential goes into it. A question that
  blocks only tests holds those tests back under `held`; any other
  question and the approval gate it as they gate every target.
- The runner is `specarch run`, not a script in the package: a script
  needs an interpreter on the customer's host and a JSON parser to check
  a body field, which a shell with curl does not have. Roles sign in
  with a `--callers` file of headers; a `--setup` program puts a case's
  records in place. A case without what it needs is skipped with the
  reason. The JUnit XML carries no time, so the same outcomes give the
  same file; each case's duration is on its progress line. `--dry-run`
  lists the requests it would make and makes none.
- `log test-run` maps a testcase whose name is a derived case's to that
  case's subject's element, so a package's results leave nothing
  unmapped; the reason printed for an unmapped testcase names this way
  too, which moved `log-test-run-writes-record` and the guides' quote.
- `extract tests` (`internal/extract/tests.go`): a Scenario or Example is
  a test, the Background's Given steps before its own; a Scenario Outline
  is a test per Examples row; a sheet's columns are found by the
  header's words. A test is red when the script says negative or its
  expected result names a refusal or an error. The subject question
  blocks the whole test, because a question on the `operation` key alone
  leaves the other ten subject keys reported missing (checked in a
  scratch specification); `names`, which needs a key pointer in both
  validator builds, is not used.
- The tree writer anchored a question's pointer only to elements held
  under a section key, so a pointer into `tests/<name>/test.yaml` was cut
  to the section `tests`; it now finds a test's own file.
- `merge` refused every test that was not a derive draft, so an
  extracted test could never be merged; it now keeps a test that cites a
  source of its tree whole, renamed with `-2` when an earlier tree has the
  name, with the questions that block only such tests.
- Cases: `generate-tests-package`, `run-package-skips`,
  `run-package-no-answer`, `run-package-servers`, `run-usage-error`,
  `log-test-run-maps-derived-cases`, `extract-tests-incomplete-scripts`,
  `merge-keeps-read-tests`; the listing cases moved with the new command.
  `TestTestPackageRuns` runs a package against a fixture HTTP service with
  a callers file and a setup program, checks a failure, and maps the
  results with `log test-run`; `TestExtractedTestJoinsPackage` follows a
  feature file through extract, merge, the held package, two decisions

- A review of the first commit found three gaps, fixed in the second: a
