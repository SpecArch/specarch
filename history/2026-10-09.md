## Extract 6/10, first part: a date moved by whole days

Step 6 of `docs/extraction.md` starts with what item 042's report found:
the expression subset had no date arithmetic, so the lending desk's
catalogue check `due_on = loaned_on + 14` could only become a `must`
question. The subset now has `duration("P14D")`, and a date plus or
minus it is a date (ADR-047), in both validator builds with the same
messages. `extract database` translates PostgreSQL's date plus a whole
number into it, so the check is now the constraint's expression,
`dueOn == loanedOn + duration("P14D")`, and only its message is left as a
question. `generate sql` writes it the way each engine keeps a date:
`+ n` on PostgreSQL and Oracle, `DATEADD` on SQL Server, `+ INTERVAL n
DAY` on MariaDB.

Choices the plan left open, taken by its rules and recorded in ADR-047:

- The days are an ISO 8601 duration, the form every other duration in
  the meta-model takes, rather than CEL's `"336h"`, which has no day
  because CEL has no date. A bare number added to a date is refused with
  the form to write, since a number names no unit.
- Only whole days written in place, the date first: a date has no time
  of day, and weeks, months and years depend on the calendar.

Conformance cases: formulas moving a date forward and back across a
month, a year and a leap day, evaluated to the expected dates (golden),
and a bare number, hours, weeks and a duration written first, each
refused (red), with the same output in both builds. Unit tests cover the
SQL dialects and the catalogue translation.

## Extract 6/10: the documents reader

`specarch extract documents` reads one Markdown document (ADR-048). Its
headings and numbered paragraphs become the clauses of one document
source at the commit that last changed the file. Every sentence that
makes a commitment becomes a requirement citing its clause, with a must
question for the requirements' kind. Every table headed Field gives an
entity's fields, with the sensitivity from its column or from a sentence
that calls the field personal or a credential. The lending desk manual
gives 11 clauses and 4 requirements and validates with no errors.

The plan's done line needed a link it did not give: the manual's "The
loan period is 21 days." is a requirement, the database's rule a check on
Loans, and merge matched only by name within a section, so a real merge
gave no question about the loan period. The owner chose a narrow rule
(option A of the question on item 046): merge compares a documents-side
requirement that gives one number of days with the code's checks that
move a date by days. When exactly one check has every word of the
statement's subject in its name, the check satisfies the requirement, and
a different number leaves the statement out with one must question
citing both. The lending desk's manual, database and router trees now
merge into one specification with that question, citing clause 3.3 and
the loans table, validated and byte-identical; CI repeats it.

Choices the plan left open, taken by its rules and recorded in ADR-048:

- A commitment is a modal (shall, must, will, should), a number followed
  by what it counts, a time of day, once or twice, or a time limit; a
  bare number such as an edition is not one. Priority is should for
  should and must otherwise; status accepted, as the hand-written
  procedure has it.
- A commitment whose subject is a pronoun is a question, the plan's
  "cannot place as one element".
- A parent heading is a clause only when it holds text of its own, so
  the outline lists leaves as docs/from-sources.md asks.
- The entity of a table takes its section's heading in PascalCase, as the
  database reader names tables, so the two meet in the merge. Its primary
  key is a must question; a field of a type the meta-model does not hold
  is left out with a line, as the database reader does.
- The source key defaults to the file's name; the requirement IDs use it
  in capitals (MANUAL-1).
- The question blocks only the requirement's statement, since a question
  is about one stage, and the check keeps the expression the code runs.

Conformance cases: extract documents on a handbook with every kind of
commitment, two tables of fields, a pronoun subject, an unheld type, an
unheld table and a code block (golden); a plain-text file refused (red);
merge of a code tree with three day checks and a documents tree with
three day requirements, one joined, one disagreeing and one matching
nothing (golden). Unit tests cover sentence splitting, commitments and
the days link.

## Extract 7/10: the OpenAPI reader

`specarch extract openapi` reads one OpenAPI 3.0 or 3.1 document, in
YAML or JSON, into a document source whose clauses are the JSON pointers
of its operations and component schemas (ADR-049). Each operation under
get, post, put, patch or delete is written under its path with its
operationId, summary, description, parameters, request body and
responses, citing its pointer. A component schema of type object is an
entity, and a string enum of snake_case values an enum. No library: the
reader takes a subset that yaml/v3, already a dependency, parses, and
JSON is read through the standard library with its keys kept in order.

`specarch merge` gains two rules. A question of one tree whose every
blocked key another tree gives is left out, with a line naming the tree
that answers it: the router asks what an operation answers and the
OpenAPI document says, and the document asks which permission an
operation checks and the router names it. A documents-side source none
of whose operations' paths the code side has is reported as a
placeholder; its operations are still compared, each a not-built
question, since the plan gives the refusal to the route-table gate.

The lending desk has an OpenAPI document,
`examples/lending-desk/sources/openapi/openapi.yaml`, with the four
routes and a renewal the router does not serve (the manual's clause
4.1). Merged with the router tree it gives the summaries, responses and
parameter values, takes the permissions from the router, and asks one
question, must, naming `/loans/{loanId}/renew`; validated and
byte-identical, and CI repeats it.

Choices the plan left open, taken by its rules and recorded in ADR-049:

- The OpenAPI file is a document source, on the documents side, so a
  path the router does not serve is a question and not a silent addition.
- A security scheme is not a permission, so every operation's permission
  is a must question that names the security the document gives; it is
  never written as public.
- 3.0's nullable, example and boolean exclusive bounds are written in the
  3.1 form. An integer or number with no width the meta-model holds (an
  int64 without bounds inside 2^53, a float) is a must question, with the
  format left out, rather than a guessed width.
- A property whose name is not camelCase is left out with a line, not
  renamed: a renamed property would generate a document that differs
  from the contract clients use. The handoff
  `metamodel-gaps-from-sources.md` asks for a name on the wire, a 0.2
  item.
- What the meta-model cannot hold prints a line and is left out: head,
  options and trace, cookie parameters, response ranges, headers and
  links, servers, tags, extensions, allOf, oneOf, anyOf, not,
  additionalProperties and a reference outside the document.
- The case `extract-not-offered` now runs `extract permissions`, the next
  source not built.

A review after the first commit (a84d25c) found two holes the lending
desk did not reach, fixed in a second commit: an object schema whose
properties are all snake_case was still referred to as an entity that
was never written, and a schema with properties or items but no type
was dropped. A component schema is now an entity only when one of its
properties can be held, and properties or items with no type are read
as an object or an array, as JSON Schema applies those keywords.

Conformance cases: extract openapi on a 3.0 document with every kind of
thing left out and asked (golden); a Swagger 2.0 file refused (red);
merge of the lending desk's OpenAPI and router trees, with the answered
questions left out and one not-built question (golden); merge of the
router tree with a template's sample document, reported as a placeholder
(golden). Unit tests cover the 3.0 rewrites, the widths and the JSON
reader.

go vet, go test, swift test (14 pass), validate in both builds with the
same output (0 errors, 22 warnings, 5 open questions), and
`document --check` pass. No dependency change. The handoff
`extract-request.md` stays in the mailbox until step 10; the new
handoffs `metamodel-gaps-from-sources.md` and `ui-generator-request.md`

## Extract 8/10: the permissions reader

`specarch extract permissions` reads roles and the permissions each
grants from a permission table, a format SpecArch defines as it does the
route table (ADR-050): the version, the folder the check is built from,
the commit that last changed it, every grant as a role and a permission,
and every check that runs only when a setting is present, by the check's
name and the setting's. `tools/permissions/dump-permissions.sh` runs the
project's own printer in a committed folder and wraps what it prints.
Each role and each permission granted is written with a citation; their
descriptions are must questions, and each declared gate prints a line and
is a must question blocking the roles. `specarch merge` now leaves out a
question whose every blocked key a question kept before it blocks with
the same priority (the router and this reader both ask what the
permissions allow), and, where the code side has operations, reports a
permission a role grants that nothing checks.

The owner's decision: the plan did not say how a reader of data sees a
check that a setting switches off, which is code. Asked with two
options, a reader of the seed SQL and the check's Go code, or a table
the project prints itself with the gates declared; the owner chose the
printed table (B). Its cost, written into ADR-050: a gate the printer
does not declare is not found.

The lending desk's roles moved from the Go map `lending/roles.go` to a
`roles` and a `role_permissions` table (`migrations/002_roles.sql`)
filled by `seeds/001_roles.sql`; its check, `lending.Allowed`, reads them
with `lending/grants.sql`, and its printer, `cmd/permissiontable/print.sh`,
runs the migrations and the seeds in a disposable PostgreSQL under Podman
and runs that query (1334b2b). The catalogue and route table were made
again at that commit, and the permission table added (3a7c660). Its one
role and three permissions come out validated and byte-identical; merged
with the database and router trees, the permissions question is asked
once and no grant is unchecked. The database and router merge still
gives its eight must questions, and the whole merge the 21 against 14
days question; the step 4 text names the new commit.

Choices the plan left open, taken and recorded in ADR-050:

- A grant nothing checks is a line of the merge, not a question, since
  only the merge sees roles and operations together and such a grant
  lets no one do what the code does.
- The roles tables stay entities in the database reader's tree.
- A role whose name is not kebab-case, a permission that is not a
  permission name and a grant of public print a line and are left out,
  and so is a role left with nothing to grant.
- The case `extract-not-offered` now runs `extract workflows`, which
  waits for meta-model 0.2.

Conformance cases: extract permissions with every kind of thing left out
and a gate (golden); a grant listed twice refused (red); merge of the

## An ungranted permission is no longer hidden by its missing description

finding came from the merge step (044), where no issue had been opened
yet. In both validator builds, a permission no role grants and with no
description gave no error. `permission_ungranted` sat at the same path as
the schema error "description is missing", so it was dropped as an echo
of it, and a must question blocking the description then covered the
schema error. A tree written by `extract router` has exactly this shape.

- A missing key no longer counts as the cause of other errors at the
  object that lacks it: it says nothing wrong about what the object does
  hold. Other schema errors still drop their echoes as before.

  others were to make the error uncoverable, so router trees could not

  grants each permission, blocking each permission itself, and a must
  question that blocks a permission covers its `permission_ungranted`.
  It is listed as covered and holds up approval and generation like any
  open must question. A question that blocks only the description does
  not cover it. ADR-017, ADR-044, the extract command and SA-5 say so.
- The lending desk's router tree now has 8 questions and its merge with
  the database 9; the CI check counts 9.

Conformance cases: `validate-permission-ungranted-without-description`

## Extract 9/10: the pages reader

`specarch extract pages` reads a file-system router's root folder, such
as a Next.js `app` folder, from the files git tracks there (ADR-057).
Every folder holding `page.tsx`, `page.ts`, `page.jsx` or `page.js` is a
page; a folder in parentheses is a route group and adds nothing to the
route, and `[name]` is the parameter `{name}`. The page is named after its
route in kebab-case, a parameter as `by-` and its name, the root's page
`root`. Two folders that give one route are refused. A catch-all segment,
a parallel route, an intercepting route, a private folder, another page
file such as `page.mdx`, and a route handler each print a line and are
left out. No printer is needed, as it is for a router built in code: in a
file-system router the tracked folders are the route table.

A page whose folder holds `page.schema.ts` takes its content from it. The
file is read in the subset of TypeScript that is also JSON5, the form the
TypeScript generator of ADR-051 writes: imports, comments and one
exported object literal, with `satisfies` and a type after it. The parser
is written in the package, with no dependency. Its keys named as the
design's page keywords (kind, title, entity, permission, columns,
compactColumns, fields, sections, filters) are taken; `source` and
`submit` are named in the question that asks for them, since the
operations they name are the router's; every other key, a value that is
not a literal and a file outside the subset print a line. An entity a
schema names is written by name, with the fields the pages show each an
empty mapping, and a must question asks its primary key and their types.
What no schema gives, and every page's permission, is a must question,
and so are each permission's description and, as the router reader now
asks, the role that grants it.

Two changes beyond the reader, both found when its first output did not
validate:

- `validate`, in both builds: a must question that blocks a field known
  only by name, an empty mapping, now covers everything under it, as it
  already did for an entity. Before, a pointer deeper than an element
  counted only as a key, so a field with no type still reported its
  missing `type` and `$ref`. `docs/conventions.md` already said an
  element known only by name is an empty mapping blocked by pointer; it
  now names a field as one.
- `merge`: an element a tree writes only as an empty mapping is not
  given, so a tree that gives it with content answers the question. The
  database tree now answers the pages tree's question about the loans
  entity's key and its fields' types.

The lending desk gains `examples/lending-desk/sources/web/app/`: a root
page, a route group `(desk)` with a lending form and a member's loans at
`/members/{cardNumber}/loans`, whose schema names the `Loans` entity, the
permission `loans.read` and four columns. It sits beside the code folder,
not inside it, so that the route table and the catalogue, which name the
code folder's commit, stay current. Its three pages come out validated
and byte-identical; merged with the database tree, the entity's question
is answered and the permission is asked once with the router's. CI runs
both twice.

Choices the plan left open, taken and recorded in ADR-057:

- The schema's keys are the design's own page keywords, since without the
  ui-components idiom SpecArch knows no library's names; a schema that
  names them otherwise is read as giving none, with a line per key.
- A page's title and a section's title are read as written.
- A compact column that is not a column, and a key a page of its kind
  cannot hold, print a line and are left out.

Conformance cases: extract pages on a tree with every kind of folder and
file left out, a schema outside the subset and a generated page; two route
groups giving one route, refused; validate covering a field known only by
name; merge answering the pages tree's entity question from the
database tree. Checks: go vet, go test, swift test, both validators the
same on the new validate case, document --check, validate on `spec/` and
`examples/`. No dependency change. Left out of the public files: nothing
came from a handoff for this step; `extract-request.md` stays in the
mailbox until step 10.

## Meta-model 0.2, step 10: a schema per fragment file

A file under a stage folder holds only some sections, and an editor
checking it against the design schema, which describes the merged
document, reported the root keys and the other files' sections as
missing. Each kind of fragment now has a schema of its own:
`schema/specarch-fragment-<stage>-0.1.schema.json` for the requirements,
design, deployment, commissioning and operation folders (that stage's
sections and `questions`), `specarch-fragment-test-0.1.schema.json` for
`tests/<name>/test.yaml`, and `specarch-fragment-questions-0.1.schema.json`
for a file directly under `tests/` or `implementation/`. Per stage rather
than per section, because a file may hold several sections of its stage.

`tools/fragment-schemas` writes them from the design schema: it copies
each section's definition and the `$defs` it reaches, byte for byte in
the design schema's own key order, so a keyword is defined once. It reads
the section-to-stage map from the loader (`internal/spec`), so a section
added there and to the design schema lands in its stage's schema with no
hand edit, and takes the version from the design schema's `specarch`
constant, so step 11 renames the files by running it. It also writes the
hint line on every fragment of `spec/` and both examples. `go test ./...`
fails when either is not current, and CI runs `-check` as a step of its
own to name the fix. The test also validates every fragment against the
schema its hint names (521 files, all seven schemas), and holds each
schema to refuse what the loader refuses in one file: a section of
another stage, a root key, and a key a test does not have.

The hints in this repository's trees are relative paths
(`../../../schema/...`): the trees are written against the schemas beside
them, and a tag URL would name files no tag holds yet. A project names
them at the tag its root file names (`docs/conventions.md`, The tree).

What one file cannot show stays `specarch validate`'s: a reference to
another file, a name defined twice, a sub-folder holding a second
section, and a required key an open must question blocks. The lending
desk's LEND-4 has no statement while Q-1 is open, so an editor marks it
missing; the test excuses only such a key, as `validate` does. The owner
chose this over dropping `required` from the fragment schemas or writing
a statement before Q-1 is answered.

No ADR: ADR-052 already takes a schema per fragment as step 10, and the
parallel 0.2 steps are numbering theirs. The validator does not change,
so the Swift build does not either. `specarch extract` and `merge` still
write the hint on the root file only; their trees' fragments get none
yet, since a tree they write sits outside this repository and would need
the tag URL.

Every other 0.2 step that changes the design schema now has to run
`go run ./tools/fragment-schemas` before it lands, or `go test` fails.

go vet, go test, swift test (14 pass), validate in both builds with the
same output (0 errors, 22 warnings, 7 open questions), `document --check`
for every target pass. No dependency change.

## Meta-model 0.2, step 6: child rows

A form now edits the records of a one-to-many relation of its entity as
rows under it: `childRows` on a page, each entry a `relation`, a
`title`, the `fields` of the relation's target shown in a row, a
`maximum` number of rows and `lockLoadedRows: true` when the rows loaded
with the record cannot be changed or removed. It is an addition to the
0.1 design schema, built in both validator builds with the same output.

- The rule `page` refuses child rows on a page that is not a form, a
  relation named twice, a relation the form's entity lacks, and one that
  is not one-to-many; `field` refuses a field the relation's target
  lacks, naming that entity, which is the plan's red case of a child row
  over an entity the relation does not reach.
- A child row's fields count as fields shown for the accessibility
  check, so a row field without a title is reported like any other.
- A maximum gives the form the derived case `<relation> with more than
  <maximum> rows`, occasional as every above-maximum case is, and
  written when the page is at stake in a requirement that names a harm.
- The techspec's table of pages lists each form's child rows with their
  fields, maximum and lock.
- The library-lending example gains `member-loans`, a form that loads a
  member's loans locked and adds up to six rows, the open loans the
  extended tier allows, submitting to the new `lendCopies` (all copies
  or none), with the tests of both; its OpenAPI document is generated
  again. The derived case `loans with more than 6 rows` is
  `member-loans-six-rows`.
- Conformance case `validate-child-rows`.

Decided here, from the plan: only a one-to-many relation takes child
rows, since a many-to-one or one-to-one relation holds one record and
the rows of a many-to-many relation are records of its join entity;
allowing more later breaks no file, narrowing later would. The maximum
counts loaded and new rows together, as a row count does on a form.
Only the over-maximum case is derived, as the plan says; a locked row
being changed is left to the stack's test until a request asks for it.
Whether rows are edited inline or in a dialog is the stack's.

The handoff `ui-generator-request.md` asks for child rows; it stays in
the mailbox, since its other asks are later steps. The fragment schemas
and the new files' hint lines are written by `tools/fragment-schemas`.

go vet, go test, swift test (14 pass), validate in both builds with the
same output (0 errors, 22 warnings, 7 open questions, all in the lending
desk), `document --check` and `fragment-schemas -check` pass. No
dependency change.

## Meta-model 0.2, step 1: separation of duties

`separationOfDuties` is in the design schema: named sets of two or more
permissions with a cardinality, at least 2 and 2 when left out, after
the static separation of duty of ANSI INCITS 359 (ADR-053). Both builds
check it under the new rule `separation_of_duties`: a set naming a
permission that is not declared, or `public`, a cardinality above the
number of permissions the set names, and a role granting as many of the
set as its cardinality are refused. A cardinality below 2, too few
permissions and a repeated permission are schema errors. The rule, the
algorithm `separationOfDuties`, SA-5's acceptance and
`docs/conventions.md` say so; the fragment schemas are regenerated.

The techspec's cross-cutting chapter has a table of the sets with the
smallest combinations of roles that together reach each, as roles never
to be given to one person. The library-lending example gains
`loans.writeoff`, a `head-librarian` role that holds it, and the set
`lend-and-write-off`; its techspec lists librarian with head-librarian.

Two things beyond the plan's words. A cardinality above the number of
permissions a set names is refused too, because such a set could never
be broken and is almost surely a mistake. The plan's example permission
`loans.writeOff` does not match the permission name pattern (lower-case
dotted words), so the plan and the example use `loans.writeoff`.

Left out: the workflow check (no role grants both a trigger's and its
approval's permission when one set holds the pair) waits for step 3, as
workflows are not on main yet. The handoffs in the mailbox were read;
neither is processed in full by this step, so both stay.

The conformance case `validate-separation-of-duties` gives the same
output in both builds. go vet, go test, swift test (14 pass), validate
on `spec` and `examples` in both builds with the same output (0 errors,
22 warnings, 7 open questions), `fragment-schemas -check` and every
`document --check` CI runs pass. No dependency change.

## Meta-model 0.2, step 2: task pages

A page of kind `task` submits to an operation without loading a record,
for sign-in, a second factor, a password reset or an e-mail confirmation
(ADR-056, step 2 of `docs/meta-model-0.2.md`). It is an addition to the
0.1 design schema: `entity` is now required only of a list, a form and a
view, a task requires `submit`, and a task's `onSubmitted` is keyed by
status, each a page event.

Both builds check it (rule `page`, and `flow` for where an answer leads):
a task naming an entity, a source, columns or filters; a field that is
not a property of the submit operation's request body; a required body
property left out; an operation that takes no body; and an `onSubmitted`
status the operation does not answer. `with` on a task's answer takes
the route parameters from the body of that response. A failed state of
a task may name its field, as a form's may. A flow's `submitted` step on
a task leads on when any of its answers leads to the next page. The
derived cases are one per answer: the first success is the golden case,
each other success is `answered <status>`, and each problem type is
`fails with <problem>`, states or not. The techspec's screen flow draws
an edge per status, and its pages table says what a task submits to.

Two choices the plan left open, recorded in ADR-056: only success
statuses (2xx) key `onSubmitted`, since a problem's message already has
its place under the failed states; and a flow step matches any answer,
since which answer comes is the server's.

`extract pages` now reads `kind: task` from a schema file: it writes a
task page, leaves out an entity the schema names with a line, and asks
for the operation it submits to rather than for an entity (ADR-057). It
also declares `public` when a page schema names it, as open to everyone,
instead of leaving a tree that refers to an undeclared permission; that
was a fault of the reader that a sign-in page hits first.

The library-lending example gains `signIn` (POST /sessions, public, 200
and 401 `sign-in-refused`), the sign-in page leading to the members
list, and five tests for them; its OpenAPI document is regenerated.
New conformance cases: `validate-task-pages` (red, the same output in
both builds) and `extract-pages-task`. The design fragment's schema is written again from
the design schema (`tools/fragment-schemas`). Three cases' expected output
follows the new wording of messages that now name a task.

Seen, not changed: `specarch derive` names a page's golden draft and its
submit operation's golden draft alike when the page is named after the
operation (`sign-in-succeeds` for both), keeps the first and skips the
other.

The handoffs `metamodel-gaps-from-sources.md` and
`ui-generator-request.md` stay in the mailbox: this step answers one
section of each. go vet, go test, swift test (14 pass), validate in both
builds with the same output, and `document --check` pass. No dependency
change.

## Meta-model 0.2, step 3: workflows

`workflows` is a design section: a request that finishes after people
approve it, as a sequential subset of BPMN 2.0. Each workflow names its
trigger operation, which answers 202, the entity that holds the request
while it waits, and its steps in order: an approval (a user task with
its approver roles, the permission it checks, a deadline and what the
deadline does) or an operation step (a service task). The rule
`workflow`, in both builds, refuses a trigger that is not an operation
or does not answer 202, a subject that is not an entity, an approver
that is not a role or does not grant the approval's permission, an
approval that checks the trigger's permission, a deadline of zero, an
operation step naming no operation, an escalation to a step that is not
a later approval, and two steps of one name. A test may name a workflow
as its subject. A workflow derives the approved path, `refused at
<step>` and `approval without <permission>` (frequent), `deadline passes
at <step>` and `requester approves own request` (critical on their own,
whatever the harm). The techspec draws each workflow in the runtime view
as a flowchart with the deadline on the edge it takes.

Spec first: SA-47, the rule `workflow`, the document command's
techspec text, and two conformance cases, `validate-workflow` (twelve
`workflow` errors and one `permission_undeclared`, the same in both
builds) and `validate-workflow-valid`; `validate-flows` and
`validate-test-subject` re-recorded for the subject list that now names
workflow. The library lending example gains the fee waiver: LIB-8, the
permissions `fees.request` and `fees.approve`, the role
`desk-supervisor`, the entity `FeeWaiverRequest`, the operations
`requestFeeWaiver` (202) and `waiveFee`, and fourteen tests completed by
hand. `specarch derive` on the example writes the workflow's five
cases.

Choices made while building it:

- The owner decided (item 056) that the check "no role grants both the
  trigger's and the approval's permission when a separation-of-duties
  set holds the pair" waits for step 1: whichever of steps 1 and 3
  lands second adds it, with its red case in both builds. Step 1 landed
  first, so this step adds it under `workflow`, whatever the set's
  cardinality; with a cardinality of 2 the role is also refused under
  `separation_of_duties`. `validate-workflow` gains the role `clerk`
  and a set of three for its red case, twelve `workflow` errors in all.
- `onDeadline` is `refuse` or `escalate`, and an escalation names its
  step under `escalateTo`, which the schema requires with `escalate`
  and refuses otherwise: one key, one shape.
- An approval's undeclared permission is reported as
  `permission_undeclared`, as every other use of a permission is,
  rather than as `workflow`; the plan put it under `workflow`.
- LIB-8 names no harm. The five workflow cases are chosen without one,
  and a harm would have made the two new operations critical and
  brought a boundary test for every field.

Left out on purpose: nothing names a real system; the fee waiver is the
generic library's.

The fragment schemas are written again from the design schema
(`tools/fragment-schemas`), and the new fragments carry their hint line.

go vet, go test, swift test (14 pass), validate in both builds with the
same output (0 errors, 22 warnings, the lending desk's), `document --check`
and `fragment-schemas -check` pass. No dependency change.
## Meta-model 0.2, step 5: page elements

A page can now say the elements every back-office screen uses: a field
picked from a list of another entity's records, an action offered only
in some states, a confirmation that asks for a reason, a field read-only
or hidden, rules across a form's fields, and a field typed twice. Each
is an addition to the 0.1 design schema, checked the same way in both
validator builds, with its derived cases and a row in the techspec's
new table of page elements (ADR-058).

- `pickers`, on a form, keyed by the field. The record's entity is the
  target of the many-to-one relation whose `via` is the field, so the
  page does not name it a second time; `source` must be an operation
  whose `listOf` names that target; `shows` and `fills` name the
  target's fields, and a fill must keep the type. A role that may open
  the form but not call the source is refused. The plan's word was
  "lookup", but `lookup` already names how an encrypted field is found
  by its hash, so the key is `pickers`.
- `when` on an action, an expression over the record it acts on; a form
  that creates a record has none, so `when` there is refused.
- `reason` on an action with `confirm`: a string property the
  operation's request body requires.
- `fieldConditions`, on a form or a view: `readOnly`, `readOnlyWhen`,
  `hiddenWhen`. The plan speaks of a field read-only or hidden "by mode
  (create, edit, view)". A SpecArch page is one mode already (a form
  without `source` creates, with one edits, a view shows), so there is
  no mode keyword: a field hidden in a mode is one that page does not
  list, and one read-only in it is `readOnly` there. A mode list on a
  field would be a second way to say which page shows it.
- `checks` and `enteredTwice`, on a form.
- New rules `picker`, `action` and `form_field`; expressions use the
  expression rules and must give true or false, never null.
- Derived cases: `picker <field> finds nothing` and `<label> not
  offered` (occasional), `<label> without a reason`, `violates <check>`
  (one per way it can be false) and `<field> entered twice differently`
  (frequent). Rows added to the table in `docs/conventions.md`.

The library-lending example: the loan form picks its member from
`listMembers` and its book from `listBooks`, which now pages
(`listOf`), so its generated OpenAPI answers a page of books. Members
have a status, `active` by default, and the members list offers
Deactivate only while `status == "active"`, asking for a reason sent to
the new `deactivateMember`. The SQL generator wrote `0002_expand.sql`
for the column; the UI generator leaves the action out, since it sends
no request body yet (the UI generator's own step). Tests were added for
every new case of the example.

Conformance: `validate-page-elements-unresolved` (every red check, 30
errors, the same output in both builds) and `derive-page-elements`
(derive writes the five new cases). Checks across fields are on forms,
as the plan's step 5 says; a task page (step 2) refuses them for now,
which is open for the UI steps to settle.

go vet, go test, swift test, validate in both builds with the same
output, and `document --check` pass. No dependency change. Nothing from
a handoff was copied in; both handoffs stay in the mailbox.

task pages, workflows): the rule enum keeps `workflow` before `picker`,
`action` and `form_field` in the design, Go and Swift, the techspec
generator keeps both its workflow and page-element functions, and the
documents and fragment schemas were written again from the merged
specification. Every check passes again on the merged tree.
