# 2026-10-11

## Failures name their real reason

The owner decided that no tool here hides why something failed, and that
each says what it is doing; the audience is technical. Most of specarch's
messages already named the file, the reason and what to do. This pass
fixed the places that dropped an error or reported the wrong one:

- validate (Go and Swift): a `tests/<name>/test.yaml` that is there but
  cannot be read was reported as missing; it is now reported at the file
  with the reason, and only a file that is not there says it is missing.
  A YAML file under `tests/` or `implementation/` that cannot be read was
  reported as a file that should hold only questions; it now says it
  cannot be read, and why. A project `idioms/` folder that cannot be read
  was skipped without a word; it is now a layout problem. New case
  `validate-layout-test-file-unreadable` (test.yaml is a folder, so the
  read fails with "is a directory" in both builds; the Swift `readFile`
  now gives that text itself).
- The Swift CLI's "cannot read" for an implementation file now gives the
  reason, as Go does; Go's CLI lines give the plain reason without the
  repeated "open <path>:" prefix, as Swift does.
- generate: files in the output folder that could not be read, and an
  idiom override or project idiom that could not be read, were dropped
  and the plug-in went on without them; each is now named on standard
  error with the reason and what the plug-in is not given. A plug-in that
  stops now names its path, the exit status, the target and the
  specification; one that answers with something other than JSON shows
  the first 400 bytes of what it wrote. When a run takes more than one
  plug-in or output folder, each step prints "N of M: running <plug-in>
  for <specification> into <folder>".
- document html: a workflow diagram or screen preview that could not be
  made left the site without it and said nothing; it now says so on
  standard error, and the site's screen section gives the reason.
- diff: an unreadable folder was always reported as "no such file or
  directory"; it now gives the real reason. A version that is not a
  semantic version made diff ask for `records/releases/0.0.0.yaml`; it
  now fails the version check naming the version and the folder (design
  `commands/diff.yaml`, new case `diff-version-unreadable`).

Checked: go build, go vet and go test ./... pass; swift build and swift
test pass, both builds print the new cases' output; specarch validate on
`spec` and `examples` gives 0 errors, as before. `docs/techspec.md`,
`docs/testplan.md` and `docs/traceability.md` were generated again; the
standard error of `commands/generate.yaml` and `commands/document.yaml`
names the new lines.

Left for later: the `readers/` scripts (JavaScript, Dart, Swift) and the
`tools/` programs have their own output and were not reviewed in this
pass. The commands other than generate finish in under a second, so they
get no step counter. Problem marks skip a file that cannot be read
without a message of their own; the loader already reports that file.
No secrets reach messages: extract reads dumps, not live databases, and
settings that look like credentials are named, never given a value.

Handoffs: none processed; the two in the mailbox stay for their items.
Simulator: not needed, no app code.

## Meta-model 0.2

Step 11 of `docs/meta-model-0.2.md`, decided in ADR-055: the design schema
is `schema/specarch-design-0.2.schema.json` and reads files that say
`specarch: "0.1"` or `"0.2"`. In a 0.2 file a test `specarch derive`
would write and nobody has is an error; a 0.1 file keeps those as
warnings and gets one `meta_model_version` warning at its `specarch`
line, until 1.0. `spec/`, both examples and everything extract and merge
write are on 0.2.

- Which missing tests are errors: exactly the ones derive writes, so that
  derive leaves a 0.2 tree with no test errors. That is a chosen case no
  test covers (`test_case_missing`) and a subject with no golden test
  when the design gives its success (`test_golden_missing`). A subject an
  open must or should question holds up stays a warning, as derive
  leaves its tests out. `test_red_missing` (no red scenario and no
  derived red case) stays a warning in 0.2: there is no case to derive a
  test from, and derive writes nothing for it. Both validator builds
  carry the same rule; Swift gained the reading of blocking questions
  that only derive had.
- derive refused any specification with errors, which in 0.2 would have
  included the errors it exists to settle. It now runs past the
  missing-test errors and still refuses on any other error.
- extract and merge run the derivation into every tree they write: the
  drafts go under `tests/<name>/test.yaml`, `tests` is listed among the
  stages when one is written, and a line counts the drafts, one names
  each held-up subject with its questions, and one names a draft whose
  name is taken.
- merge refused every tree that held tests. It now takes a tree whose
  tests are exactly the drafts derive writes for it (compared by name and
  value, so problem marks do not count), leaves them out, and derives
  again for the merged specification; any other test is refused as
  before, with the advice to write it in the merged specification. The
  merged tree from trees with drafts is byte-identical to the merge of
  the same trees without them (`merge-takes-derived-drafts`).
- The fragment schemas are `specarch-fragment-*-0.2`; `tools/fragment-schemas`
  takes the version from the design schema's file name, since the
  `specarch` key is now an enum. Every hint line in the repository's own
  trees moved with it.
- The root files of `spec/` and both examples, the schema line extract
  writes, and the editor hints in the README and `docs/conventions.md`
  point at `main`'s 0.2 schema: no tag serves it yet, and the release
  that cuts one moves them to the tag, as 0.5.0 did. The install lines
  stay at v0.5.0.
- The lending desk's own specification gained its tests stage: Q-5 moved
  to `tests/questions.yaml`, now asking only for the data, and derive
  wrote 24 drafts. Its requirement LEND-4, which waits on Q-1, is now
  reported as verified by no test (a warning), since its subject's test
  is held up by that question.
- Conformance fixtures stay on 0.1 (owner's decision on the item's
  question): they test other rules, and each validate case's output now
  starts with the `meta_model_version` warning. Two fixtures with no
  missing tests moved to 0.2 because their point is having no problems
  (`document-problems-none`, `document-problems-implementation-broken`);
  `document-problems-marks-current` carries the new mark in its input,
  and the two `document-check-*` cases carry a regenerated techspec.
- `specarch version` prints "specifications: meta-model 0.2, and 0.1
  until 1.0" in both builds. Generated files' headers say meta-model 0.2.

New cases: `validate-meta-model-0-2-missing-test`,
`validate-meta-model-0-1-missing-test` (the same tree, both builds, same
output), `derive-meta-model-0-2`, `derive-meta-model-0-2-other-error`,
`merge-takes-derived-drafts`, `merge-refuses-edited-test`.

Checked: go build, go vet, go test ./... and swift test pass; specarch
validate gives the same output in both builds on `spec` and `examples`,
with 0 errors; `go run ./tools/fragment-schemas -check` is current;
document --check and generate --check pass; every lending desk, notice
board, reading list and room booking extraction step of CI was run
locally and passes, and `examples/lending-desk/extract.sh` writes
byte-identical output on two runs.

Handoffs: none processed; the two in the mailbox stay for their items.
