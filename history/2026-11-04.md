## Item 2041: the Dart test file imports only what its tests name (BUG-070)

Summary: `specarch-gen-tests-dart` imported the library of values,
harness and checks into `specarch_design_test.dart` even when no test
named it, as for a specification whose design tests all have bodies
written by hand, and `dart analyze --fatal-infos` failed on the generated
file with an unused import. The generator now writes `main` first and
writes each import only when a line of it names that import's code.
BUG-070 records it.

- `internal/gentests/dart.go`: `dartUses` notes, while `main` is written,
  whether it names the framework (`test`, `group`), the project's harness
  (`newHarness`, the bodies) and the library (`Value`, the checks,
  `mappingHarness`). The framework and harness imports follow the same
  rule, so a specification whose tests all do not apply gets a test file
  with no import, which `dart analyze` also accepts.
- ADR-041 and `docs/generators.md` say the test file imports only what
  its tests name.
- Conformance case `generate-tests-dart-hand-written-bodies` (SA-31): an
  operation and a constraint whose tests have no call, one signing a
  caller in, and one test that does not apply; the test file imports
  `package:test` and `specarch_harness.dart` only.
  `TestHandWrittenBodiesDartAnalyzes` runs `dart analyze --fatal-infos`
  on it beside a stub harness, and checks the all-not-applicable file
  has no import. It fails on the generator before this fix.
- The output of `generate-tests-dart` and of the library lending example
  is unchanged: their tests name the library.
- Left open: the estate's integration tests, which are not on `main` yet,
  analyze their Dart output without fatal warnings because of this bug;
  their check can turn to `--fatal-infos` once both are on `main`.
- Nothing left out for the public repository: the case is generic.
- Handoff mailbox: empty; nothing processed.

## Item 2044: the tests leave no specarch-plugins folder behind (BUG-071)

Summary: `go test ./cmd/specarch` left a `specarch-plugins-<n>` folder of
about 120 MB in the temporary folder after every run, the plug-ins it
built, and nothing removed it. Several of them filled a self-hosted test
runner's disk. Each top-level test that runs plug-ins now makes its own
plug-in folder and removes it with `t.Cleanup` when it ends, passed,
failed or panicked. BUG-071 is logged and closed in `BUG_HISTORY.md`.
- The folder is made per top-level test, not once per run in `TestMain`:
  a panic never returns from `m.Run`, while Go runs the cleanups of a
  panicking test and of every test above it.
- It keeps the `specarch-plugins-` prefix (`os.MkdirTemp` with a
  `t.Cleanup`, not `t.TempDir`), so a sweep of the temporary folder still
  finds one left by a run that timed out or was killed, which runs no
  cleanups.
- Each such test builds the plug-ins it needs again; a cached link takes
  under a second per plug-in.
- `TestPluginFolderRemoved` proves it: the test binary runs again as a
  child with its own `TMPDIR`, with a case that passes, fails or panics,
  and the folder the child built into is gone each time. With the cleanup
  taken out it fails on all three.
- A full `go test ./cmd/specarch` with a fresh `TMPDIR` left that folder
  empty and no `specarch-plugins` folder in `/tmp`.
- The conformance suite's description in the Go implementation file says
  where the plug-ins are built and when the folder is removed.
- Left out for the public repository: the runner's host name and the
  agent that found the leftovers; the entry says "a self-hosted test
  runner".
- Open: a run killed or stopped by `-timeout` runs no cleanups and can
  still leave a folder; the runner's own sweep of `specarch-plugins-*`
  covers that.
- Handoff mailbox: empty; nothing processed.

## Item 1771, round 2: a fresh environment that runs, and one name for the database's password

Summary: the review of round 1 found that the example's `fresh.sh`
stopped at its fourth step, since it named the migrations and the seed
relative to the deploy output and not to its own folder, and that a
cloud-init database host took its password under the image's variable
while every other form and the design name `<SERVER>_PASSWORD`. Both are
fixed, and a run of the generated script against a real PostgreSQL 16
found three more faults on the way, all fixed: the script never parsed,
the run's project name was refused by Compose, and a cluster built from
nothing has none of the roles the migrations' row policies name.

- The paths: `fresh.sh` sits in `<output>/<deployment>/` and names the
  sql and seed targets' folders from there (`../../migrations` in the
  example).
- The parse: `${1:?...}` held an apostrophe (`file's`) outside double
  quotes, which the shell reads as the start of a quoted string, so the
  script stopped at its last line. Each refusal is now a test with its
  text as one single-quoted word.
- The settings: the script read the env file by sourcing it, which reads
  a value as shell (a URL with `&` would have started a background job);
  it now exports each `NAME=value` line as it stands, as Compose reads it.
- The project name: `date +%Y%m%dT%H%M%SZ` gave capitals, which Compose
  refuses in a project name; it is `%Y%m%d-%H%M%S` now.
- The roles: on postgresql the script creates each role of the design,
  as the database role the sql target's policies name
  (`gensql.DBRole`, shared with the sql target), before the migrations.
  The migrations leave roles to the operator, as cluster state, and a
  fresh cluster has none.
- The database's password on a host: the operator writes
  `<SERVER>_PASSWORD` in `secrets.env`, as for Compose and Kubernetes;
  the unit checks it and copies that one line under the image's variable
  into `/run/<system>/<server>.env`, readable by root alone, which the
  container reads. A variable on the podman command line was the other
  way, and lost: anyone on the host reads a command line through `ps`.
  The database's container no longer reads the services' secrets. The
  unit's check doubles its `$` (`$${v}`), since systemd expands `$` on a
  command line before the shell sees it.
- The ports: a fresh run publishes the deployment's own ports, so one
  run at a time fits on a host, not beside a running project of the
  deployment; the script and the docs say so and say where the suite
  reaches each server. Ephemeral ports lost: the suite reaches the
  database through a secret such as a database URL, set before the run
  with its port, and a Compose override adds to a service's ports rather
  than replacing them.
- The deployment names under `settings.deployments` that a file lacks
  are reported in name order; a unit test helper lost its unused
  parameter.
- Proof: a unit test runs a generated `fresh.sh` under a stub compose
  command (roles, migrations in order, seed, a value with `&` and an
  apostrophe, the teardown, the project name), another runs the host
  unit's two commands on a temporary folder; the example's script ran
  against `postgres:16` through `podman compose` with only its build and
  test lines swapped (the example holds no Containerfile or Go module),
  loaded six migrations and the seed's 12 books, and tore the project
  down with its volume.
- Docs: ADR-227, SA-121's acceptance and `docs/generators.md` say the
  password rule per form, the roles step and the ports.
- Renumbered: while the item was in review, main took ADR-226 and SA-120
  for the tests target's integration tests (item 1770), so on the rebase
  the deploy target's decision is ADR-227 and its requirement SA-121,
  the round 1 entry of 2026-11-03 included; the scripts build and check
  both the tests-go and the deploy plug-ins.
- Left open: one `DATABASE_URL` serves the api container (the database
  at `db:5432`) and a suite on the host (`localhost:5432`) in a fresh
  run; splitting them is a design choice not taken here. The host unit
  is proven by a simulation of systemd's `$$`; a run on a Linux host
  with podman 4.4 or later is owed.
- Handoff mailbox: empty; nothing processed.
- Nothing left out for the public repository.

## Item 1771, round 3: the fresh run tears down on an interrupt too

Summary: the review of round 2 found that `fresh.sh` set its teardown
trap on `EXIT` alone, and dash, `/bin/sh` on Debian and Ubuntu, runs no
`EXIT` trap when a signal ends the shell. A Ctrl-C or a CI timeout
during a run left the project's containers and volume running, holding
the deployment's ports, so the next fresh run on that host failed. The
script now also traps `INT`, `TERM` and `HUP` and exits with the
signal's status (130, 143, 129), which runs the teardown in every shell.

- The generator: `internal/gendeploy/compose.go` writes the three traps
  right after the `EXIT` trap, before `compose up`; the golden case
  `generate-deploy` and the example's `deploy/local/fresh.sh` are
  re-recorded.
- The test: `TestFreshScriptTearsDownOnASignal` runs the generated
  script under `sh` and, where the host has it, `dash`, sends each of
  the three signals once `compose up` has started, and checks the exit
  status and the `down --volumes --remove-orphans` call. Without the
  traps all six cases fail: dash ends by the signal with no teardown, and
  bash on an interrupt carries on and exits 0.
- The real run, asked for by the review: the example's `fresh.sh` ran
  under dash against `postgres:16` through `agentq podman compose`, on a
  scratch copy with the api service removed and its build and test lines
  swapped (the example holds no Containerfile or Go module): six roles,
  six migrations and the seed loaded, 12 books counted, the project torn
  down. A second run sent `TERM` to dash during the load: dash exited
  143, the trap tore the project down, and no container, network or
  volume of a fresh run was left.
- Docs: ADR-227, SA-121's acceptance and `docs/generators.md` say the
  teardown covers an interrupt, a termination and a hang-up, and why.
- Left out for the public repository: nothing; the example and the case
  are generic. Handoff mailbox: empty; nothing processed.
- Rebased onto main (item 1773's test-run records, 7 commits). The
  history files kept both sides; every generated file was taken from
  main and regenerated, which moved only the digest in the example's
  deploy files (main added a target to its implementation file). The
  ids stand: main took ADR-230 and SA-125.
