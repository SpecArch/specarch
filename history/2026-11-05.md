## Item 2167: the landing checks and regenerate run on the Linux runner

Summary: `scripts/landing-check.sh` and `scripts/regenerate.sh` run their
work as heavy-lock jobs that heavy-lock sends to a healthy Linux build
runner: the go part, the swift part (the Swift validator's build, its
tests and its comparison with the Go build) and the regenerate, each one
job. The Swift validator builds and passes its tests on Linux for this
(ADR-243). A full landing check costs the Mac about 3 s of CPU, where its
go part alone took 352 s.

- Why: the Mac's CPU was the bottleneck for the build jobs of every
  repository, while the runner sat idle; the landing check ran `go`
  through `sh`, which heavy-lock reads as a job that stays on the Mac.
- How a job reaches the runner: heavy-lock places a job by its command,
  and `sh` is not a kind it knows, so each script names the kind in
  `HEAVY_LOCK_KIND` (`go_build_test` for the go part and regenerate,
  `swift_linux_static` for the swift part), the variable heavy-lock reads
  for a script that knows its kind. One job per part sends one snapshot
  and builds once; a job per step would send the 79 MB snapshot and
  build from scratch for each.
- regenerate on the runner takes the checksums of the tree before and
  after, packs every file it wrote into `.bin/regenerated/files.tar` and
  the ones it removed into `removed.txt`, and that folder comes back as
  heavy-lock's artifact; the script writes them into the checkout and
  removes the removed ones, refusing a path outside it.
- Falling back: a part runs on the Mac, with the reason printed, when no
  runner can take it (heavy-lock prints why), when files have changes not
  staged or are untracked (the runner gets the committed files with the
  staged changes only, so it would check another tree), when the script
  runs inside a heavy-lock job (a heavy-lock inside a job runs in place),
  and where there is no heavy-lock, as in CI. Every failure line names the
  job, the host it ran on and the step.
- The Swift validator on Linux (ADR-243): CryptoKit is missing there, so
  the evidence file's SHA-256 uses a FIPS 180-4 implementation of its own
  where CryptoKit is absent, tested against the standard's examples and
  against CryptoKit on macOS; a JSON boolean is told from a number by the
  NSNumber's Objective-C type where CoreFoundation's API is missing; and
  the expression tests require the backward zone name EST only where the
  host's time zone database holds it (Debian 13 ships those names in
  tzdata-legacy). No dependency was added.
- Measured on 2026-11-04 and 2026-11-05, wall time and the Mac's CPU (user
  plus system), each run with the tree clean:

  | run | where | wall | Mac CPU |
  | --- | --- | --- | --- |
  | `landing-check.sh go`, before | Mac | 505 s | 352 s |
  | the swift part, before | Mac | 220 s | 123 s |
  | `landing-check.sh go`, after | runner | 307 s | 2.0 s |
  | the swift part, after | runner | 234 s | 1.0 s |
  | `landing-check.sh`, both parts, after | runner | 448 s | 2.9 s |
  | `regenerate.sh`, after | runner | 143 s | 1.7 s |

  Another full run that first waited for a runner slot took 643 s. The runner
  has 4 cores and 2 slots, so each job gets 2; the Mac had 10.
- Regenerate on the runner, on a clean tree, wrote no file that differs
  from the committed ones: the generators' output on Linux is the Mac's,
  byte for byte. A generated file staged with a wrong line came back
  corrected through the runner.
- The owner's decision (2026-11-05, 02:40): the repository's
  `test_command` is the whole landing check, `sh scripts/landing-check.sh`,
  so both parts gate every landing. agentq lets only the owner or the
  dispatcher change it, and the dispatcher set it at 02:57.
- `scripts/sbom.sh`, the scan run by hand before a release: its govulncheck
  step, the one that builds the module's code, runs as the heavy-lock job
  `specarch:sbom-govulncheck`, which went to runner-node0 and found no
  vulnerability; with a file changed and not staged it ran on the Mac and
  said why, in its report too. On the Mac, warm, it costs about 8 s of
  CPU; through the runner, 20 s for the whole script and 3.7 s of Mac CPU.
- What stays on the Mac, and why:
  - syft in `scripts/sbom.sh`: it reads go.mod, go.sum and the Swift
    package files of HEAD through `git archive`, and a runner has no .git.
  - grype and osv-scanner in `scripts/sbom.sh`: they read the SBOM the
    script has just written into `sbom/local/`, which git ignores, so a
    runner's snapshot does not carry it. Each is a lookup over 17
    components that takes seconds.
  - The test map's commands at landing: the tool that runs the test map
    wraps each in a heavy-lock job, and a heavy-lock inside a job runs in
    place. That is a change in that tool, reported, not made here.
  - Any part run with files changed and not staged, or untracked: the
    runner would check the committed tree, not this one; each script
    prints that reason and runs the part here.
  Nothing else needs macOS: SpecArch has no app of its own to build, and
  CI's macOS swift job still builds the Swift validator on macOS.
- The release step's own scan (the SBOMs, scanners and draft release) is
  run by the release tool, not by a script of this repository, so where it
  runs is that tool's choice.
- Left open: the test map's commands still run on the Mac (above).

## Item 2164: intent phase 2, the work-package records and their seven rules

Phase 2 of the intent design (ADR-242, docs/intent-and-work-packages-2026-11-04.md)
is built, recorded as ADR-245 with requirements SA-140 to SA-142.

- A work package is a record of kind `work-package` in
  `records/work-packages/`, named by its ID: `id`, `title`,
  `requirements` and `status` required, `release`, `after`, `assignedTo`,
  `effort` and `why` optional. The kind is spelled `work-package`, as
  ADR-242's consequences settle and as the other kinds of two words are,
  where the design document's example and the item wrote `workPackage`.
  `effort` is the change record's shape, now one definition both kinds
  use, not the "3 days" of the example. `assignedTo` is a plain name of a
  person or a team (the owner's decision 4), not a stakeholder role, and
  the progress document for everyone leaves it out.
- References: a requirement that is not one, one named by pointer, a
  release with no record and an `after` package with no record are
  `record_ref` at the entry.
- `work_package_cycle` is an error at each `after` link on a cycle, naming
  the chain, as `decision_cycle` is. Six warnings, held to packages that
  are not withdrawn: `work_package_order` (read from the references
  `specarch model` lists, cut to elements, without satisfies, verifies,
  decidedIn and the target of a one-to-many or many-to-many relation;
  an element no package builds is unplanned, not out of order),
  `work_package_overlap`, `work_package_release` (only when both name a
  release), `work_package_unconfigured` (a setting that is not secret, has
  no default and no deployment gives a value, once some deployment gives
  any setting a value), `work_package_not_ready` and
  `work_package_unverified` (any passed result in a test-run record counts).
  Both validator builds print the same lines.
- `document progress` gains a Work packages section once a package is
  recorded, with one row per package (release, status, assignee, after,
  requirements, estimated and spent hours, and what blocks it: the after
  packages not done and the rules the validator warns it of) and the
  accepted requirements of a planned release no package holds, named as
  unplanned. The test plan gains Tests by work package. The burn-up still
  counts the elements of change requests; a package's hours stand in its
  row. Both sections are in Indonesian too.
- `docs/maintenance.md` gains the record's row and a Work packages
  section, which says once that a work package is what a tracker may call
  an epic or a batch, and the rules table its rules.
- The library lending example records three packages, WP-1 done, WP-2 in
  progress and WP-3 planned; its WP-1 is warned `work_package_unverified`,
  since no test run records its catalogue and registration tests passing,
  which shows the exit criterion at work. Building it showed that a
  one-to-many relation made an entity "need" the entity that points back
  at it; such a relation is left out of the order rule.
- New cases: validate-work-package-cycle, validate-work-package-warnings,
  document-progress-work-packages and document-testplan-by-package.

## specarch plan: propose, next, brief, export and import (item 2165)

Phase 3 of the intent and work-package design (ADR-242): `specarch plan`,
recorded as ADR-246 with SA-143 to SA-145 and the command's design in
`spec/design/commands/plan.yaml`.

- `specarch plan <folder>` proposes packages for the requirements
  `document progress` calls unplanned: accepted, of a planned release, in
  no package that is not withdrawn. `--release <version>` plans one
  recorded release and takes the accepted requirements that name no
  release with it; without it they are named as left out, as are the
  requirements that are not accepted. Requirements met by a common element
  go into one package (a decision groups nothing: it explains, it builds
  nothing), groups that need each other are merged, so no proposal makes a
  `work_package_cycle`, and each package comes after the package that
  builds what its elements need, read from the same references
  `work_package_order` reads. Records are written with status `proposed`
  under the next WP numbers. The case validate-plan-proposals shows the
  proposals of plan-proposes validate with no work-package warning.
- `--next` prints the first planned or ready package, by ID, whose after
  packages are done or withdrawn and which the validator's own readiness
  and order checks pass; the checks are shared through
  `validate.PlanWorkPackages`, so what plan calls ready is what validate
  accepts. With none it prints what each candidate waits on and exits 1.
- `--brief WP-n` prints one Markdown page: whether the package can start,
  its requirements with acceptance criteria, the elements to build, the
  tests that must pass, the goals served, the out-of-scope entries near it
  (ruling out a need its requirements refine, or a need serving a goal it
  serves) and the others by ID, the quality goals in rank order, and the
  settings, migrations, jobs, processes and monitors it changes in
  operation.
- `--export csv|json` prints every package for a tracker; `--import <file>`
  (.csv or .json) writes back status, assignedTo and effort, keeping the
  record's comments and key order, and warns with both values at a title,
  release, after or requirements the file changes, at an invalid status or
  hours, at an unknown or repeated ID and at a column it does not read.
  The warnings are lines on the command's output, not rules in the
  problems file, since the validator reads no tracker file.
- Brief and export print on standard output rather than writing files
  under `--out`; the caller redirects them.
- Go only: plan is a command, not a validator change; the order check
  moved into a method both the rule and plan call, and validate prints
  what it printed before.
- `docs/maintenance.md` describes the command in the Work packages
  section, and both guides by situation (English and Indonesian) under
  building the system; AGENTS.md, the manual, the skill, the capabilities, guide and MCP listings
  gain it. New cases: plan-proposes, plan-proposes-dry-run,
  plan-release-unknown, plan-next, plan-next-none, plan-brief,
  plan-brief-unknown, plan-export-csv, plan-export-json, plan-import,
  plan-import-json, plan-usage-error and validate-plan-proposals.

## specarch plan, review round 1 (item 2165, round 2)

The review of `specarch plan` found six faults in the code, all fixed:

- Hours of NaN or Inf from a tracker passed the import's check, since a
  float parser takes them and NaN <= 0 is false; they are now warned as
  not a positive number of hours, and hours the import writes go into the
  record in plain decimal form (16.0 as 16).
- A record's hours written as .5, 1. or +5 are YAML numbers but not JSON
  numbers, and the JSON export printed an error object and exited 0. The
  export now writes the hours as plain decimal numbers, in the CSV too,
  and exits 2 naming the cause if the JSON cannot be encoded.
- The import replaced the value node of a key it changed, so a line
  comment on status or assignedTo was lost; the node is now changed in
  place and its comments stay.
- A CSV saved by a spreadsheet as "CSV UTF-8" starts with a byte order
  mark, and the import refused it for having no id column; the mark is
  now skipped.
- `--next` and `--brief` judged work_package_order for a requirement of a
  requirement set, which the validator's rule skips; they now skip it too,
  so they cannot report a reason validate never warns.
- The brief listed a decision under "Design elements to build"; a
  decision explains a requirement and builds nothing, so it is left out.

plan.yaml, ADR-246 (with RFC 8259's reason for writing hours in decimal
form, and why a byte order mark is skipped) and SA-145 say so. The cases
plan-import, plan-export-json and plan-brief cover each fix, and the new
case plan-brief-requirement-set shows a package holding only a
requirement of a requirement set can start. Nothing was left out on
purpose. The handoff mailbox was empty.
