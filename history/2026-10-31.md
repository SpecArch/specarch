## A test map: the narrowest check for each changed path (item 1589)

`scripts/test-map.json` maps the repository's paths to the narrowest
command that covers them, so work in progress runs those instead of the
whole landing check; the landing check stays the test before landing.
The first matching rule takes a path:

- `go.mod`, `go.sum`: `go test ./...`.
- `spec/tests/**`: only the conformance cases the change touches (the
  case folder names, from the paths, as a `-run` filter on
  `TestConformance`, with `TestCommandTestsHaveCases`), the Swift
  conformance suite, and `validate spec examples`.
- `swift/**`: the landing check's swift part.
- `schema/**`, `idioms/**`, `scripts/landing-check.sh`,
  `scripts/regenerate.sh`: the whole landing check, since both builds
  embed the schemas and idioms.
- `embed.go`, `docs/help/**`: `go test ./cmd/specarch` (its self tests read
  them).
- `third_party/**`: `go test ./internal/extract ./cmd/specarch`.
- `cmd/specarch-gen-*/**`, `internal/gen*/**`: `go vet` and `go test
  -count=1` of the changed packages and `./cmd/specarch`. The count is
  forced because the conformance suite builds the plug-ins with `go build`
  while it runs, which Go's test cache does not see, so a cached pass
  would hide a broken generator.
- `*.go`: `go vet` and `go test` of the changed packages and
  `./cmd/specarch`. Most packages have no tests of their own; the
  conformance suite in `cmd/specarch` is what exercises them.
- `spec/**`, `examples/**`, `records/**`, `vocabularies/**`, `readers/**`,
  `tools/**` and the generated documents in `docs/`: the landing check's
  go part (validate, documents and generated code current).

Paths no rule takes run nothing: the prose in `docs/` and at the root,
`history/`, `.github/`, `sbom/`, `scripts/sbom.sh` and the map itself.
`CONTRIBUTING.md` says how the map is read.

Each rule was then checked by changing one file under it and running the
map's selection on that change. Two rules did not do what this entry says, and the map
was corrected:

- A glob ending in `/**` takes a literal folder, so
  `cmd/specarch-gen-*/**` and `internal/gen*/**` matched nothing and every
  generator file fell to the `*.go` rule, without `-count=1`. They are now
  `cmd/specarch-gen-*/*`, `cmd/specarch-gen-*/*/*`, `internal/gen*/*` and
  `internal/gen*/*/*` (a `*` stops at `/`). The folders two levels deep
  hold templates, not packages, so they have a rule of their own that
  vets and tests the generator package above them.
- The `.go` files under `examples/` went to the `*.go` rule, whose `go vet`
  fails on them: the lending-desk code is a module of its own and the
  notice-board sources import a library this module does not require.
  `examples/**` is now its own rule, the landing check's go part, listed
  before `*.go`.

`cmd/specarch/testdata/**` was added to the `go test ./cmd/specarch` rule;
its two fixtures matched no rule before.

## Asking a person: one question at a time, ranked by gaps --next (item 1680)

The owner compared SpecArch with Spec Kit (github.com/github/spec-kit,
MIT) and tried both on an existing system. SpecArch checked and captured
better; Spec Kit's clarify command asks better: one question at a time,
two to five options with one recommended that the person can accept in
a word, ranked by impact and uncertainty, at most five per run. SpecArch
recorded answers (questions, decide, decision records) and gave the
agent no method for asking. This item takes that method over, credited
to Spec Kit in ADR-209, the help topic and `docs/refinement.md`.

- `specarch help asking`: the procedure. Run `gaps --next`, put the one
  question to the role it names, offer two to five options with one
  recommended and its reason, record the full text of the option chosen
  with `decide --source` an interview, write the entries decide lists,
  validate, and run `gaps --next` again, since an answer can settle or
  open other questions. No fixed number of questions: a must question
  left unasked leaves keys undefined. A material question is asked as a
  request for the file. The agent guide's workflow step 4 and its list
  of what to ask the owner point to it, and `AGENTS.md` follows.
- `specarch gaps --next`: per specification, the one open question
  ranked first: priority, then the outputs it holds up (documents and
  code targets, from the same list as the outputs table, which now reads
  it too), then the entries it blocks, then the stage, then the ID. It
  prints who decides, what it blocks with the keys missing there, what
  it holds up, the options, the Insight and the decide line, with
  `--source` filled when the root file declares exactly one interview
  source (a document source for material), otherwise a line saying
  which to declare or choose. Errors come first as problem lines; the
  exit status is that of gaps. With `--json`, `next` holds the same as
  data and `recommendation: null`, for the agent to fill before it
  passes the question on.
- Specification first: SA-107, ADR-209 (proposed), the option and its
  output in `spec/design/commands/gaps.yaml`, the source `spec-kit` in
  the root file, the topic in `help.yaml`. Cases `gaps-next-ranks-by-outputs`,
  `gaps-next-ranks-by-blocks` (with an error in the specification),
  `gaps-next-should-before-could`, `gaps-next-json`, `gaps-next-none`,
  `gaps-next-usage-error` and `gaps-next-unknown-option`;
  `capabilities-text` and `guide-order-of-work` recorded again.

Left out on purpose: uncertainty as a ranking key. No key of a question
says how unsure the people are (`certainty` is only for questions a
reader asks about code), so the agent says it in its recommendation's
reason. A `recommended` key on the question in the meta-model was
considered and not taken: a format change in both validators that would
write into the design a guess no person has seen. Not built in the Swift
build, which has no gaps. Nothing of the trial's system is named here.

The specarch handoff mailbox was checked and is empty; nothing was
deleted.
