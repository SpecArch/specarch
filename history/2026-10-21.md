## The operations guide: a job tried again once, and the checklist pointer

Two follow-ups to the dead-letter handling (953e0b0e, ADR-166). The jobs
table wrote "tried again up to 1 times" for a retries limit of 1
(BUG-043, opened and fixed in the same commit): it now writes "1 time".
The case `document-writes-operations` gives its job `countStock` a limit
of 1 to pin it. The daily checklist row of a job that keeps items apart
points to the section Jobs only when the job has a `deadLetter`; for one
without, Jobs says only that the specification does not say, so the row
reads as before. The library lending guide is unchanged by either.

## ADR-166 says which checklist rows point to Jobs

Review of the dead-letter handling found ADR-166's sentence "the daily
checklist row of such a job sends the reader to that part" following the
sentence about a job with no `deadLetter`, so it read as the opposite of
what is built. It now says the row of a job with a `deadLetter` sends the
reader to its part and a job without one keeps the plain row. The
technical specification is regenerated; no generated guide changes.

## Guarded scripts for MariaDB

Roadmap target 8 left another dialect unbuilt. `specarch-gen-scripts` now
writes the scripts of ADR-158 for MariaDB too, when the scripts target's
dialect is `mariadb` (ADR-167, proposed; MariaDB chosen as the dialect
closest to the PostgreSQL path). SQL Server and Oracle stay an error at the
target; ADR-158 and SA-87 say PostgreSQL or MariaDB.

A MariaDB script is a strict session (`STRICT_ALL_TABLES` added to the
session's mode) and one compound statement for the mariadb client, with
the values as user variables given in `--init-command`. Choices settled by
trying them on MariaDB 11.4.4 in a disposable container: a `SOURCE` after a
`SET` on one `-e` line does not parse, and an error inside a sourced file
does not stop the client, so the file is read on standard input; a
compound statement may not start with a label, so the label is on the
inner block; MariaDB's `CAST` truncates or rounds and warns (123.7 is 123
as UNSIGNED, 124 as DECIMAL(65,0)), so each variable's text is checked
against its column's form before anything is read; without strict mode a
value too long is cut, so the script makes the session strict itself;
`COUNT(*) ... FOR UPDATE` locks the counted rows (a second session's
UPDATE timed out on one). On MariaDB the audit instant is `VARCHAR(35)`
text, so `gensql.Column` now carries the field's format and the script
writes the instant in the idiom's nine-digit UTC form. The PostgreSQL
scripts are byte for byte the same.

The six scripts of the new case `generate-scripts-mariadb` were run by
hand against the tables `specarch-gen-sql` writes for MariaDB: unset
variable, malformed uuid, fractional unsigned key, fractional INT and an
`@apply` that is not a boolean refused before reading; dry runs rolled
back; applied runs committed; second runs reported already applied or
were refused by the count; a title too long and a status outside the
check were refused and rolled back. `generate-scripts-dialect-refused` now
names sqlserver. The generators guide, roadmap, README, idioms guide and
the implementation file say so; techspec, requirements, testplan and
traceability are regenerated.

Found on the way and left open: BUG-044, a MariaDB date-time with
`generatedDefault: currentTime` gets `CURRENT_TIMESTAMP`'s own text form.
The handoff mailbox was empty.


## MariaDB scripts: text compared exactly, and no trailing newline

Review of the MariaDB scripts found two gaps, both fixed in ADR-167
(still proposed). The already-applied step and the postcondition of a
PUT compared text under the column's collation, which on MariaDB is the
server's case- and accent-insensitive default, so a title changed only
in case was reported as already applied. A text column is now compared
with its value converted to utf8mb4 under `utf8mb4_nopad_bin`, so a
change of case or a trailing space counts, as it does in PostgreSQL;
keys and from states still match under the column's own collation. The
variable form patterns ended in `$`, which in MariaDB's PCRE2 also
matches before a final newline, so `'5\n'` passed as a whole number;
they now end in `\z`. The session statement also takes
`NO_BACKSLASH_ESCAPES` out of the session's mode, so the backslash in a
pattern reads the same on every server.

Tried on MariaDB 11.4.4 against the tables `specarch-gen-sql` writes:
'The Hobbit' to 'the hobbit' dry-ran and applied, the second run
reported already applied, a trailing space alone was a change; a
trailing newline in an integer, a uuid key and an unsigned key was
refused before reading, also with `NO_BACKSLASH_ESCAPES` set. The
previous scripts let the newline through and reported the case change as
already applied. The six expected scripts of `generate-scripts-mariadb`
are re-recorded; techspec and testplan are regenerated.


## A guard says what any other change writes: writes (ADR-168)

Roadmap target 8 left one gap: a guarded change whose entry is not a
transition, a PUT by its key or a DELETE by its key (a PATCH, a command
no transition names, a POST that changes records already there) was a
warning at its guard, its script written by hand, because the meta-model
had no word for what such a change writes. A guard now takes `writes`:
`set`, the fields the change sets, each to `given` (the value the
operator gives) or a literal of the field's type, or `delete: true`.
ADR-168 (proposed) says why: values are kept to given and literals so a
record already changed can be told apart and a second run changes
nothing, and `writes` on a PUT or DELETE by its key is an error, since
the keyword already says the change.

Both validators check it under the rule `guard` (`validate-guard-writes`,
the same output in both builds): writes beside a PUT or DELETE by its key,
delete beside a transition, a field the entity lacks, its key or its
state field, a computed value, null on a required field, a wrong type, a
value no enum has, a decimal with more digits than its scale, a string on
a date and a number an int32 cannot hold. `specarch-gen-scripts` writes
the script from it on PostgreSQL and MariaDB: a set by key checks
"already applied" as a PUT does; a set on many records leaves out the
records already holding every value written, so a second run is refused
by its count; a set beside a transition adds its fields to the change.
The warning stays for what no word says (a POST that makes a record,
encrypted fields, two to states, a transition to its own state, a keyed
change of more than one record, a key of two fields), and the warnings of
a POST, a PATCH and an unnamed command now point to `writes`.

`generate-scripts` and `generate-scripts-mariadb` gain amendLoan's
writes, a soft delete of many records, a set of null and of a string on
many records and a note set beside a transition; their expected scripts
are recorded from a real run. Tried by hand on PostgreSQL 16 and MariaDB
11.4.4 against the tables `specarch-gen-sql` writes: dry run, apply, the
keyed second run reported already applied, a change of case alone
applied, a note left out set to NULL, a null note labelled, and the
second run of each change of many records refused by its count with
nothing changed. A first version compared a literal with `=` on
PostgreSQL, which leaves a null note out of `NOT (note = 'Returned')`;
the comparison is `IS NOT DISTINCT FROM`, as for a given value. SA-29 and
SA-87 say it in their acceptance; ADR-158, the generators and conventions
guides and the roadmap read with it.

## Caller checks in the Swift, JavaScript and Dart readers (ADR-169)

Roadmap 5, caller context: `extract swift`, `extract javascript` and
`extract dart` now read the gates the implementation file names under
`clientChecks` (with `clientArgument`), `signatureChecks`,
`applicationChecks`, `callerChecks`, `audienceChecks` and `eventWriters`,
as `extract go` has done since ADR-154 and ADR-159. Each reader finds a
gate where it finds a permission check: Swift in a group's middleware;
JavaScript in a route's middleware, a mount's, an earlier `use()` (cited
at that line) or the handler, called or named without a call; Dart in a
wrapper around the handler (nested wrappers are now followed to the
handler), a call in the handler, and a dart_frog `_middleware.dart` above
the route or its `onRequest` in the method's branch. A gate is never read
as a permission check. The names come from a string, an array or list
literal, or in JavaScript a const.

The writing and the questions moved out of the Go reader into
`internal/extract/gates.go`, which all four readers share, so the
callers, via and every question read the same in each language. The Go
reader's cases are unchanged by the move, and so are every other extract
case and the four examples' extract output (checked against the build
before the change). The facts dumps needed no change: they already carry
calls with their arguments and array and list literals.

New cases `extract-swift-caller-checks`, `extract-javascript-caller-checks`
and `extract-dart-caller-checks` mirror `extract-go-caller-checks`; their
dumps were made with `tools/code-facts`. SA-89 names the four readers; the
extract design, the implementation schema's descriptions, reading-code,
conventions, the roadmap and caller-context say the same.

Left out on purpose: the `Txn-Token` header read stays with `extract go`,
since the other readers do not read a handler's headers yet; it is named
as left to build in the roadmap. The pages reader's Next.js routes go
through the JavaScript reader's check code and now collect gates too, but
the pages reader writes nothing from them.

## Caller checks: a gate passed on a JavaScript mount is cited at the mount (ADR-169, review)

The review of the caller checks found that a gate passed as middleware
of a mount, `app.use('/admin', requireClient('admin-console'), admin)`,
was cited at the route's line in the router, a line that does not call
it. A mount now keeps where each of its middleware is added, carried
through nested mounts, Fastify plugins and `route()`, and a gate on a
mount is cited at the `use()` that mounts the router, as a Swift group's
is cited at the group. `extract-javascript-caller-checks` now mounts a
router with a client check on the mount; the extract design says so.

Found on the way and filed as BUG-045, not fixed here: a `use()` on the
application before a mount does not reach the mounted router's routes,
since the reader reads only an earlier `use` on the route's own router.
The case's golden records it until the fix.
