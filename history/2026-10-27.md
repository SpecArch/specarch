# 2026-10-27

## Both builds read `date()` of an instant in the specification's time zone (BUG-064, item 1300)

Asked by the owner (item 1300), from the finding item 1291 reported: `date()`
of an instant in an expression gave the calendar date at the offset the
instant was written with in the Go build and in UTC in the Swift build,
so `date(timestamp("2026-10-27T03:00:00+07:00"))` was the 27th in one and
the 26th in the other, against the rule that both builds print the same
output; the Go build also printed such an instant with its written
offset where the Swift build printed `Z`. The rule was already designed
by 1291 (ADR-193, `docs/state-machines.md` 12.3, SA-99) and nothing of it
was built.

Built, in both validators: the root key `timeZone`, a name of the IANA
Time Zone Database, in the 1.0 design schema (root only, like
`trustDomain`, so the fragment schemas are unchanged) and in `rootOnly`;
the rule `time_zone` with its two cases for the key, a name the database
does not hold as an error at the key, and a `date()` of an instant in a
specification that declares none as a warning at the call, naming the
input the call reads; both evaluators take the zone and give the
instant's date in it, UTC without one, and the Go build keeps every
instant in UTC, so both print one writing for one instant. The warning
comes from one hook, `zoneWarnings`, after every successful type check:
an entity's check and unique condition, a guard's precondition, a
formula, a page condition, a role's row policy and a token's check; the
tenant rule is derived and holds no `date()`. The design gives `date()`
no zone argument, so the item's "or an explicit zone" branch has nothing
to build. A `timeZone` the database does not hold is the error at the
key alone, and the date is UTC's until the key is corrected (12.3).

The name check is the same on every host, which the platform libraries
alone are not: on this Mac the Go build's `time.LoadLocation` accepted
`asia/jakarta`, `utc`, `Local` and `posixrules` (a case-insensitive file
system, the host's zone), and Foundation accepted `PST` and `GMT+7`
(names ICU knows beyond the database) while refusing miscased names.
Both builds now check the form first (each part begun with a capital),
refuse `Local`, read the host's `zoneinfo` folders by exact spelling and
refuse a name a folder holds in another spelling (`Asia/JAKARTA`), and
the Swift build takes a name no folder holds only when Foundation lists
it as a zone of the database or it is `UTC`, since the Go build's
embedded copy of the database decides there. The case
`validate-time-zone-unknown` holds five specifications at the edges
(`WIB`, `asia/jakarta`, `Asia/JAKARTA`, `PST`, `GMT+7`) and expects the
same five lines from both builds; `validate-time-zone` declares
`Asia/Jakarta` and expects one date for one instant written with `+07:00`
and in `Z`; `validate-time-zone-missing` expects the warning at a call
over an input and over a literal, and the dates in UTC. Each verifies
SA-99, which is proposed, as ADR-193 is: the owner approved the design
(item 1291, round 3) and asked for this fix; the statuses are the
owner's to move.

The library lending example declares `timeZone: UTC`, the zone 12.5
proposes for an example that names no place: its Loan's check
`lentOn <= date(loanedAt)` keeps the reading it had and gets no line.
The Go build imports `time/tzdata`, the database itself, so a host that
keeps none still reads a name. `docs/state-machines.md` 12.3, 12.5 and
the build plan's step 5 now read as the current truth: the `date()`
reading is built, the rest of step 5 (the two formats, `why`, the other
five cases of `time_zone`, the idiom rows, `generate sql` rendering
`date()` in `timeZone` and the nullable `EnteredAt` column) remains;
`docs/conventions.md` gains the `timeZone` row in the keyword table and
the zone in the `date(x)` row and the timestamp row.

Found on the way and reported, not fixed: `generate sql` renders
`date()` of an instant as `CAST(x AS DATE)` (Oracle `TRUNC`), which reads
the zone the stack's type gives it, the session's on PostgreSQL, where
the design said no generator renders `date()` today; the design now
names its rendering in `timeZone` as the build item's. The generated
SwiftUI `Rules.swift` pins UTC for its date reading, for the same item.
