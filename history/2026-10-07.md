## Decisions by the owner

- SpecArch is published under Apache-2.0 and stays the owner's own name and
  mark.
- No authoring layer for 0.1: specifications are written in plain YAML.
- A specification has two kinds of file. The design file
  (`*.specarch-design.yaml`) says what the system is and does and is
  neutral about language and framework. The implementation file
  (`<name>.<stack>.specarch-implementation.yaml`) says how one stack builds
  it. One design can have several implementations.
- The boundary between them: what a client of an interface must know is
  design; what only the builders or operators of one implementation need is
  implementation. Standalone OpenAPI and AsyncAPI documents are generated
  from the design, never kept beside it.
- Expressions in checks and formulas are a small subset of CEL, with CEL's
  strict typing: int, uint, double and decimal never mix without a written
  conversion, and a lossy conversion states its rounding.
- Types are design, and concrete: int32, int64, uint64, double, decimal with
  precision and scale, string, bool, bytes, date, timestamp, duration. A
  design that is too abstract cannot be implemented correctly; in JavaScript
  every number is a 64-bit float, so an int64 above 2^53 loses digits. The
  design says how values travel: decimals, and integers that can pass 2^53,
  as JSON strings.
- Before adopting or deviating from a standard, find out why it is the way
  it is and write the reason next to the choice.
- The Low IQ Tax principle governs the language, the tools and the
  documents.
- Tests are part of the specification. Design tests say what must hold on
  every stack, each marked golden or red; implementation files say how one
  stack runs them. The validator lists every red case the specification
  implies and no test covers.
- The command-line tool and generators are written in Go first. A second
  implementation in Swift follows from the same design, and both must pass
  one language-neutral conformance suite.
- Generator defaults: PostgreSQL for SQL; plain JavaScript for the web UI,
  with native ES modules, no build step, pinned vendored libraries and one
  small event bus; SwiftUI for the iPhone.
- Contributions: anyone who wants to contribute contacts the owner first,
  and the owner decides each case. Agents never merge outside changes.
- Commits and pushes follow the repository's switches, which are on.
- The project history is kept in this folder, one file per day, because a
  change log only grows and the reader of a design wants the design as it
  is now. Design files, schemas and documents carry no change log.
- An empty section of a specification's Markdown is left out, not filled
  with "Nothing yet.".
- Every subject (operation, command, page, constraint, transition) has
  golden and red scenarios. The validator derives every red case the design
  implies and names each one that no test covers; a warning in 0.1.
- The conformance suite holds inputs and expected outputs only, so a second
  implementation in Swift can pass the same cases.
- The techspec generator reads the design file for the design chapters and
  the implementation file, when given, for the deployment and
  implementation chapter, and keeps the two apart.

## What the second implementation showed

- Nothing in the design file had to move: it named no language, library or
  build tool, and the Swift build needed only its own implementation file.
- The design says decimals are exact but sets no bound on `precision`. Go
  computes with unbounded rationals; Swift's Foundation Decimal holds 38
  significant digits. They agree within that. Proposed for the design: a
  decimal's `precision` is at most 38.
- The conformance suite fixes things the design does not state: which
  schema problem is reported when several apply, the wording of YAML syntax
  errors, and the program version printed by `version` (0.1.0 in both
  builds). For one broken file, an unclosed quote, the two YAML libraries
  explain the error differently, so the two builds differ on its line and
  wording.
- The implementation schema has no word for which commands or generator
  targets a build offers; the Swift file says in a mapping that `generate`
  exits 2. A candidate for 0.2.
- Comparing the two builds found a Go bug: the JSON Schema library stores
  the location of a bad map key in a slice it keeps changing, so such a key
  was reported at a wrong path and on line 1. The Go build now finds the
  object from the key, its depth and the schema location. Two messages
  that passed the library's own words through (`dependentRequired`,
  `maxProperties`) are plain sentences in both builds now.

## The folder tree and the whole life cycle

The owner asked for two things at once: a specification that is a folder
tree instead of one file, and coverage of the whole life cycle, from
stakeholders and needs to the commissioning test, each stage a folder with
its own concepts. With them came the two fields every element may carry,
`why` and `cites`, the one-binary decision with verbs named by direction and
generator plug-ins on PATH, and the owner's confirmation of everything the
validator and techspec items had chosen. The changes went into `spec/` and
the code together.

- A specification is a folder rooted at `specarch.yaml`, which names the
  system, its version, the stages it keeps (`stages`) and the sources it
  cites (`sources`). Each listed stage is a folder: `requirements/`,
  `design/`, `implementation/<stack>/`, `tests/<name>/`, `deployment/`,
  `commissioning/`. A file under a stage folder holds one or a few objects
  of one section; a sub-folder named after a section holds only that
  section. A stage that is not listed has no folder and its sections are
  written in the root file, so a tiny specification is still one file. The
  validator merges the tree into one document, so a reference stays the
  plain key it was, wherever its target's file is; a name defined twice is
  refused with both files named. The single-file kind
  `*.specarch-design.yaml` is gone: one root form, not two. ADR-010 records
  it and supersedes ADR-007.
- The requirements stage: stakeholders (roles, never people), needs,
  requirements with the attributes of ISO/IEC/IEEE 29148 (kind, priority
  after MoSCoW, status, acceptance criteria, verification method after
  MIL-STD-961E, the needs refined), glossary, assumptions, constraints.
  The deployment stage: environments with their promotion path,
  configuration with secrets that may never carry a value, release and
  rollback as steps with a check each, migrations with their reversal. The
  commissioning stage: checks on the installed system (smoke, end-to-end,
  performance, security, data) in a named environment, and the sign-off
  with its criteria and signing roles. The results of a commissioning run
  are records kept outside the specification, one file per run under
  `records/commissioning/`; the conventions say their shape, and the
  documentor will read them. ADR-011 records the stages and why each
  follows its standard; `docs/stages.md` explains them for a reader.
- `why` and `cites` on every element at every stage, in the specification
  and in implementation files. A citation names a source declared once in
  the root file, the clause, and what the source says here; the validator
  refuses an undeclared source. Decisions keep context, decision and
  consequences and gain `why`. ADR-012.
- The link from an element to its requirements is `satisfies`; from a test
  or a check it is `verifies`; from a requirement to its needs, `needs`.
  `requirements` is now the section that holds the requirements, so the
  same word on every element would have meant two things at two levels.
  Satisfy and verify are the relations' names in 29148 and SysML. External
  requirement sets are sources of kind `requirement-set` with a prefix.
  ADR-014.
- One binary with verbs named by direction: `validate`, `document <target>`
  (the techspec moves here), `generate <target>` (code, through the plug-in
  `specarch-gen-<target>` on PATH, with protoc's protocol: the request on
  standard input, the files and diagnostics on standard output, the program
  writing the files, so `--check` and "only its folder" hold for every
  plug-in), `extract <source>` (designed, answers with status 2 until it is
  built), `version`. ADR-013. The implementation file's `generators` became
  `targets` and its `target` became `stack`, so the two words do not
  collide.
- New validator rules: `layout`, `need`, `stakeholder`, `source`,
  `environment`, `setting`, `secret_value`, and the warnings
  `need_unrefined`, `acceptance_missing`, `requirement_unsatisfied` (once a
  design exists) and `requirement_unverified` (once tests or checks exist).
  Tests and implementation suites carry a `level` after ISO/IEC/IEEE
  29119-1.
- The techspec gains chapter 2 from the constraints and assumptions,
  chapter 7 from the deployment and commissioning stages and then each
  implementation file, chapter 12 from the glossary, chapter 13 from the
  needs and requirements with the traceability matrix. It is one file,
  `techspec.md`, in the folder the implementation file names:
  `docs/techspec.md` here and `examples/library-lending/docs/techspec.md`.
- SpecArch's own specification moved to the tree and gained its
  stakeholders, needs, requirements SA-1 to SA-14, glossary, assumptions,
  constraints, deployment (two environments, release, rollback) and
  commissioning (three checks and the sign-off), with citations of the
  standards that shaped it, each clause checked against the standard's
  table of contents. The conformance suite is now the tests stage of that
  specification, `spec/tests/`: each test folder holds the design test, the
  case's arguments and expected output, and the files it runs on; a case
  that needs a plug-in carries it under `plugins/`. Thirty-two cases were
  added for the layout, the links, the secrets, the traceability warnings,
  the plug-in protocol and the two new verbs; every expected output was run
  and read before it was recorded.
- The library-lending example moved to `examples/library-lending/spec/`
  with every stage, cited sources (an interview, the lending policy, the
  data-protection rules), three environments and five commissioning checks,
  and its document in `examples/library-lending/docs/`.

Decisions by the owner, 2026-10-07: the choices of the validator and techspec
items stand as they are; a specification is a folder tree with one root
file; the whole life cycle is in scope, each stage optional until reached;
`why` and `standards` on every element, kept as two fields because one feeds
an Insight block and the other a Note block; one binary with verbs named by
direction, never separate programs; generators are plug-ins on PATH.

Decisions made here, for the owner to confirm or veto in review: the link
key renamed to `satisfies` and `verifies`; the implementation file's
`generators` renamed `targets` and `target` renamed `stack`; the single-file
kind dropped for the one root form; golden and red kept as a mark inside each
test rather than two folders; `cites` as the field name, with a registry of
sources rather than inline references; `conformance/` folded into
`spec/tests/`; the meta-model version kept at 0.1, since nothing has been
released.

Left out on purpose: validation of commissioning records (the documentor's
item), a schema for a fragment file on its own (editors validate the root
and the implementation files), and a golden test of `extract`, which cannot
run until the verb is built; the validator says so on every run.

will conflict with this work in the schema messages, the techspec, the
conformance folders and `spec/`; it is owed a migration once both land.

### Review of the folder tree, round one

The review found two faults in the new rules and both were fixed on the
branch, each with a conformance case under `spec/tests/`.

`need_unrefined` warned on a need whose status was already `rejected`, while
its own message told the reader to set that status to silence it. The rule
now skips rejected needs, as the requirement rules skip rejected and retired
requirements; `validate-need-rejected` is the golden case. The rule's one
line in the Rule enum, `docs/stages.md` and `docs/conventions.md` say so.

A folder at the root named after a section, such as `entities/` beside
`specarch.yaml`, was reported as a stage missing from `stages`, and adding it
there would only have produced the next error. The loader now tells the
reader which stage the section belongs to and where the folder goes, for
example `design/entities/`; `validate-layout-section-folder-in-root` is the
red case. The Swift validator gets both cases when it is migrated to the
tree.

The checks after the fix: `go vet` and `go test` pass, `validate spec
examples` reports no error and the known `extract` warning, and the
regenerated techspec passes `--check`.

## Expression errors name their own file

In a specification tree, an error in a check or a formula was reported
against `specarch.yaml` with the line of the file the expression was really
in (GitHub issue 1). The expression checks wrote the diagnostic against the
checker's own file; they now take the file of the expression's node, in the
Go and the Swift build alike. The other places that use the checker's own
file were checked and are right: an implementation file checked on its own,
a file given by name, and an error in the built-in schema. The red case
`validate-expression-in-stage-file` puts a formula and a check in files of
the design stage and expects each error at its own file and line.

## After commissioning, designed

The owner asked for SpecArch not to stop at commissioning: change requests,
defect fixes, version increases, and enough of production operation to
support them. `docs/maintenance.md` is the design; nothing of it is built
yet, and the roadmap lists the five items it splits into.

The first decision is where each thing lives. A file that changes or grows
with every event is a record, kept beside the specification under
`records/`, the rule the stage design already applies to commissioning
results.
So change requests, defects, releases and incidents are records that point
into the specification, and no element of the specification points back
at them. Monitors describe the live system the way requirements do, so
they are specification, in a new seventh stage, `operation`.

Versions follow Semantic Versioning 2.0.0, with the public interface of a
specification spelled out (paths, commands, channels, page routes,
settings). The validator, which sees one version, checks that records
agree with the specification and with each other; comparing two versions
needs a new verb, `specarch diff`, which is its own item.

What it changes in the stage design: the seventh stage, two source kinds
for external trackers (`change-set`, `defect-set`), and the commissioning
record becoming one kind of record file. Clause numbers of ISO/IEC/IEEE
12207:2017 (6.3.5, 6.4.12, 6.4.13) were checked against its table of
contents and SemVer's rules against semver.org. ISO/IEC/IEEE 14764 and
ITIL 4 are named without clause numbers, since their texts were not read.

## The documentor

`specarch document` now writes six documents: the technical specification,
the requirements specification, the test plan with its test cases, the
traceability matrix with its gaps, the deployment guide, and the
commissioning procedure with a Result column for every step and a sign-off
sheet. They are the five the specification already holds everything for,
plus the techspec. The user manual and the operations guide wait: they
need task-by-task and operational content that no section holds yet, and a
document of blanks would be one someone writes by hand anyway (ADR-016).

Wherever an element says why, or cites a source, every document now shows
it: a paragraph that starts with **Insight:** for the why, one that starts
with **Note:** for each citation ("From <title>, <edition>, clause <x>:
<what it says>"), under the element's heading, or after the table when the
element is a row, labelled with the row's name. A document ends with the
sources its Notes cite (ADR-015). A decision's why is now its Insight,
so the techspec no longer prints a separate Why paragraph for it.

Sections of the new documents are numbered as they appear, so a section
with nothing in it leaves no gap. A secret appears in the deployment guide
by name only, with a pointer to its description for where the value comes
from. The commissioning procedure is the form a run fills in; reading the
filled-in records is part of the design in `docs/maintenance.md`.

SpecArch's own documents and the example's are in their `docs/` folders,
beside the hand-written ones, and CI checks all six targets. New cases:
a golden case for each new target, the requirements one covering an
Insight only, a Note only, both, several Notes and neither, and a red case
for a citation of an undeclared source. `document-target-not-offered` now
asks for the manual.
